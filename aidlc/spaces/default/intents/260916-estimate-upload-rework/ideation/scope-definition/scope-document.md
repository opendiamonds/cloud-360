## In Scope（本次要做的能力）

### CAP-1 — 上傳估價表（Must）

使用者可上傳 AWS／Azure／GCP 的官方估價表，各雲各支援一種主格式（AWS CSV、Azure XLSX、GCP CSV）[T1]。至少上傳一朵雲即可進行後續處理 [T5]。原始檔不留存，解析完即丟棄，只保留結構化資料 [T2]。

上傳的估價表是獨立資源，可選擇性綁定一張架構圖，但不得設為必要關聯 [T8]。

### CAP-2 — 解析與明細呈現（Must）

解析後在畫面上呈現**逐項明細**：品項、規格、數量、金額，並附各雲總額 [Q2]。

解析採寬鬆策略：能解析的照用，解析不出來的列標記為「無法辨識」並仍繼續往下走，不得整批拒絕 [T4]。「無法辨識」的列必須在畫面上可見。

### CAP-3 — 省錢建議（Must）

指出哪些項目偏貴、可以換規格／改計費模式／使用保留量方案。三類建議中唯一的核心 Must——本能力做不到，整個改版不成立 [Q1]。

### CAP-4 — 跨雲比較建議（Should）

同一套架構在三朵雲的成本差異與取捨。輸入門檻為至少一朵雲；只上傳一朵時必須明示「資料不足以進行跨雲比較」，不得靜默略過 [T5]。

降為 Should 的依據：intent-capture 審查 R-01 指派本 stage 定義優先序，使用者選擇以省錢建議為核心 [Q1]。上游 `intent-statement.md` 不回改，以本階段的確認紀錄向下游傳遞。

### CAP-5 — 估價品質檢查建議（Should）

指出估價表本身的漏項、規格與架構不符、數量不合理。

**這項能力在系統中的角色比它的 MoSCoW 等級重要**：它是解析靜默錯誤（欄位對錯、月費當年費、幣別誤判）的唯一防線 [RISK-01]。降為 Should 意味著在最壞情況下，系統會呈現逐項明細與省錢建議，但沒有任何機制指出那些數字可能是錯的。這個後果在 RAID log 有對應條目，設計階段需要判斷是否補上機械檢查。

### CAP-6 — 成本 agent 遷移至 LangGraph（Must）

成本 agent 改用 LangGraph，經 OpenRouter 的 OpenAI 相容端點存取模型 [T6]。其餘五個走 `claude-agent-sdk` 的模組另開 intent 遷移 [P4]。

### CAP-8 — agent 按需查官網現價（Should）

**新增於 2026-09-16 的 approval-handoff**，來源 ADR-0017 §8。

agent 產生建議時，得經 `pricing_client` 呼叫三朵雲的**公開免帳號**價目端點確認現價，用來支撐「換成 X 規格可省 Y」這類具體主張。

四條界線，缺一不可：

1. **只有 agent 能呼叫**，系統本身不主動取價。這不是一條自動估價路徑。
2. **按需，非逐列**。agent 自己決定查哪幾筆，不做全表掃描、不做完整 SKU 對應。
3. **所得價格只寫入建議文字**，不得回寫明細表的任何數值、不得新增「官方現價」欄位。跨過這條線就等於系統在改寫使用者上傳的權威估價。
4. **只准公開免帳號端點**。走 IAM 的 boto3 Pricing Query API 禁用（`project.md` 原始規則，ADR-0017 §8 重申）。

查不到時 agent 必須明說查不到，不得改用推測值 [RISK-07]。引用現價時須標明那是**未折扣定價**——估價表可能含 CUD／RI／Savings Plan 折扣，兩者不該相等 [RISK-08]。

### CAP-9 — 解析結果的確定性機械檢查（Must）

**新增於 2026-09-16 的 approval-handoff**（AH-1）。

不依賴 LLM 的程式判定：總額對帳（逐列加總 vs 表上總額）、幣別一致性、數量落在合理範圍。**不需要 SKU 對應**，因此不繼承 RISK-07 的脆弱性。

**它與 CAP-5、CAP-8 是三件不同的事，不得在下游被合併**：CAP-5 是 agent 用自然語言指出可疑數字（Should，LLM 判斷）；CAP-8 是 agent 按需查現價（Should，LLM 決定查什麼）；CAP-9 是每次都跑、結果可複現的程式判定（Must）。只有 CAP-9 能作為 RISK-01 的確定性防線——前兩者都由 LLM 決定要不要做。

### CAP-7 — 既有自動估價路徑退場（Must）

移除 `cost_router.py` 全部 9 個掛在 `/diagrams` 之下的端點 [R1]；移除 4 張資料表（`diagram_cost`、`diagram_cost_line`、`pricing_cache`、`cost_audit_event`），不保留歷史資料、不做遷移 [R2]；移除 AWS／GCP／Azure 的 Playwright calculator runner 與相關 spike 腳本 [R3]。

**2026-09-16 修訂**：`pricing_client.py` 由退場清單**移出**，改由 CAP-8 承接（ADR-0017 §8）。其消費端模組（`sku_mapper.py`、`price_cache.py`、`pricing_azure.py`、`pricing_gcp.py` 等）的去留由 code-generation 依 CAP-8 實際需要判定，不預先承諾全留或全刪。`pricing_sdk.py` **確定刪除**——它是 boto3 IAM 路徑，仍在禁用之列。`pricing_cache` 資料表仍在退場清單，不因 CAP-8 而保留。

**退場與新功能上線在同一次部署完成** [Q3]。

## 交付排序

**value-first** [Q7]：先做上傳與明細顯示，建議功能後補。

**這個排序與 Q3（同批部署）合起來的後果**：第一次部署之後，自動估價已移除、上傳與明細可用，但還沒有任何建議——而「讓 agent 給建議」正是本次改版的目的。第一批交付完成到第二批之間存在一段產品能力低於現狀的窗口期。使用者在 Consolidated Summary Confirmation 已知情並確認。窗口期長度取決於第二批的交付速度，delivery-planning 應把縮短這段期間列為排程考量。

## 價值流：從上傳到決策

| 階段 | 使用者動作 | 系統產出 | 承載能力 |
|---|---|---|---|
| 1. 取得估價 | 在官方 Calculator 完成估價並匯出 | （系統外） | — |
| 2. 上傳 | 上傳一至三份估價表 | 接收、解析、丟棄原始檔 | CAP-1 |
| 3. 檢視 | 瀏覽逐項明細與總額 | 明細表、總額、無法辨識列 | CAP-2 |
| 4. 取得建議 | 等待（有進度指示） | 省錢建議、跨雲比較、品質檢查 | CAP-3／4／5 |
| 5. 決策 | 依建議調整架構或選雲 | （系統外） | — |

斷點在第 4 階段：這是唯一有外部依賴（LLM）、唯一不可控耗時、也是唯一沒有確定性正確性保證的環節。

## Assumptions & Open Questions

- ~~[assumption] CAP-5 降為 Should 後，若最終未交付，系統將沒有任何機制指出解析結果可能有誤。~~ → **已處理 2026-09-16**：approval-handoff AH-1 追加 CAP-9（Must），確定性機械檢查補位。
- [assumption] CAP-8 的四條界線（只有 agent 呼叫、按需非逐列、只寫建議文字、只准公開端點）沒有機械強制手段，全靠實作者遵守。第 3 條最容易被跨越——「在明細旁多加一欄現價」在 UI 上是自然的想法，但那正是被禁止的行為。設計階段應考慮是否需要可執行的檢查。

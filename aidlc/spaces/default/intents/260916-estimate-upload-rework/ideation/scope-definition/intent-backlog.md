## 排序：value-first

依 Q7 的 value-first 偏好，把「使用者看得到東西」的路徑排在前面：

**第一梯次**（可平行起跑，依賴為空）：PU-1、PU-3、PU-5、PU-10

PU-1 是純函式，可獨立驗證；PU-3 是刪除工作，不依賴任何新建物；PU-5 是新的模型存取路徑，屬 feasibility 認定的最大不確定來源之一，儘管排序偏好是 value-first，它的依賴為空且是兩條建議路徑的共同前置，越早開始越好；PU-10 是純文件工作但阻擋 construction，不能拖。

**第二梯次**：PU-2、PU-11（皆只需要 PU-1）

PU-11 排在這裡而非更後面，是因為它是 RISK-01 的確定性防線，而 RISK-01 的後果（畫面數字看似正常但其實是錯的）會在明細頁一上線就開始發生。PU-4 若先於 PU-11 落地，等於讓使用者先看到未經檢查的數字。

**第三梯次**：PU-4（需要 PU-2）

**第四梯次**：PU-6（需要 PU-5 與 PU-2）

**第五梯次**：PU-9（需要 PU-4 與 PU-6）；PU-7、PU-8、PU-12 可在此梯次或之後

## 兩條必須一起走的約束

**PU-3 與 PU-4 不得分批部署。** 這條約束比依賴圖上的邊更強——依賴圖只說先後，這條說不得分開。本專案是 deploy-on-merge，每個 Bolt 邊界都是一次真實部署 [S5]；PU-3 移除 `/cost` 頁面與其全部端點，PU-4 提供替代頁面。若分兩批，中間會有一次部署讓 `/cost` 是死的。Q3 選 A（同批部署）即是對這條約束的確認。

**PU-9 決定窗口期的結束。** value-first 讓 PU-4 先落地，但在 PU-9 完成之前，使用者看得到明細卻看不到任何建議。這段期間產品能力低於改版前。窗口期的長短是 delivery-planning 要優化的對象，不是既定事實。

## 每項的驗證方式與主要風險

| ID | 怎麼知道它完成了 | 主要風險 |
|---|---|---|
| PU-1 | 三雲樣本檔各自解析出預期的品項集合；property-based 測試涵蓋（ADR-0006 hard constraint，解析器為純函式） | 靜默錯欄（RISK-01）；格式無預警改版（RISK-05） |
| PU-2 | 端點回傳預期 schema；C1 allow／deny 雙向授權測試（team.md A＋B 規則） | 全 repo 第一個檔案上傳面，無既有形狀可沿用 |
| PU-3 | 9 端點、4 表、runner 皆不存在；既有測試同步移除；`openapi.json` re-dump | 隱性依賴未盤點到（ASSUM-04） |
| PU-4 | Playwright e2e 斷言明細表頭與至少一列值（team.md C 規則） | 整頁改寫，範圍膨脹（RISK-06） |
| PU-5 | 能對 OpenRouter 發出一次成功推論並取回結構化結果 | 與現行依賴的相容性未驗證（DEP-02） |
| PU-6 | 對已知偏貴的樣本估價表產出可辨識的節省項 | LLM 輸出品質不可控 |
| PU-7 | 只上傳一朵雲時明示「資料不足」；多朵時產出差異比較 | 同上 |
| PU-8 | 對刻意植入錯誤的樣本估價表指出該錯誤 | 這是 RISK-01 的唯一防線，而它是 Should |
| PU-9 | 端到端計時落在 5 分鐘內；全程有進度指示 | 3 分鐘目標未經實測（ASSUM-01） |
| PU-10 | ADR 明確廢止或改寫 M2，`validate_repo_contract.py` 通過 | 拖延成本隨時間上升 |
| PU-11 | 對刻意植入總額不符、幣別混用、數量異常的樣本檔，三種錯誤各自被指出；同一輸入跑兩次結果相同 | 無——這是純程式判定，是本 intent 少數不依賴 LLM 的部分 |
| PU-12 | agent 能對至少一個品項取得公開端點的現價並寫進建議文字；查不到時明說查不到；明細表的值未被改動 | SKU 對應失敗（RISK-07）；目錄價與折扣價被當成同一種東西比較（RISK-08）|

## Assumptions & Open Questions

- [assumption] PU-1 到 PU-10 的切分以能力邊界與驗證方式為準，實際的 Unit 切分由 units-generation 重做，本清單不預設它的結果。
- [assumption] PU-7 與 PU-8 標為 Should，但兩者都依賴 PU-5，而 PU-5 是 Must。若 PU-5 完成後產生三類建議的邊際成本很低，Should 與 Must 的區分在實務上可能沒有差異；反之若某一類特別難產，Should 才會真正發揮作用。
- [assumption] PU-10 列入本清單是因為它阻擋 construction，但它不是產品能力，delivery-planning 不應把它當成一個可展示的 Bolt。
- [open] 第一梯次四項是否真能平行，取決於是否有足夠人力。單人作業時 value-first 的實際順序需由 delivery-planning 決定。
- [open] PU-2 的結構化資料模型會決定 PU-8 能不能做機械檢查。若 domain-design 把明細存成無型別的 JSON blob，品質檢查就只剩 LLM 判斷一條路。

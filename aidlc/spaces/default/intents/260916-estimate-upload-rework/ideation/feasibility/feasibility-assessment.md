# 可行性評估：C1 成本估算改版（上傳估價表）

## 判定總結

**GO，但附兩項上線前必須先解決的前提。**

本次改版把估價的取數來源從「系統自動抓」換成「使用者上傳」，技術上沒有任何一段需要本專案沒有能力做到的事。三段工作各自的難度都在既有工程能力範圍內：讀一個固定格式的檔案、把結構化資料丟給模型、把結果畫出來。真正的風險不在能不能做，而在兩處判斷：**解析正確性沒有系統性防線**，以及**三分鐘的時間預算裡有一段是不可控的外部呼叫**。兩者都在 RAID log 有對應條目。

## 技術可行性

### 逐項判定

| 面向 | 判定 | 依據 |
|---|---|---|
| 檔案上傳 | 可行，但為全新能力 | 全 repo 目前沒有任何檔案上傳端點（無 `UploadFile`、無 multipart 處理）。FastAPI 原生支援，工作量在於這是第一次做，沒有既有形狀可沿用。[Q1][Q2] |
| 估價表解析 | 可行，需引入新依賴 | 各雲只需支援一種主格式（AWS CSV、Azure XLSX、GCP CSV）。CSV 用標準庫即可；XLSX 需新增試算表解析套件，目前 `requirements.txt` 完全沒有。[Q1] |
| agent 建議產生 | 可行，需新的模型存取路徑 | 現行兩條 provider 路徑都是驅動 `claude-agent-sdk`，LangGraph 不吃這個介面。決定沿用 OpenRouter 的 OpenAI 相容端點，等於新開一條與既有 agent 完全平行的呼叫路徑。[Q3][Q8] |
| 既有估價路徑退場 | 可行，範圍明確 | 9 個 `/diagrams` 端點、4 張資料表、兩支 Playwright runner 一次移除。範圍是可列舉的，不是模糊的重構。[Q5] |
| 三分鐘完成 | **有條件可行** | 解析是本機運算，毫秒級；瓶頸完全在 LLM 推論。三朵雲的完整品項送進模型、要求三類建議，單次推論可能數十秒到數分鐘，且不可控。需要進度指示與逾時處置。[Q3][Q7][Q9] |

### 不需要的東西

- 不需要雲端供應商帳號或憑證：價格由使用者提供，不再呼叫任何計價 API。這反而讓 `project.md` 的計價 API 禁令自然滿足。
- 不需要物件儲存：原始檔不留存，解析完即丟，沒有檔案持久化需求。[Q2]
- 不需要新的基礎設施層：沿用現有的 FastAPI + PostgreSQL + Cloudflare Tunnel 部署形狀。

## 風險分析

### 風險一：解析正確性沒有系統性防線（高）

最危險的失敗模式不是「讀不出來」，而是「讀出來但對錯了」——月費讀成年費、數量對到單價欄、幣別誤判。這類錯誤不觸發任何錯誤訊息，畫面上的數字看起來完全正常，agent 會照著錯的數字給出有自信的建議，使用者也沒有理由懷疑。

已定的處置是交給 agent 的「估價品質檢查」建議去指出不合理的數字。[Q10] 這個處置的性質要說清楚：它是**啟發式的、由 LLM 判斷的、沒有確定性保證的**防線，不是機械檢查。上游的成功指標只有「時間」，沒有任何一項衡量正確性。[S8]

### 風險二、三分鐘預算的不可控段（中高）

時間上限定為三分鐘且要有進度指示。[Q9] 這三分鐘裡，解析佔不到一秒，其餘全部是 LLM 推論。當使用者上傳三朵雲、每朵數十個品項，要求三類建議同時產出時，單次推論的耗時不由本系統決定。改版的動機正是「舊做法太慢太常失敗」[S8]——若新做法因為 LLM 逾時而同樣失敗，改版沒有解決原本的問題，只是把失敗點從 Playwright 換成模型。

### 風險三：完整估價內容送往第三方（中）

原始檔不在本地留存 [Q2]，但解析後的完整內容（品項、規格、數量、金額）會送進 OpenRouter [Q3][Q8]。估價表可能含客戶名稱、專案代號、內部服務命名。這兩個決定合起來的實際效果是：資料在本系統的留存面縮小了，但離開本系統的面擴大了。使用者已知情並選擇此配置，記為已接受的風險而非待解問題。

### 風險四：LangGraph 與既有 agent 框架並存（中）

本 intent 只把成本 agent 遷到 LangGraph，其餘五個模組另開 intent。[S8] 這段期間 repo 內同時存在兩套 agent 框架與兩條模型存取路徑（`claude-agent-sdk` 經 CLI／OpenRouter，以及 LangGraph 直接走 OpenRouter 的 OpenAI 相容端點）。兩套的錯誤處理、逾時、重試、記錄形狀都不同，維運面的認知負擔加倍。這正是 `stakeholder-map.md` 裡「維運這個 repo 的人」關注的事。

## 對現有系統的影響

- **資料庫**：移除 4 張表、新增上傳估價表所需的表。這觸發 `project.md` 的 blocking 規則——`schema_rbac.sql` 與 `DEPLOY.md` 必須在同一批變更中同步更新。
- **API 契約**：移除 9 個端點、新增上傳與建議相關端點。CI 有 OpenAPI drift 檢查，`openapi.json` 必須同批重新 dump，前端型別檔隨之更新。
- **前端**：Cost 頁面整頁改寫。既有頁面繞著「選一張架構圖看它的成本」設計，新頁面繞著「上傳檔案看建議」設計，不是加欄位的程度。
- **依賴**：新增試算表解析套件與 LangGraph 相關套件。`requirements.txt` 目前只有 `fastapi` 與 `pydantic` 精確釘選，其餘未 pin。
- **測試**：新端點依 `team.md` 的 B 規則需 TestClient 測試、依 C 規則需 Playwright e2e 斷言；C1 的 allow/deny 雙向授權測試義務仍然成立。解析器是純函式，落在 ADR-0006 property-based testing 的 hard constraint 範圍內。

## Assumptions & Open Questions

- [assumption] 「各雲一種主格式」假設三家官方工具的該格式在可見期間內穩定。實際上這三個匯出格式都可能在沒有通知的情況下改版，而解析器會在格式變動當天無聲失效。本階段未確認要不要對格式版本做偵測。
- [assumption] 三分鐘上限的可達性未經實測。要確認它，需要一次真實的端到端量測（三朵雲、代表性品項數、實際模型），這在 ideation 階段做不到，列為 nfr-requirements 的必答項。
- [assumption] 「可選綁定架構圖」[Q6] 的綁定語意未定義：綁定後兩者是否需要一致性檢查（估價表的品項與架構圖的元件對不對得起來），或只是一個標籤。這會大幅影響工作量。
- [assumption] 既有 4 張表全部移除 [Q5]，但新的上傳估價表功能仍需要稽核記錄（ADR-0006 的 audit logging 面向）。新稽核表的設計未在本階段確認。
- [assumption] 本階段未判定是否有法規框架適用。估價表內容為商業成本資料，不含個資或健康資料，故 PCI／HIPAA／GDPR 均不觸發；此判定基於估價表不含個人資料的前提，若實際檔案含客戶聯絡人資訊則需重新判定。

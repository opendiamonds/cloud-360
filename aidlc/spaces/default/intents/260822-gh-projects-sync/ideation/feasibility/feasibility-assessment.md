## 上游輸入

- 本評估的必要上游為 intent-capture 的 **intent-statement**（`../intent-capture/intent-statement.md`）：問題陳述、四類受益者、三項成功指標與已確認的產品邊界皆承襲自該文件。
- market-research 依 scope 設計跳過，其可選產出 **competitive-analysis**、**market-trends**、**build-vs-buy** 不存在；本評估不依賴市場面輸入，此缺席屬 scope 設計而非缺漏。

## 評估結論

**可行（conditional GO）**。技術路徑存在且有官方支援，但可行性建立在五個已確認的前提上，其中第一項是尚未滿足的外部依賴：

1. **憑證形式已定，但尚未取得**：以 GitHub App（org 層 Projects 讀寫）作為 CI 端身分 [Q1]。平台預設的工作流程憑證對 Projects 讀寫皆無效 [ext:E1]，而本 repo 至今沒有任何 GitHub API 憑證先例 [repo:R4]，因此這是一項需要人工完成的前置依賴，未完成前整個機制無法運作。
2. **本機與遠端的可見性落差已被明確吸收**：AI-DLC 的 stage 推進發生在開發者本機 [repo:R2]，遠端在推送前看不到任何變化 [repo:R1]。事件因此定義為推送與 PR 生命週期兩條 [Q2]，並以「推送後 5 分鐘內完成、PR 事件優先於推送」作為可判定的門檻 [Q9]。
3. **綁定已由推測改為確定**：在自動建立追蹤項目的同一時機記錄其識別碼並寫回 intent 的紀錄，之後一律查表 [Q8]。此決定取代了原先「由代理人依標題語意推測」的選擇，理由是自動建立的當下識別碼本就是已知事實，且推測式綁定會使一致率指標失去可定義的分母 [intent:Q12]。
4. **表達力落差已被接受**：狀態欄位只有三格能表達進行中的語意，與 19 個執行中的 stage 之間落差顯著 [repo:R6] [repo:R7]；決定不改動既有欄位，改以三態呈現並將細粒度進展承載於他處 [Q4]。
5. **驗證落點已在本階段決定**：映射邏輯以 dry-run 斷言、另加對真實測試項目的端到端驗證 [Q6]，並以寫入前回讀比對防止寫錯對象 [Q10]。此決定是為了讓兩條在本 intent 相交的規則（禁止以 repo 內程式承載 [memory:M1]、construction 必須產出實際跑綠的自動化 [memory:M3]）不在 construction 階段才發現無處落腳。

## 技術可行性

以能力層描述現況與落差（技術細節的出處見問題檔 `## Sources`）：

| 面向 | 現況 | 落差與可行性 |
| --- | --- | --- |
| 寫入看板狀態 | 平台預設憑證對 Projects 讀寫皆無效 [ext:E1]；工作流程框架本身提供受管的看板更新輸出型別，可依欄位名稱設定單選欄位 [ext:E3] | 路徑存在且為框架原生支援；可行性完全取決於憑證是否備妥 [Q1] |
| 讀取 AI-DLC 進度 | 進度事實所在的紀錄檔在版控內 [repo:R1] | 遠端讀得到，但只讀得到已推送的內容；即時性落差由 [Q2] [Q9] 定義吸收 |
| 觸發即時性 | 推進在本機發生，遠端無鉤子可掛 [repo:R2] | 無法做到「stage 一完成就更新」；改以推送與 PR 為事件並訂出延遲上限 [Q9] |
| intent 與看板項目的對應 | 雙方互不記錄對方的識別碼 [repo:R1] [repo:R6] | 由 [Q8] 在自動建立時建立確定綁定；此為整個機制的地基 |
| 狀態表達粒度 | 6 個選項中僅 3 個能表達開工後的語意 [repo:R6]，對應 19 個 stage [repo:R7] | 落差真實存在，[Q4] 選擇接受並將細節外置，而非改動既有欄位 |
| 驗證能力 | 不得以 repo 內程式承載 [memory:M1]；工作流程的產出檔目前不受任何 CI 閘門驗證 [repo:R5] | 驗證落點由 [Q6] [Q10] 指定；缺口是產出檔本身仍無閘門，列為風險 |
| 內部經驗 | repo 內 12 組既有代理式工作流程，零 Projects 使用先例，且從未使用過任何 GitHub API 憑證 [repo:R3] [repo:R4] | 全新路徑，無內部經驗可循；官方文件已查證但未經本 repo 實測 |

## 驗證方式

- 映射邏輯以 dry-run 步驟輸出預期結果並比對，不觸及真實 API [Q6]。
- 另設一個真實的測試項目，於 CI 中實際寫入並讀回斷言，以涵蓋權限與 API 契約這類 dry-run 看不到的失敗 [Q6]。
- 每次寫入前先讀取目標項目並與預期比對，不符即中止寫入並開立問題單 [Q10]。此措施保護的是後續更新，不保護首次建立（見風險分析）。
- 同步失敗與對帳發現的不一致，皆以工作流程失敗加自動開立問題單通報 [intent:Q9]；框架具備對應的輸出型別 [ext:E4]。

| --- | --- | --- | --- |
| R-1 | 首次自動建立追蹤項目時，尚不存在可回讀比對的既有對象，[Q10] 的防護在此刻不成立 [Q7] | 首建若指向錯誤脈絡，錯誤會被固化成往後查表的依據 | **未解**；記入 raid-log，需在設計階段補一條首建專屬的檢查 |
| R-2 | 推送與 PR 兩條觸發都會寫狀態，可能互相覆寫 [Q2] | 看板狀態來回跳動，可信度反而下降 | 由 [Q9] 的「PR 事件優先」緩解；排程對帳與此優先序的互動未定 |

## ADR-0006 Security Baseline 四面向判定

`project.md ## Mandated` 要求對每一項變更逐項檢查此四面向，不適用者須附理由 [memory:M2]。

| 面向 | 判定 | 影響與處置 |
| --- | --- | --- |
| IAM | **適用** | 新增本 repo 第一個 GitHub API 身分 [repo:R4]。權限限縮為組織層看板讀寫，不索取 repo 內容寫入權；憑證以 repo secret 承載，名稱由框架規定 [ext:E2]。輪替週期、撤銷路徑與「憑證失效時如何被察覺」尚未定義，列入 raid-log 的 Dependencies 與 Risks（R-5）。 |
| Encryption | **部分適用** | 傳輸層由平台 API 的 HTTPS 承擔；靜態機敏資料僅有上述憑證，由平台的 secret 機制加密保管。本機制不自行儲存任何機敏資料，亦不新增資料庫或檔案落地。無自訂加密需求。 |
| Network exposure | **不適用** | 不新增對外服務、不開啟任何埠、不新增可被外部存取的端點；全部行為是託管執行環境對平台 API 的出站呼叫。既有的對外暴露面不受本變更影響。 |
| Audit logging | **適用** | intent-capture 的成功指標之一為「每次狀態變更都能說出是哪個 intent、哪個 stage、什麼時間觸發」；本階段的確定綁定 [Q8] 是該指標可判定的前提。失敗與對帳不一致一律開立問題單留痕 [intent:Q9]。以 App 身分執行使動作在組織稽核紀錄中具備可識別的主體，優於個人憑證 [Q1]。 |

## Assumptions & Open Questions

- 組織層具備安裝 GitHub App 的管理權限，且安裝流程不受組織政策阻擋；此點未經實際嘗試驗證。 [assumption]
- 框架用來承載 App 識別碼的變數名稱與其文件描述不一致（名稱指向應用程式識別碼，敘述指向用戶端識別碼），兩者為不同的值；實作時需逐一嘗試確認。 [assumption]
- 框架文件所述的看板更新行為（依欄位名稱設定單選欄位、名稱不分大小寫）在本 repo 的實際執行環境中如文件所述；本輪僅查證文件，未實測 [ext:E3]。 [assumption]
- 看板的狀態欄位識別碼在本 intent 的實作期間保持穩定；若有人手動改動欄位定義，綁定與映射需重新確認 [repo:R6]。 [assumption]
- 「細粒度進展承載於他處」的具體落點（問題單留言或看板自訂欄位）尚未選定，屬設計階段決定 [Q4]。 [assumption]
- 排程對帳的頻率尚未決定；其與 [Q9] 觸發優先序的互動亦未定義。 [assumption]
- 看板更新的操作次數上限與超限時的行為尚未確認 [ext:E3]，可能影響多 intent 並行時的完整性。 [assumption]

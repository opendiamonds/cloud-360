## Persona 集合的由來

`intent-statement` 列了四類受益者。本站依 [Q1=A] 做了兩處調整，兩處各自的理由如下——**兩者都不是新的範圍決定，是同一組已核可需求的主體歸屬**：

- **「未來的自己」併入 P1 開發者**：兩者在看板上的行動完全相同（都是讀），只有時間差。分開會產生一組驗收條件幾乎重疊的故事，而 `project.md ## Corrections` 對合併故事的紀律要求逐條確認 AC 承接——與其事後合併，不如一開始就不拆。P1 的 goals 明列回溯需求，該受益者的需求未被丟失。
- **新增 P4 同步機制維運者**：此角色**不在** `intent-statement` 的受益者清單上，但 requirements 有三類工作明確要求有人去做——處理通報 issue（FR-E1，FR-C1 的中止亦以開 issue 收尾，兩者對人是同一件事）、審反向 PR（FR-G1）、看對帳的兩份清單（NFR-O2）。這三類各自都可追溯到已核可的上游，**P4 是它們的主體歸屬，不是新引入的需求**。若不設 P4，這四條會被寫成無主詞的系統行為，或掛到 P1 身上——而 P1 故事的核心 benefit 是「不用再記得手動改」，同一主體同時要「不必費心」又要「收到通報去修」，兩種期待互相沖淡。

**P4 目前與 P1 是同一個人。** 這是誠實記載而非缺陷：persona 分的是**角色**不是身體，同一人在不同角色下的目標與判準確實不同。若未來團隊擴編，P4 可能落到不同的人身上，屆時故事不需改寫。

## Persona 定義

### P1 — 開發者（含未來的自己）

| 項目 | 內容 |
| --- | --- |
| 身分 | 本 repo 的唯一開發者（Danniel），同時是本 intent 的唯一決策者 |
| 脈絡 | 以 AI-DLC 逐 stage 推進 intent；每個 stage 完成後會 commit 並推送 record；跨 session 工作，經常在數日後回頭 |
| 目標 | ①跑完 stage 之後**不需要記得**回去改看板 ②事後回溯某個功能走過哪些 stage、卡在哪裡時查得到 |
| 痛點 | 「每跑完一個 stage 還要記得回去手動改看板狀態，經常忘記」[intent:Q2]；「事後回溯……無跡可循」[intent:Q2] |
| 在看板上的行動 | **讀**（確認狀態已自動更新）；不主動寫 |
| 主要相關故事 | S-1、S-2、S-4、S-5 |

### P2 — 協作者

| 項目 | 內容 |
| --- | --- |
| 身分 | 本 repo 的其他協作者 |
| 脈絡 | 不跑 AI-DLC，透過看板理解專案進度；會在看板上手動拖動卡片表達自己的判斷 |
| 目標 | ①從看板看出別人正在做什麼 ②自己在看板上的操作**算數**，不會被機制悄悄彈回 |
| 痛點 | 「看板狀態不準，看不出別人正在做什麼」[intent:Q2] |
| 在看板上的行動 | **讀 ＋ 寫**（拖動卡片、改欄位）——這是四個 persona 中唯一會寫的 |
| 主要相關故事 | S-2、S-6、S-11 |
| 已知未確認 | 其具體成員在 `intent-statement` 中「未經逐一確認其對本功能的實際需求」（該檔的 assumption，本站沿用不擴大） |

### P3 — 觀看者

| 項目 | 內容 |
| --- | --- |
| 身分 | 不參與開發、只看看板的人 |
| 脈絡 | 不參與開發；其查看 repo 的頻率與是否有交叉驗證管道，**上游未定義**（`stakeholder-map.md:41` 的既有 assumption：「其人數、身分與查看頻率均未定義」）。本站據此以「無其他管道」為**最壞情境**進行設計，此為本站假設而非已知事實（見文末 Assumptions） |
| 目標 | 看得到 AI-DLC 內部走到哪一站，而不只是「有一個 issue 開著」 |
| 痛點 | 「只看看板，看不到 AI-DLC 內部的 stage 進度」[intent:Q10] |
| 在看板上的行動 | **只讀**；不寫。是否會去查 repo 佐證上游未定義，本站按「不會」設計 |
| 主要相關故事 | S-1、S-2、S-3、S-4、S-5 |
| 特別註記 | 此角色在第一輪答案中與受益者清單不一致，**經追問後確認確實是受益者** [intent:Q10]。在本站採用的最壞情境下（無交叉驗證管道），**看板寫錯對他的傷害最大**——S-3（寧可不寫，不可寫錯）主要是為他而寫。若日後確認他其實會查 repo，此推論的強度隨之下降，但 S-3 的必要性不依賴它（P2 亦受益） |

### P4 — 同步機制維運者

| 項目 | 內容 |
| --- | --- |
| 身分 | 負責讓同步機制本身持續可信的人（目前與 P1 同一人，見上方說明） |
| 脈絡 | 不在看板上找進度，而是在**機制的輸出**裡找異常：通報 issue、對帳報告、反向 PR、workflow 紅燈 |
| 目標 | ①機制出事時知道**出什麼事、哪個 intent、哪個 stage、什麼時間** ②判斷該不該接受看板端傳回來的改動 ③看得出可信度本身是好是壞（一致率、補平次數、延遲分佈） |
| 痛點 | 目前**沒有任何機制**會告訴他哪一格是錯的。`intent-statement` 記載的既成事實（看板 item 標 In review、對應 issue 其實已關閉）在無任何通報機制的情況下持續存在——兩件事並存，本站不宣稱前者是後者的成因（該檔記載的成因是「看板狀態靠人工維護」[Q1]） |
| 在看板上的行動 | **不直接操作看板**；讀機制的輸出，並在 repo 側行動（審 PR、修設定、開 issue） |
| 主要相關故事 | S-3、S-6、S-7、S-8、S-9、S-10 |
| 來源 | 本站依 [Q1=A] 新增；其三類工作各自追溯至 [req:FR-E1]／[req:FR-C1]（處理通報 issue）、[req:FR-G1]（審 PR）、[req:NFR-O2]（看清單） |

## Persona 優先順序

排序依據是**「這個 intent 的成功指標為誰而設」**，不是使用頻率。

| 序 | Persona | 理由 |
| --- | --- | --- |
| 1 | **P1 開發者** | 「零人工更新」這項成功指標**直接**衡量他的體驗 [intent:Q2]；他也是唯一決策者 [stakeholder-map:Q5]（此句的來源是 `stakeholder-map.md`，非 `intent-statement`） |
| 2 | **P4 維運者** | 核心價值是可信度，而可信度的守門工作全落在他身上。他失效時，其餘三人看到的東西會靜默地變成錯的 |
| 3 | **P3 觀看者** | 經追問後**正式列為本次要服務的對象** [intent:Q10]。在本站的最壞情境假設下，他也是「看板寫錯」傷害最大的人；該假設若被推翻，此列可下降一位，但不影響 P3 的受益者身分 |
| 4 | **P2 協作者** | 需求真實（FR-G3 專為他而設），但其具體成員與實際需求未經逐一確認（`intent-statement` 的既有 assumption） |

## Persona 之間的關係

- **P1 與 P4 是同一人的兩種角色**，且**目標會互相拉扯**：P1 要「不必費心」，P4 要「主動去看有沒有出錯」。機制若把太多判斷推給 P4（例如每次小落差都開 issue），就會侵蝕 P1 的核心價值。這條張力是 S-8 與 S-9 的設計約束，明記於該兩則故事。
- **P2 的寫入與機制的寫入會在同一格上相遇**：這是 FR-G3「暫停覆寫」與 FR-C1「回讀後中止」的共同來源。P2 與機制之間**不是主從關係**——[Q5=D] 已定案為「機制不得直接改 `aidlc-state.md`，須開 PR 給人審」，即 P2 的意見要經過 P4 才成為 record 的事實。
- **P3 是否有交叉驗證管道，上游未定義**；本站按「沒有」設計，因此他是「錯誤的覆蓋感比沒有覆蓋更危險」這條原則在本 intent 的具體落點。這是本站的最壞情境假設，不是已知事實。

## R-1 群：區塊必載內容

**R-1.1～R-1.4** 四項皆為 [US-OQ-3] 定案、[ad:component-methods.md] §C-6 逐字列出，**本站一項未增未減**；**R-1.5 是本站新增**（來源 [US:S-6 AC 5]，由 ADR-0015 §12 承載），故下表共五條。

> **前言於 2026-08-30T00:48:38Z 補上範圍限定（reviewer iteration 3 Group B F8）**：先前寫「四項皆為……本站一項未增未減」而下表實列五條，讀起來像是把新增的 R-1.5 也算進「未增未減」。限定不是為了讓陳述技術性成立，是因為 R-1.1～R-1.4 的「未增未減」本身是一個有價值的事實（它們是 [US-OQ-3] 的逐字轉錄），不該被 R-1.5 稀釋掉。

| # | 規則 | 可判定方式 |
| --- | --- | --- |
| R-1.1 | 含目前 Status 與其 `traceable_row`；**或**機制決定不寫的原因類別與 ISO 8601 時間戳 | 渲染輸出的 fixture 比對；兩支分別有 fixture |
| R-1.2 | 含 `[S]`（在 scope 內被跳過）與 `— SKIP`（不在 scope 內）的差別（[req:FR-F3]） | 兩個只在此處不同的 `Decision` 產生**可區分**的區塊文字 |
| R-1.3 | 含固定說明「Status 欄位為權威來源；本 issue 依 OOS-2 不自動關閉，其開／關狀態不表示進度」 | 字串比對 |
| R-1.4 | 含固定說明「自訂欄位為空的 item 不由本機制維護」（[Q6=A] 的規則落點） | 字串比對 |
| R-1.5 | `Context.rejection_notice` 非 `null` 時，**額外**載明「該次人工改動未被採納」與其 `closed_at`（[US:S-6 AC 5]）；為 `null` 時不渲染該段 | 兩個只在此欄不同的 `Context` 產生**可區分**的區塊文字，且兩者 `parse` 回來的 `Block.rejection_notice` 分別為該值與 `null` |

> **R-1.5 是送審前自檢補上的（2026-08-29T23:42:35Z）**，不是 [US-OQ-3] 的第五項必載內容——上一行「四項皆為 [US-OQ-3] 定案、本站一項未增未減」講的是 R-1.1～R-1.4，該陳述維持成立。R-1.5 的來源是 [US:S-6 AC 5]，其承接鏈為 U-6 的 R-6.2b 填 `Context.rejection_notice` → 本規則渲染。`Context` 的定義見 `domain-entities.md`（同批補上的契約缺口）。
>
> **先前此處寫「`null` 支的輸出與 R-1.5 引入前逐字相同」，該子句已於 2026-08-30T00:48:38Z 撤回（reviewer iteration 3 Group B F3 Critical）。** 它與同批寫入的另一個宣稱**不可同真**：`rejection_notice` 是 `Block` 的新增欄位 ⇒ 依 ADR-A6 與下方 R-4 群是一次格式變更 ⇒ 須 bump `format_version`；而 `format_version` **內嵌於區塊文字**且在 `content_hash` 涵蓋範圍內（見 `domain-entities.md`「為什麼 `format_version` 要進區塊」），bump 之後所有既有 item 的區塊文字與雜湊**必然改變**。
>
> **保留的是 bump，撤回的是「逐字相同」**。理由：不 bump 會讓新舊渲染器對同一段文字解析出不同的 `Block`，那正是 ADR-A6 點名的最危險失敗模式；而 bump 的代價（重新基準化全部既有 item）在 **Bolt 1 首次上線時為零**——既有受管 item 數是 0。這是這次 bump 最便宜的時點，延後到任何後續 Bolt 都要付全量重新基準化的代價。已由 **ADR-0015 §12** 承載。

R-1.2 與 U-1 的關係要講清楚：**U-1 決定 Status（且 `[S]`／`— SKIP` 對 Status 無影響，[req:FR-B3]），U-2 負責讓那個差別在別處看得見。** 兩者合起來才滿足 FR-B3 的兩個要求（Status 相同、差別可讀）。這也是 U-1 的 R-3.6 能把 `[S]` 判為「不算動過」的前提——差別沒有消失，只是不在 Status 上。

## R-2 群：雜湊

| # | 規則 |
| --- | --- |
| R-2.1 | `content_hash` 的輸入是 `Block`（parse 後的結構），輸出 sha256 |
| R-2.2 | 相同 `Block` 必得相同雜湊；任一欄位不同必得不同雜湊（[ug:unit-of-work.md] U-2 完成判準前兩條） |
| R-2.3 | `decided_at` **在**涵蓋範圍內（[Q2=A]） |
| R-2.4 | `format_version` 在涵蓋範圍內——它是 `Block` 的欄位 |

**R-2.3 的隱含依賴（必須被寫下來，否則會被預設沿用而破功）**：兩次語意相同的判定會有不同的 `decided_at` ⇒ 不同雜湊。churn 不會發生，**只因為** [ad:services.md] 的 S-A 明文「有漂移才寫」——語意沒變就不會走到重寫。

> **這條依賴不在任何依賴圖上，也沒有任何測試會在它被破壞時失敗。** 若未來有人讓區塊在無漂移時也重寫（例如加一個「定期刷新」或「每輪都蓋一次以自癒」），看板上每個 item 每輪都會變一次，而且**反向同步會把它讀成人為變更**。[Q2=A] 的選項本文已載明此代價。建議的承接方式：在 **U-9**（本 intent 唯一的自我測試層；先前誤寫為 U-6）的斷言中加一條「連續兩輪無語意變化 ⇒ 看板 item 的 `updated_at` 不變」的斷言——但那是 U-9 的落點（[Q2=A] 的選項本文原寫「U-6／U-9」，其中 U-6 沒有自我測試層，本 intent 的自我測試層只有 U-9），本站只標出。

## R-3 群：`parse` 的行為

| # | 規則 |
| --- | --- |
| R-3.1 | 無受管標記的 issue body → 回 `null`（[ad:component-methods.md] 逐字） |
| R-3.2 | 有標記但版本標記缺失或不可解析 → 回 `null`（與 R-3.1 同一條路徑） |
| R-3.3 | 有標記且版本在**已知版本集合**內 → 套用該版本的解析器，回 `Block` |
| R-3.4 | 有標記且版本**高於**當前渲染器 → 回 `null` |

**R-3.4 是刻意的保守選擇**：一個比自己新的區塊代表有另一個版本的機制在寫同一個看板，此時「解析不出來」比「用舊規則猜」安全。

> **但這個保守選擇在現行簽章下做不到，reviewer iteration 1 判為 Critical。已於 2026-08-29T15:24:44Z 標出並指派。**
>
> `parse` 的簽章是 `(issue_body) -> Block | null`（[ad:component-methods.md]）。**R-3.1（完全沒有標記）與 R-3.4（有標記但版本較新）回傳同一個 `null`**，型別上沒有任何東西讓呼叫端分辨。
>
> 而本設計已承諾的呼叫端行為是 [ad:services.md] 的「**不得重複附加區塊——`parse` 先跑再 `render`**」。於是「`parse` 回 `null`」最自然的實作是「沒有偵測到區塊 ⇒ 渲染一個寫進去」——**恰恰是 R-3.4 要防的覆寫**。R-3.4 宣稱「機制不會覆寫它」，字面上不成立。
>
> **這不是罕見邊角**：正向同步對**任何分支**的 push 觸發並直接寫真實看板（[ad:services.md]），所以任何進行中的 `format_version` 升版、或一次升版合併後的 `revert`，都會在一般 git 工作流下重現它。而 ADR-A6 正把「舊版程式誤讀新格式區塊」點名為本設計**最危險的失敗模式**。
>
> **指派**：`parse` 的簽章在 [ad:component-methods.md]（已通過 application-design 三輪 reviewer 的上游），故**標出不逕改**。**本項已改由 ADR-0015 §6 承載**（送審前自檢，2026-08-29T23:42:35Z）——在單元產出裡寫「指派 X」對一份已定稿的上游而言是一張沒有收件人的便條，ADR 才是這批修訂唯一有效的載體，先例為同 intent 的 ADR-0014。建議修法二選一——(a) 回傳三態（`Block` ／ `Unmanaged` ／ `FutureVersion`）；(b) 另加一個廉價述詞 `has_managed_marker(issue_body) -> bool`，讓呼叫端在 `parse` 回 `null` 時能區分。**確認人為 Bolt 1 的 gate**（U-2 於 Bolt 1 交付）；指派目標 stage 為 EXECUTE，無被 skip 的風險。
>
> **在修正落地前，R-3.4 的保護不存在**——這一點必須寫進實作註解，不得預設它已生效。

代價是這種情況下不會有任何告警；**若要告警需 U-5 的落點，本站不擅自指派**。

## R-4 群：格式契約的互鎖（[Q1=C] 定案，ADR-A6 指派）

ADR-A6 把「設計一個**機制**（而非流程紀律）使格式變更與重新基準化不能脫鉤」指派給本 stage。[Q1=C] 的三道互鎖：

| # | 檢查 | 觸發紅燈的情形 |
| --- | --- | --- |
| R-4.1 | golden fixture 快照與當前渲染器輸出逐位元一致 | 改了 `render` 而沒更新快照 |
| R-4.2 | `FORMAT_VERSION` 等於 `format-migrations` 登錄表最後一筆的版本 | 更新了快照但沒 bump 版本 |
| R-4.3 | 登錄表最後一筆含非空的重新基準化說明與其執行方式 | bump 了版本但沒加登錄 |

三道互鎖使「改格式」這個動作無法在不碰其餘兩者的情況下通過 CI。

**天花板（誠實記載，[Q1=C] 選項本文即已載明）**：登錄表可以被寫成空殼——加一筆、填上說明、但不真的執行基準化。**三道互鎖保證作者無法「忘記」，不保證他「做了」。** 唯一能保證做了的形狀是 [Q1=B]（格式指紋 ＋ 錯配時自動重新基準化），但它把 ADR-A6 的「單一 PR 一次性遷移」改成「逐 item 惰性遷移」，屬對已核可 ADR 的實質變更。**兩者的取捨已在 Q1 呈現並由人裁定，本站不重開。**

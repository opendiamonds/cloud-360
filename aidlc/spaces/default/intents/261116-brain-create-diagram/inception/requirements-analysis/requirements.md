## Intent Analysis

- **目標**：使用者在入口頁或小助手說「幫我畫一張……架構圖」，不必離開對話，就在目前的系統下得到一張完成的新圖，專案頁看得到它。[desc][IC:Q6]
- **要解決的問題**：系統下沒有圖時架構設計直接失敗，使用者必須離開對話去工作區建空白圖；使用者不知道要先建圖而以為大腦壞了。[IC:Q1]
- **受益者**：所有有大腦使用權（K1）的使用者；其中有架構編輯權者可以新建，沒有者得到明確說明。[IC:Q2][IC:Q9]
- **類型與範圍**：既有大腦能力的強化；跨意圖路由、工作編排、WebSocket 反問候選、架構圖資料與前端清單。
- **深度**：Standard。

## Functional Requirements

### FR1 — 新建架構圖並交給架構設計能力產出

- **FR1.1** 作業對象是一個系統、且判定為「要新的一張」時，大腦以**使用者自己的權限**經既有建圖端點（`POST /api/collab/diagrams`，帶 `system_id`）在該系統下新建一張圖，再走既有的「讀圖 → 架構設計 agent 產圖 → 存圖」鏈完成產出。[desc][IC:Q6]
- **FR1.2** 系統下**沒有任何圖**時，畫圖請求依 FR2.2 的判定表處理；除了明確的修改意圖（改走 FR2.4），都直接新建，不再回「這個系統下沒有掛上的架構圖」。[IC:Q1][desc]〔推導：無圖時「判定不明」也新建，因為沒有可修改的對象〕
- **FR1.3** **建圖成功當下**（不等產圖完成）作業對象即切到這張新圖；之後說「改一下」即指它，產圖失敗時它就是那張草稿。[RA:Q6][RA:Q10]
- **FR1.3a** 既有建圖端點會把使用者的「最後開啟的圖」設為新圖；這與 FR1.3 作業對象切到新圖一致，接受此副作用，下次進工作區會開啟這張圖。〔推導〕
- **FR1.4** 〔推導〕一個工作項至多建立一張圖：同一工作項的重試、復原掃描或重送，不得再建第二張；工作項記住它建立的圖並在後續步驟沿用。（corner：重試不得重複副作用）
- **FR1.5** 可測形式：在只有系統、沒有圖的作業對象下說「幫我畫一張電商網站的 AWS 架構圖」→ 工作項完成、該系統下多一張正式狀態的圖、專案頁可見、作業對象為該圖。

### FR2 — 新建或修改的判定

- **FR2.1** 作業對象已有圖時，依句意判斷：要新的（例如「新的」「另一張」）就新建；要修改（例如「改」「加上」）就改目前的圖；判斷不出來就反問。[IC:Q3]
- **FR2.2** 判定由路由向模型多問一題「是否要一張新的圖」，取得機率 p；這一題**併入既有的同一次路由請求**，不另發一次模型呼叫〔推導〕。設 t 為信心門檻（`BRAIN_ROUTER_CONFIDENCE_THRESHOLD`，現值 0.7，`260920-orchestration-brain` 的 FR1.7）。判定表：[RA:Q3]

  | 作業對象 | p ≥ t（要新的） | p ≤ 1 − t（要修改） | 1 − t < p < t（不明） |
  |---|---|---|---|
  | 系統，系統下**沒有**圖 | 新建 | FR2.4：回覆沒有圖可改並反問是否新建 | 新建〔推導〕 |
  | 系統，系統下有圖 | 新建 | 依 FR3.2 選定要改的圖 | 反問「新建或修改」 |
  | 某張圖（含草稿） | 新建 | 改這張圖 | 反問「新建或修改」 |
- **FR2.3** 判定規則是不讀 DB、不連外的純函式，並以 property-based 測試鎖住下列性質（ADR-0006 agent routing hard constraint）：[RA:Q3]
  - 對任何 t ∈ (0.5, 1]，新建與修改互斥，同一個 p 不會同時成立；
  - 作業對象有圖時，1 − t < p < t 一定反問；
  - 對 p 單調：p 增加不會使結果由「新建」變為「修改」；
  - 相同的 p、t 與作業對象，判定結果決定性一致。
  〔推導：四項性質為分析者依判定表導出〕
- **FR2.4** 系統下沒有圖、使用者卻表達修改意圖時，回覆目前沒有圖可改，並反問是否要新建一張。[RA:Q4]

### FR3 — 作業對象不足時的反問

- **FR3.1** 沒有作業對象，或作業對象只是專案（沒有系統）時，反問要掛在哪個系統，列出使用者**擁有的**系統作為候選。[IC:Q4]
- **FR3.2** 系統下有多張圖、使用者要修改但作業對象只選到系統時，反問要改哪一張，列出該系統下使用者自己的圖作為候選；作業對象已選到某張圖就直接改那張。取代現行「這個系統下有多張架構圖，請在脈絡列選定要用的那一張」的直接失敗。[IC:Q10]
- **FR3.3** 使用者名下沒有任何系統時，回覆需要先建立專案與系統，並提供到專案頁的路徑；不自動建立專案或系統。[IC:Q11]
- **FR3.4** 反問候選**可直接點選**：候選帶系統或圖的識別碼，使用者點選後大腦依該候選繼續原本的請求，不必再說一次。[RA:Q2]
- **FR3.5** 〔推導〕點選時伺服器**重新驗證**：候選的系統或圖必須仍存在、且使用者仍有權限；不符時回覆說明並重新列出目前可選的候選，不得依客戶端送來的識別碼直接執行。（corner：失效參照、不信任客戶端）
- **FR3.6** 〔推導〕候選依「最近更新時間由新到舊，再依識別碼」排序；超過上限時只列前若干筆並說明「其餘請用切換對象選取」。上限數值由 contract-design 定案。（corner：大量項目、決定性排序）

### FR4 — 權限

- **FR4.1** 新建需要架構編輯權（沿用建圖端點既有的檢查）。有 K1 但沒有架構編輯權的人說要畫圖時，不新建，明確回覆「建立架構圖需要架構編輯權」，並說明向平台管理者申請角色變更（管理者在「使用者角色」頁調整）。[IC:Q9][RA:Q1]
- **FR4.2** 修改既有圖沿用既有權限檢查，行為不變。
- **FR4.3** 所有新建、修改與候選驗證都以使用者自己的 token 經既有端點執行，大腦不取得使用者本身沒有的權限。

### FR5 — 新圖的名稱

- **FR5.1** 名稱由使用者的句子取出主題：去掉指令詞，截到固定長度，補上「架構圖」；不額外呼叫模型。[IC:Q5][RA:Q5] 指令詞初版清單〔推導〕：「幫我」「請」「麻煩」「畫」「做」「建」「一張」「一個」「新的」「另一張」「架構圖」「的」；最終清單由 contract-design 定案（OQ1）。
- **FR5.2** 〔推導〕去掉指令詞後主題為空（例如只說「幫我畫一張架構圖」）時，以「<系統名> 架構圖」為名。（corner：空字串）
- **FR5.3** 〔推導〕截長以可見字元計算，不切斷組合字元；控制字元與標記去除後才當名稱。（corner：長文字、控制序列）
- **FR5.4** 同一系統下已有同名的圖時，加序號（例如「電商網站 AWS 架構圖（2）」）。[RA:Q5]

### FR6 — 草稿狀態

- **FR6.1** 架構圖新增狀態：**草稿**或**正式**。經大腦新建的圖建立時為草稿。[RA:Q7]
- **FR6.2** 只有兩種情況使草稿轉為正式：大腦產圖並存檔成功，或使用者在工作區按「儲存架構圖」**手動**存檔。工作區的自動存檔（`frontend/src/pages/WorkspacePage.tsx:269-286`）與評核前的寫回（`:500`）**不改變狀態**，因此打開草稿不會使它轉為正式，草稿也不會因評核前寫回而繞過 FR6.4a。存檔 API 須能區分「轉正式」與「只寫內容」，形狀由 contract-design 定案（OQ7）。[RA:Q9][RA:Q12]
- **FR6.3** 產圖失敗時保留為草稿，工作項標失敗並說明原因；使用者再說一次（作業對象仍是那張草稿），大腦接著畫**同一張**草稿，不另建新圖。[RA:Q7][RA:Q10]
- **FR6.3a** 作業對象是系統、而該系統下有**未完成的草稿**時說要畫圖，反問「要接著畫哪一張草稿，或新建一張」，以可點選候選列出草稿與「新建」。[RA:Q10] 本條**優先於** FR2.2 判定表第二列：即使 p ≥ t，也先反問，避免在使用者不知道有草稿時又多一張。只有草稿、沒有正式圖的系統視為「有圖」，適用本條。〔推導：優先序與「只有草稿」的歸類〕
- **FR6.3b** 可測形式：建圖成功、產圖失敗，使用者再說一次 → 系統下仍只有一張圖，且它在產圖成功後轉為正式。
- **FR6.4** 草稿可被選為作業對象，並在切換對象選單、專案頁「系統的架構圖」與工作區歷史清單標示「草稿」（使用者要能找到它才能接著畫）。[RA:Q7][RA:Q9]
- **FR6.4a** 下列「拿圖來用或對外呈現」的地方一律**排除**草稿：[RA:Q11]
  - 專案頁的架構圖計數不計草稿；
  - 評核（WA，`review_router`／`review_orchestrator`）與 WA 共編（`wa_collab_orchestrator`）不得以草稿為對象：作業對象是草稿時交辦評核，回覆「這張圖還是草稿，請先完成產圖」且不執行；
  - 估價綁定架構圖（`cost/estimate_intake_router.py:89` 的 `diagram_id`）時不得綁草稿，處置同上；
  - 分享（`collab_router` 的 `diagram_shares`）不得分享草稿。
  - 可測形式：對每個上述入口各一案，以草稿為對象 → 被拒並顯示上述訊息，資料不變。
- **FR6.4b** 下列「判斷系統或專案底下有沒有圖」的地方**必須包含**草稿，不受 FR6.4a 影響〔推導：排除會造成錯誤〕：
  - 刪除系統的檢查（`backend/services/hierarchy_service.py:212` 起，系統下仍有圖即拒絕；資料表也以 ON DELETE RESTRICT 擋，排除草稿會讓刪除撞上資料庫限制）；
  - 清除空的預設專案的判斷（`backend/services/user_router.py:438` 起，專案下有圖就不清除；排除草稿會刪掉仍有草稿的專案）；
  - 反問候選：FR3.2 的「要改哪一張」與 FR6.3a 的「接著畫哪一張草稿」都列出草稿並標示。
  - 可測形式：系統下只有一張草稿 → 刪除該系統被拒；預設專案下只有草稿 → 不被清除。
- **FR6.4c** 既有「列出系統下的圖」（`list_diagrams_of_system`）同時供 FR6.4a 與 FR6.4b 使用，呼叫端必須明示要不要包含草稿，不得依預設值；做法由 domain-design 定案（OQ8）。〔推導〕
- **FR6.5** 既有的圖一律視為正式；新增欄位的預設值為正式，舊版程式讀到新欄位時不受影響。[RA:Q9]（corner：遷移與回滾）

### FR7 — 紀錄

- **FR7.1** 經大腦新建的圖在專案頁「最近變更」記一筆「經大腦建立」，沿用既有的 `diagram_change_records`。[RA:Q8] 該表的 `source` 只允許 `brain_orchestration`（`schema_rbac.sql:425`）、摘要不得空白，故「經大腦建立」以摘要文字表示，不新增 source 值〔推導〕；產圖成功後既有程式會再記一筆存檔變更，同一張圖因此有「建立」與「產圖」兩筆，屬預期行為〔推導〕。摘要的確切文字由 contract-design 定案（OQ9）。

## Non-Functional Requirements

- **NFR1 判定準確率**：新增「新建或修改」判定後，沿用 `260920-orchestration-brain` 的 60 句標註集重測意圖識別準確率；另〔推導〕新增至少 10 句「新建／修改／應反問」的標註，報告準確率、反問率與交辦錯筆數。門檻沿用 80%，未達標時依該 intent 的校正程序由決策者裁決，不得自動改寫門檻。
- **NFR2 延遲**：「是否要新的一張」併入既有的同一次路由請求（FR2.2），不增加模型往返；新建步驟只多一次同行程的建圖呼叫，發生在首則內容之後。首字回應仍須符合既有 NFR3（P50 ≤ 2 秒，伺服器端），build-and-test 量測確認。
- **NFR3 冪等**：同一工作項不得建立第二張圖（FR1.4）；以後端單元測試覆蓋「重試」「復原掃描」「再說一次接著畫」三種情況。
- **NFR4 可觀測**：路由觀測事件加上判定結果（新建／修改／反問）的類別，不含使用者原文與圖名；健康檢查與日誌查詢沿用既有機制。
- **NFR5 測試底線**（`team.md` A／B／C）：改動的 HTTP 回應（架構圖帶狀態）須有 TestClient 測試；前端清單的草稿標示須有 Playwright 斷言；新建權限須有 allow／deny 雙向測試（有架構編輯權 → 建立成功；只有 K1 → 不建立並回說明）。

## ADR-0006 Security Baseline 四面向

| 面向 | 判定 | 說明 |
|---|---|---|
| IAM | 適用 | 新建沿用建圖端點的架構編輯權檢查（`collab_router.py:556`），以使用者自己的 token 呼叫（FR4.3）；可點選候選帶的識別碼在伺服器端重新驗證存在與權限（FR3.5），不信任客戶端；候選只列使用者擁有的系統與自己的圖（FR3.1、FR3.2） |
| Encryption | 不適用 | 不新增任何儲存或傳輸機密的路徑；新增的狀態欄位與候選識別碼不是敏感資料，沿用既有 HTTPS／WSS |
| Network exposure | 適用 | 不新增對外端點；擴充的是既有 `/api/brain/ws` 的反問候選形狀與既有架構圖 API 的回應欄位，須通過 WebSocket 契約與 OpenAPI 的漂移檢查 |
| Audit logging | 適用 | 經大腦新建記入 `diagram_change_records`（FR7.1）；日誌不得含使用者原文與圖名（圖名由使用者句子取出，屬使用者內容，沿用路由日誌白名單的禁止欄位） |

## Constraints

- 不建立新 agent，不採 A2A；重用既有架構設計 agent 與既有端點。[IC 前置查證]
- **WebSocket 契約變更**（FR3.4）：反問候選形狀擴充，須同步後端契約、前端型別與 `dump_ws_contract` 漂移檢查。
- **資料表變更**（FR6）：`user_diagrams` 新增狀態欄位，觸發 `project.md` 的 blocking 同步：`schema_rbac.sql`（只在**空** volume 執行）與 `DEPLOY.md` 必須在同一變更內更新；**既有非空 volume 的唯一演進路徑是 `hierarchy_migration.py` 的 `_ensure_hierarchy_schema()`**（`schema_rbac.sql:345-347`），加欄位必須在那裡以預設值「正式」補上，`DEPLOY.md` 寫明升級方式。可測形式：已部署的資料庫升級後，所有既有圖的狀態皆為正式。若另動 `backend/database.py` 的啟動補丁，須同步更新 `LOCAL-DEV.md`。
- **API 回應變更**：架構圖回應帶狀態，須重新產生 `openapi.json` 與前端型別。
- 路由判定屬 property-based testing 的 hard constraint（FR2.3）。
- 每個 intent 必經 `tcms-test-cases`（`project.md` `## Mandated`）。
- 計畫調整：本站作答使範圍超出原 8 站計畫的預期（WebSocket 契約、資料表），使用者於本站決定加回 domain-design、units-generation、contract-design 三站。

## Assumptions

- **A1**：「授權申請」頁只處理新註冊者的角色申請，已核准帳號沒有線上升級流程（`user_router.py:833`），故 FR4.1 的申請對象是平台管理者。
- **A2**：一個請求一次只新建一張圖；一句話要求多張圖不在本次判定範圍內，會依既有多意圖規則處理或反問。
- **A3**：草稿不設保存期限，也不自動清除；使用者可用既有的刪除功能刪除。

## Out of Scope

- 不新增讓已核准帳號線上申請升級角色的流程。[RA:Q1]
- 不自動建立專案或系統。[IC:Q11]
- 不採 A2A，不把架構設計 agent 拆成獨立服務。

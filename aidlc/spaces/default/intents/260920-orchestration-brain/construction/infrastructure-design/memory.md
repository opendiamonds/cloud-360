- 2026-09-27T04:53:27Z — **`[I2b]`=A 被使用者裁決推翻，因為它與另兩個定案合起來製造了死結**。`[I2]`=C（六個全設）＋ `[I2b]`=A（沒量過不得設）＋ 值硬寫在 compose，使 `code-generation` **不存在任何合規輸出**——被禁止猜、又必須產出十個數字，而量測的執行者、時點、通過判準三者皆無。我寫的「不得靜默填一個猜測值」是**禁令而非路徑**。改為「先以公開基準設值、`DEPLOY.md` 標記暫定並限期複量」。**教訓的可執行形式**：寫下任何「不得 X」的約束時，同時寫出「那要做什麼」——只有禁令沒有路徑的規則，會在下游變成一個必然被違反或必然停擺的選擇。
- 2026-09-27T04:53:27Z — **同一條「最糟時點是升版窗口」的推導，我只對磁碟做了、沒對記憶體做**（審查 R-07）。`db` 的容器記憶體上限在升版窗口內同樣生效，而 dump/restore 是它記憶體用量最異常的一段（大批 `COPY`、索引重建、`maintenance_work_mem`）；以正常穩態峰值得到的上限正是**最可能在還原中途被突破**的那一個，而突破的後果是 OOM kill ＋ 重啟迴圈，發生在回退**依賴 dump 完整性**的那個窗口裡。**可執行檢查**：任何「這個資源的上限」決定，都要對照 `NFR6.3` 的升版窗口問一次「這一段期間的用量是正常的嗎」。

- 2026-09-27T12:11:58Z — **redo jump 的代價比上一筆量到的「三個使用者回合」更高，因為 `STAGE_JUMPED` 是所有 stage 共用的 attempt floor。** `aidlc-lib.ts:25036` 對 `STAGE_JUMPED` **無條件**回 true，所以在 construction block 內任何一站做 redo，會把該單元**每一站**的 `UNIT_COMPLETED` 與審查收據一起壓到新 floor 之下。上一次量到三個回合是因為當時下游尚未完成；本次 `nfr-requirements` 與 `nfr-design` 都已完成並 commit（`126af50`／`918264b`），所以同一個動作的代價變成兩整站的重取確認與重跑審查。使用者裁決改走「不記收據的審查 ＋ 暫時降 review class 完成本站」，換掉的是引擎層的審查收據，換到的是不動兩站的已完成狀態。

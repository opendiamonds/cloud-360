# 擴展需求 — `U12 work-orchestrator`

## 〇、本單元的擴展面

本單元沒有自己的儲存（工作項住在 `U10` 的工作階段 key 內）、沒有新進程。真實的擴展面只有兩個：**多 worker
同時處理同一個工作階段**時的正確性，以及**單一行程內背景執行的數量**。

## 一、多 worker 正確性

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR12.12`** | 工作項的每次更新皆為比對 `status` 與 `dispatchStage` 的原子寫入（`BR52.7`），正確性不依賴「哪個行程在跑它」 | 模型式 PBT（`hypothesis` 的 stateful 測試）：在記憶體替身上隨機交錯「背景推進 `dispatchStage`」「`correct`」「復原掃描」三串操作，性質為 (a) 請求已送出（`dispatchStage` ≠ `not_dispatched`）時停掉後 `sideEffect` 不為 none（成本項除外）；(b) 終態不被改寫；(c) `estimateSetId` 一旦寫入不被清為 null |
| **`NFR12.13`** | 復原掃描推進同一個項目時，**只有比對後寫入成功者**啟動背景執行與送訊息（帶入項 2） | 兩個併發的復原掃描面對同一個孤兒等待項：能力替身被呼叫恰 1 次、失敗或建立訊息恰送 1 次 |

## 二、單一行程內的數量

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR12.14`** | 背景執行的數量等於該行程內處理中的工作項數，不另設 executor、不排隊；每條都有牆鐘上限（`BR56.6`），故不會無限累積 | 進入處理中的每一項 `deadlineAt` 非 null（`entities.md` 的實體約束）；PBT 的 `transition` 性質涵蓋 |
| **`NFR12.15`** | 一次交辦的工作項數等於路由結果的意圖數（`BR52.1`），本單元不額外放大 | 3 個意圖 → 恰 3 個工作項 |

## 三、刻意不設的目標

| 不設 | 理由 |
|---|---|
| 每工作階段工作項數上限 | 工作項隨工作階段 24 小時到期（`BR52.4`）；每次交辦只增加意圖數個欄位，無上游數據顯示需要上限 |
| 背景執行的併發上限 | 每項有牆鐘上限且數量由使用者說話的頻率決定；加上限會讓工作項排隊，與「先回覆、後執行」的體感無關卻增加狀態 |

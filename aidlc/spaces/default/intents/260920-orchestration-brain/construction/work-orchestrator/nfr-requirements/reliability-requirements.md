# 可靠性需求 — `U12 work-orchestrator`

## 〇、本單元的可靠性面

本單元的可用性等於既有後端（embedded）。會壞的地方在**背景執行的生命週期**：重啟後 task 消失、停掉與背景推進
交錯、在途的存檔被取消、送訊息失敗。上游 `NFR4`（狀態外部化與重啟還原）在本單元的承接見第一節。

## 一、狀態外部化與重啟復原（承接 `NFR4`）

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR12.16`** | 工作項只存在 Redis（`BR52.4`），行程記憶體只持有 task 參考 | 交辦後丟棄 `WorkOrchestrator` 實例、以新實例 `list_items`：取回的集合與丟棄前相同 |
| **`NFR12.17`** | 復原掃描（`BR56.7`）：處理中且已過 `deadlineAt` 者轉失敗；等待中而被等待者已是終態者補做推進 | 兩案：把 `deadlineAt` 設在過去 → `list_items` 後為失敗；寫入「被等待者完成、等待者仍等待中」→ `list_items` 後等待者為處理中且能力替身被呼叫 1 次 |
| **`NFR12.18`** | `put_work_item`／`update_work_item` 在 key 不存在時拒絕，不重建沒有到期時間的 key（`BR52.4`） | 刪除工作階段 key 後呼叫 `put_work_item`：回 False，且該 key 仍不存在（`EXISTS` 為 0） |

## 二、生命週期與交錯

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR12.19`** | 每個處理中的工作項有牆鐘上限，逾時轉失敗（`BR56.6`） | 能力替身永不返回、假時鐘推進 300 秒 → 失敗「架構設計逾時」 |
| **`NFR12.20`** | 停掉時在途的存檔請求，其結果不因 task 被取消而遺失：PUT 成功則寫變更紀錄並更新 `sideEffect`（`BR55.7`；帶入項 1） | 替身讓 PUT 延遲、期間呼叫 `correct`：PUT 完成後變更紀錄恰 1 列、`sideEffect` 為「已存回架構圖〈名稱〉」、status 為已停掉 |
| **`NFR12.21`** | 先以比對後寫入記下 `request_sent` 成功，才送出請求（帶入項 3） | 讓該次寫入回 False：能力替身被呼叫 0 次 |
| **`NFR12.22`** | sink 送出失敗不改變工作項、不讓背景執行拋出未處理例外（`BR56.8`） | sink 替身一律拋例外：工作項照常走到完成，事件迴圈無未處理例外 |
| **`NFR12.23`** | 不自動重試任何對既有能力的呼叫（`BR56.4`）；輪詢連續 3 次失敗才判斷線（`BR57.2`） | 能力替身回 500：被呼叫恰 1 次；輪詢替身失敗 2 次後成功 → 不失敗 |

## 四、刻意不設的目標

| 不設 | 理由 |
|---|---|
| 可用性 SLO | 本單元沒有獨立的可用性，等於既有後端；repo 尚無可用性量測 |
| 重啟後自動續跑中斷的能力呼叫 | 已送出的請求結果未知（`sideEffect` 為 unknown）；自動續跑可能重複建立 A3 檢視或覆寫圖，故以失敗＋請使用者再說一次處理（`BR56.7`） |

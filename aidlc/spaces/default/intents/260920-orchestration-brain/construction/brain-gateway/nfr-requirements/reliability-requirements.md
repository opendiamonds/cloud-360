# 可靠性需求 — `U13 brain-gateway`

## 〇、本單元的可靠性面

本單元的可用性等於既有後端（embedded）。會壞的地方在**連線與輪次的生命週期**：Redis 或嵌入提供者暫時不可用、載入期間
的扇出與 ready 交錯、送出失敗、行程重啟，以及**對象解析在名稱有歧義時靜默改掉作業對象**（帶入項 1、2 指出的正確性缺陷）。
上游 `NFR4`（狀態外部化與重啟還原，`requirements.md:500-508`）在本單元的承接見 `NFR13.31`。

## 二、載入期與 ready 的收斂

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR13.26`** | ready 之前的狀態收斂（帶入項 3）：送出暫存佇列時，**「確認佇列已空」與「phase 改為 ready」之間不得有任何 `await`**；送出期間新到的扇出因 phase 仍為 loading 而附加到佇列尾端、由同一迴圈送出——不得漏送、不得重送、不得插到快照之前 | 送出替身每次送出都 `await asyncio.sleep(0)` 讓出；注入器在送出第一則暫存訊息時觸發一次新的 `emit_session`（帶可辨識的工作項集合）。斷言：該連線收到的訊息序列為 `ready` → 快照 → 原暫存佇列 → 新訊息，新訊息恰出現 1 次且為最後一則 `work_items`；結束時 phase 為 ready。突變驗證：在「確認已空」與「改 ready」之間插入 `await asyncio.sleep(0)` 並在該處注入 → 新訊息遺失、測試紅燈 |

## 三、帶入項的正確性要求（對象解析）

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR13.27`** | （帶入項 1）原句名稱掃描（`BR64.13`）改為**最長完整名稱**比對：在 casefold 後的原句中找出所有目錄名稱的出現區間，**被較長命中區間完全覆蓋的較短命中不計**（中文沒有詞邊界，「完整名稱」以區間覆蓋定義）；掃描命中後**一律以對象反問確認**（`clarify{kind:"target"}`，沿用 `BR64.11` (a) 的候選形狀，含單一命中時），**不得**直接 `set_work_target`。**高信心路徑（`BR64.9`）維持唯一相符即更新、不反問**——理由：高信心路徑的 referent 是 `U11` 與意圖一併判讀出的語意指涉，掃描是對原句的字面啟發式；兩者證據強度不同，處置不同。此為本站選定、提請核可 | ① 目錄含專案「訂單」與其系統「訂單系統」，原句「改訂單系統的圖」：掃描結果只含「訂單系統」。② 目錄含兩字的通用名稱（如「系統」），反問選定意圖後原句含該詞且無其他命中：收到 `clarify{kind:"target"}`、`set_work_target` 替身 0 次、`dispatch` 0 次；選定候選後才各 1 次。③ 高信心、referent 唯一相符：`set_work_target` 1 次、未送 `clarify` |
| **`NFR13.28`** | （帶入項 2）`BR64.9` 與 `BR64.13` 對「專案與其**自己的**系統同名」給出**同一結論**：系統命中**吸收其所屬專案的命中**（不論專案名是否與系統同名，與 `BR64.13`「同一專案下系統命中時專案名的命中不另計」同義），故專案與其自己的系統同名時視為**一個對象（該系統）**，`BR64.9` 第 2 步不再計為兩筆；不同專案的同名對象仍為多筆。名稱正規化統一為 `casefold()` 後 `strip()`（只去頭尾空白，不動內部空白）。PBT 性質五改寫為可失敗的版本：**對任意原句 u 與目錄，(a) 結果中每個對象的名稱 n 滿足 casefold(n) 是 casefold(u) 的子字串；(b) 目錄中長度 ≥ 2 的名稱 n 若在 u 中至少有一個出現區間不被更長命中完全覆蓋、且 n 不是某個已命中系統的所屬專案名，則 n 的對象在結果內；(c) 結果中任兩個對象的名稱區間互不完全覆蓋** | ① `hypothesis` 以 (a)(b)(c) 三條性質驗證 `scan_targets_in_utterance`。突變驗證：把最長比對改回單純子字串 → (c) 紅燈；拿掉所屬專案吸收 → (b) 的反例（同名專案與系統）紅燈。② example：專案「訂單」含系統「訂單」，referent「訂單」→ `BR64.9` 走唯一相符（`set_work_target` 帶 `system_id`），原句「改訂單」→ `BR64.13` 結果恰一個對象（該系統）。③ referent 為「 訂單 」（頭尾空白）與「訂單」結果相同；「訂 單」與「訂單」**不同** |

## 四、輪次與送出

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR13.29`** | 每輪至多一個終止事件；終態之後不放行任何輪次訊息；`done` 若且唯若之前有內容；`clarify` 不使結束為 `done`（`TurnLedger`，`BR64.7`；PBT 性質三） | `hypothesis` 對 `TurnLedger` 的任意操作序列驗證四條不變量（`functional-spec.md:264-265`）；另以 example 驗證：`dispatch` 回傳但 `emit_in_turn` 從未被呼叫 → 收到 `error(EMPTY_RESPONSE)` 而非 `done` |
| **`NFR13.30`** | 一條連線送出失敗不影響其他連線與背景工作：失敗即移出登錄、記 DEBUG、不向上拋（`BR63.4`） | 同一 session key 三條連線，其中一條的送出替身拋 `WebSocketDisconnect`：`emit_session` 後其餘兩條各收到 1 則 `work_items`；呼叫 `emit_session` 的協程未收到例外；登錄剩 2 條 |

## 五、狀態外部化、重啟與部署假設

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR13.31`** | （承接 `NFR4`）本單元**不在行程記憶體保存任何會話狀態**：作業對象、共享模式、歷程、工作項一律讀寫 `U10`／`U12` 的 Redis；行程內只有連線綁定的暫態（登錄、`PendingClarify`、`TurnLedger`、暫存佇列），連線斷即失效。重啟後重連即由 `load` ＋ `list_items` 取回完整快照（`BR62.4`、`BR63.2`）。**揭露**：等待中的反問（`PendingClarify`）在重啟後消失，使用者需重說一次——它本來就隨連線生命週期，重啟必斷線 | 建一條連線、設定作業對象與共享模式、交辦一項；丟棄 `app.state.brain_gateway` 並以同一個 Redis 替身重建（模擬重啟），新連線收到的 `sharing_mode`、`work_target`、`work_items` 與重建前最後一次扇出的值逐欄相同 |

## 三、問題

## F1. 交棒橫幅掛在哪一層？

`[US:D-11]` 要求它**在落地時即存在於 DOM**，而 `[US:D-17]` 要求它出現在使用者
**自己的落地頁**（不限入口頁）。兩者合起來決定了掛載層，而掛錯會讓 `AC12.4.3`
在某些角色組合下靜默失效。

- **A. 掛在既有 `Layout` 元件裡（包住每一頁）**：任何落地頁都在初始 DOM 就帶著它。
  一處實作涵蓋全部落地頁，`AC12.4.3` 的 Then 對任何角色組合都成立。代價是每一頁
  都會掛載該元件（即使沒有待通知事件也要判斷一次）。
- **B. 每個可能的落地頁各自掛一次**：精確控制出現位置。代價是「可能的落地頁」
  集合會隨 story id 與 `DefaultRedirect` 變動，漏一頁就是一個靜默失效的角色組合
  ——這正是 `[D-17]` 已經抓到過一次的失敗形狀。
- **C. 掛在 `DefaultRedirect` 解析出的目標頁**：與「落地頁」的語意最貼近。代價是
  使用者直接輸入網址（不經 `DefaultRedirect`）時不會看到。
- **D. 新建一個 `<BannerHost>` 掛在 router 之上、`Layout` 之外**：與 `Layout` 的
  職責解耦。代價是多一層元件，且 `Layout` 之外沒有既有的版面約束可沿用。

## F2. 橫幅狀態怎麼取得與清除？

`AC12.4.4` 要求換一台裝置重新登入後橫幅不再出現，所以已讀狀態必須**伺服器持久化**
（不能放 `localStorage`）。取得方式則未定。

- **A. 掛載時打一次 REST，按「知道了」後再打一次寫入**：沿用 `AdminPage.tsx` 的
  兩層抓取形狀（純抓取函式 ＋ 呼叫端在 `.then/.catch/.finally` 更新 state ＋
  `useEffect` 內 `cancelled` flag），零新機制。代價是每次落地多一次請求。
- **B. 走既有 WebSocket（`U2 brain-ws-contract`）推播**：不增加 REST 往返。代價是
  WebSocket 連線建立**晚於**首次渲染，所以橫幅不會「在落地時即存在於 DOM」——
  與 `[US:D-11]` 直接衝突。
- **C. 輪詢**：實作最簡單。代價是改選是罕見事件，輪詢的請求幾乎全是空的；且仍不
  保證首次渲染時就在 DOM 裡。
- **D. 隨登入回應／使用者 profile 一起帶回來**：首次渲染時必定已在手上，完全滿足
  `[US:D-11]`。代價是把 per-project 的改選事件塞進認證回應，擴大了一個既有契約的
  責任範圍（`openapi.json` 的既有 operation 要改）。

## F3. 可朗讀的載入／錯誤提示元件由誰擁有？

`U23`／`U24` 共同的硬約束逐字為：載入態與錯誤態須有 live region，**不得**沿用
`AdminPage.tsx:104` 的 4 秒 toast 形狀（它沒有 `role`／`aria-live`）。兩個單元都
需要它，而 `team.md` 的「單一真實來源」規定：同一份事實不得物化第二份；無法避免時
同一個 PR 必須附鎖住一致性的測試。

- **A. `U23 project-pages-ui` 建共用元件，`U24` 沿用**：`U23` 在依賴序上較早
  （`delivery-planning` 的交錯順序裡 `U23` 先落地），所以「先建的那個擁有它」不需
  任何等待。代價是 `U24` 的完成條件多一條跨單元依賴。
- **B. `U24` 建，`U23` 沿用**：代價是 `U23` 要等 `U24`，而這會新增一條依賴圖上
  不存在的邊——`project.md` 逐字禁止「因為 A 讓 B 更有用就列依賴邊」。
- **C. 兩個單元各自行內實作**：零跨單元依賴。代價是同一份無障礙行為物化兩份，
  直接違反單一真實來源，且兩份會各自漂移。
- **D. 擴充既有 `AdminPage.tsx` 的 toast 為共用元件並補上 `role`／`aria-live`**，
  三處（Admin、`U23`、`U24`）共用。代價是動到既有頁面，而 `AdminPage.tsx` 目前
  **沒有** e2e 以外的測試保護；但它同時消除了既有的那個無障礙缺陷。

## F4. 在成員詳情頁改完角色之後，成員清單怎麼更新？

`AC12.2.1` 的 Then 是「**成員清單**顯示其新角色」，所以清單必須反映變更。
`project.md` 的 `application-design:c15` 記過同形缺陷：沿用既有的整份重抓會讓
每次操作閃一次整頁載入，**字面通過 AC 但打斷工作流**。

- **A. 就地更新（`setMembers(prev => prev.map(...))`）**：無閃爍。沿用
  `AdminPage.tsx` 既有的就地更新形狀，且符合 `react-hooks/immutability`
  （error 級）。代價是前端持有一份推導狀態，與伺服器的真實值可能短暫不一致。
- **B. 整份重抓**：永遠與伺服器一致。代價即 `application-design:c15` 記載的閃爍，
  且清單可能很長。
- **C. 重抓但保留舊資料直到新資料到達**（stale-while-revalidate）：既一致又不閃。
  代價是需要一個「舊資料 ＋ 載入中」的雙狀態，而本 repo 既有的兩層抓取形狀沒有
  這個先例，等於新增一個形狀。
- **D. 導回清單頁並重抓**：流程最單純（詳情頁是獨立路由，存檔後返回是自然動作）。
  代價是使用者若要連續改兩個人的角色，每次都要重新進入詳情頁。

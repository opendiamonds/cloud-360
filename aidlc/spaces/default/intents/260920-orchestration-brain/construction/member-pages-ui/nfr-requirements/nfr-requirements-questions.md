## 二、問題

## N1. 成員清單的規模上限是多少，超過之後怎麼辦？

**這是本站唯一有真實失敗面的效能題。** 實測 `list_members` **沒有任何分頁參數**，
一次回傳該專案的全部成員；而本單元把它整份渲染成 DOM 列。對照組是既有的
`AdminPage.tsx`——它**有**分頁（`PaginationControl` 在該檔命中 2 次），所以
「清單不分頁」是本單元與既有唯一前端清單先例的**刻意差異**，需要一個數字把它釘住。

- **A. 訂一個上限（例如 200 列）並在超過時顯示「成員過多，請聯絡管理者」**：
  上限成為可被 e2e 斷言的數字，超過時**不渲染**半套清單。代價是超過上限的專案
  完全無法用成員頁管理成員——而本單元是管理成員的唯一入口。
- **B. 不訂上限，全部渲染，並把「清單規模」列為已知風險**：零實作成本，與
  `list_members` 的現況一致。代價是一個 1000 人專案會渲染 1000 列 DOM，
  而沒有任何數字可以斷言「這樣算不算壞」。
- **C. 不訂上限，但加前端虛擬滾動（只渲染可視範圍）**：DOM 列數與專案規模解耦。
  代價是**需要新依賴或自寫虛擬滾動**，與「零新前端依賴」的已定案直接衝突，
  且會讓 `BR22.2`（清單上沒有改角色控件）的 e2e 斷言需要改寫（控件可能不在 DOM 裡）。
- **D. 訂一個上限並在超過時改由伺服器分頁**：最完整。代價是**要改 `U19` 已完成的端點**
  （加 `page`／`limit`），那是一次跨單元的契約擴充，而 `U19` 的 code-generation
  已完成且在游標之前——與 `OPEN-MP24-1` 同一個形狀。

## N2. 橫幅的 REST 請求要不要在同一個工作階段內快取？

`[F1]`=A 把宿主放進 `Layout`，`[F2]`=A 讓它掛載時打一次
`GET /api/membership/reselections/pending`。兩者合起來的後果是：**使用者每換一頁
就多一次請求**。`BR21.3` 已排除缺 `K3 view` 的三個角色，但**有**該權限的人仍是每頁一次。

- **A. 不快取，每次掛載都打**：最簡單，且「按下知道了之後其他分頁也會跟著清掉」
  這件事自然成立（下次換頁就重抓）。代價是換頁密集時的固定請求開銷，
  且該端點對多數使用者永遠回空陣列。
- **B. 同一工作階段內快取（記憶體，非 `localStorage`）**：請求數由「每頁一次」降為
  「每次登入一次」。代價是**在 A 分頁按下「知道了」之後，B 分頁的快取仍是舊的**
  ——使用者會在另一個分頁看到一則已經確認過的橫幅，直到重新載入。
- **C. 快取但在「知道了」成功後主動失效**：解掉 B 的分頁不一致。代價是需要一個
  跨元件的失效機制（context 或自訂事件），而本 repo 的既有兩層抓取形狀沒有這個先例。
- **D. 不快取，但只在「落地頁」掛載時打，換頁不打**：請求數最少且語意貼合
  `AC12.4.3`（「抵達我的落地頁」）。代價是**「落地頁」在前端無法可靠判定**
  ——`[F1]`=A 選 `Layout` 的理由正是不必維護一份落地頁清單；D 等於把那個清單加回來。

## N3. 本單元要不要產生任何可被觀測的前端錯誤訊號？

`observability-requirements` 對 `ui` 單元不適用（`[service]` only），但
`security-requirements` 仍要回答「稽核與記錄」那一面，而 `BR28.1` 只規定
**不得記什麼**，沒規定**要記什麼**。本 intent 目前**無任何 dashboard 或告警通道**
（`U10` 的 `OPEN-N10-4`）。

- **A. 不產生任何訊號**：與「無通道」的現況一致，不製造無人看的資料。
  代價是成員頁的載入失敗率完全不可知——連「這個頁面常壞」都無從得知。
- **B. 只記 console（型別名稱與端點標識，不含使用者文字）**：零基礎設施成本，
  開發者在本機與瀏覽器 devtools 看得到。代價是生產環境沒有人在看 console，
  等於只對開發期有用。
- **C. 送到既有後端的某個記錄端點**：訊號真的可被聚合。代價是**本單元會因此
  新增一個對外請求與一個端點依賴**，而它目前宣稱「無端點、無持久層」
  ——這會推翻一條本單元的結構宣稱，且需要 `U19` 或其他單元提供該端點。
- **D. 不記錯誤，但在畫面上以 live region 明確告知使用者失敗**（`BR27.1` 已要求）：
  把觀測責任交給使用者回報。代價是只有使用者主動說才會知道。

## N4（審查 `R-01` 觸發的追問）. live region 元件由誰建？`[F3]`=A 的排序理由是反的

**`[F3]`=A（「`U23` 建，`U24` 沿用」）的決定本身還可以成立，但它的理由不成立。**
審查以已核可的 `bolt-plan.md` 查出排序事實是**反的**，我逐一複驗：

| 查證 | 結果 |
|---|---|
| 已核可的交錯交付順序（`bolt-plan.md:494`） | `B1 → B10 → B2 → B11 → B3 → **B12** → **B13** → B4 → B5 → …` |
| `U24 member-pages-ui` 的 Bolt（`:480`） | **B12** |
| `U23 project-pages-ui` 的 Bolt（`:479`） | **B13** |
| `U24` 的已核可依賴（`unit-of-work.md:426`） | 只有 `U19` 與 `U3`，**沒有任何一條指向 `U23`** |

所以 **`U24` 比 `U23` 先施工**，而 `tech-stack-decisions.md` 的 `TS-U24-6` 寫的是
「`U23` 在交錯順序中較早落地，故不新增依賴圖上的邊」，`traceability.json` 更把它
升格成「本單元的完成條件含『`U23` 已提供該元件』」——**那條完成條件在 B12 被施工
的那一刻不可能為真**。附帶：`frontend-components.md:176` 明文禁止退回
`AdminPage.tsx:104` 的 4 秒 toast（實測無 `role`／`aria-live`），所以也沒有合法的退路。

- **A. 改由 `U24` 自建 live region 元件，`U23` 之後沿用**：`U24`@B12 自給自足，
  與已核可的依賴圖（只依賴 `U19`／`U3`）一致，不需要改任何已核可的 Bolt 順序。
  代價是把 `[F3]`=A 的方向反過來——本站須明記這是**對齊已核可 Bolt 計畫的更正**、
  不是本站新定案，且 `U23` 屆時的技術選擇會變成「沿用 `U24` 的」。
- **B. 維持 `U23` 建，並把它標成跨 Bolt 的真實阻塞**：忠於 `[F3]`=A 的字面。
  代價是 `U24`@B12 在施工時沒有可用元件，必須有人裁決**改 Bolt 順序**
  （把 `U23` 提前到 `U24` 之前）——那是改一份已核可、且被五份產出與
  `contract-design` 引用的交付計畫。
- **C. `U24` 自建一個只給自己用的簡版，`U23` 另建共用版**：兩站都不必等。
  代價是同一個無障礙播報機制有兩份實作，直接牴觸 `team.md` 的「單一真實來源」
  （該規則要求新增副本的同一個 PR 必須有鎖住兩者一致的測試，而本 repo 前端
  沒有 unit 測試框架可寫那種測試）。
- **D. 本站不決定，把它原樣記成 open item 交給 `code-generation`**：零成本於現在。
  代價是 `code-generation` 是**實作站**，它撞上這件事的時候已經在寫碼，
  而該站的 Plan Approval 關卡會因為一個無法滿足的完成條件而卡住；
  本站是擁有技術選擇的站，把它往下推等於讓下游在最貴的時點做同一個決定。

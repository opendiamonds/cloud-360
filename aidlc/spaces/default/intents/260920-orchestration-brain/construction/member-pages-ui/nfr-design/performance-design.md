## 一、每條效能要求的達成手段

| 要求 | 達成手段（設計，非實作） | 為什麼是這個手段 |
|---|---|---|
| `UIP-1` 100 列上限 | **渲染閘**：抓取回來後先判長度，超過則不渲染清單、改渲染提示節點。閘門放在「資料→視圖」的轉換點，不是在列的 `map` 內部 | `list_members` 無分頁參數（實測），故上限只能是前端防護。放在轉換點而非 `map` 內，是為了讓「不渲染半套清單」成為結構保證而非逐列判斷的巧合 |
| `UIP-2` 不快取、每次掛載一次 | **不新增任何快取層**：`Layout` 掛載時由橫幅宿主自己發出一次請求，請求函式不持有模組層狀態 | `[N2]`=A。本站刻意**不**套用 `nfr-design-guide.md` 的 cache-aside——那會讓「在 A 分頁按下知道了之後 B 分頁仍顯示舊橫幅」成真，而該後果是 `[N2]`=B 被排除的理由 |
| `UIP-3` 三種操作後不整份重抓 | **就地更新**：成功回應的 `MemberView` 直接併入既有陣列（`map`／`filter`），不呼叫清單抓取函式 | `TS-U24-5`＋`[F4]`=A。先例 `AdminPage.tsx:153`／`:179`／`:200`；該先例的 `:201` `setTotal` 遞減與 `:203` 背景重抓**不適用**（無分頁即無 offset 位移可補） |
| `UIP-4` 首次可互動前 1 次請求 | **單一來源推導**：`canManage` 由 `list_members` 回應中自己那一列的 `role` 推得，不另發請求 | `BR22.3`。這同時是 `I-5` 的結構前提：前端沒有第二個授權資料來源可取用 |
| `UIP-5` 變更紀錄 100 列、最新在前 | **同 `UIP-1` 的渲染閘形狀**，加上排序鍵為時間遞減 | 一致性優先於另立機制。**但它目前不可量測**——取得變更紀錄的端點不存在（`OPEN-MP24-7`），故本設計是「端點到位後即適用」的待命設計，不宣稱已可驗 |
| `NFR11.80` 改角色後 0 次頁面切換 | 就地更新的直接後果（見 `UIP-3`），不另設機制 | `[F4]`=A |
| `NFR11.81` 橫幅到達目標專案 1 次切換 | 橫幅的「查看成員」以被點選事件的 `project_id` 組路由，不走「先回清單再選」 | `BR26.2` |

## 二、刻意**不**採用的效能樣式（逐項附理由）

`nfr-design-guide.md` 與 `nfr-design-patterns.md` 列出的樣式，逐一對照本單元：

| 樣式 | 判定 | 理由 |
|---|---|---|
| Cache-aside／write-through／write-behind | **不採用** | `[N2]`=A 已定案不快取；三者皆會製造跨分頁不一致（見 §一） |
| CDN／reverse-proxy 快取 | **不適用** | 本單元不新增任何可被快取的端點；六個消費點全屬 `U19` |
| 連線池 | **不適用** | 瀏覽器端無連線池概念；後端連線池屬 `U19` |
| 分頁／虛擬滾動／lazy loading | **不採用** | 分頁需改 `U19` 已完成的端點（`OPEN-MP24-6`）；虛擬滾動需新依賴或自寫，與 `TS-U24-1`（零新依賴）衝突，且 `[N1]`=C 已被排除 |
| 非同步化／佇列 | **不適用** | 本單元無長時工作；三種操作都是單一 HTTP 往返 |
| 預取（prefetch） | **不採用** | 會違反 `UIP-4`（首次可互動前恰 1 次請求）與 `UIP-2`（恰 1 次橫幅查詢）的可斷言數字 |

> 這張表的用途是讓「為什麼沒有快取設計」成為**可查的判定**，而不是看起來像漏寫。

## 三、`UIP-2` 的請求量上界（承接 `R-06` 的已揭露代價）

`security-requirements.md` §四 的 DoS 列已寫明：`UIP-2` 對一個既有端點新增的負載
與使用者換頁頻率成正比，**本站亦不為它設界**。設計層面可說的是上界的形狀：

- 每次 `Layout` 掛載 1 次 → 上界 = 單一使用者的換頁次數，由人的操作速度決定。
- 缺 `K3 view` 的角色為 **0** 次，機制是**發出前的能力判定**：掛載時先
  `can("K3","view")`，為 false 則不發請求。`frontend-components.md:157` 已逐字
  定案此前置條件（「`ReselectionBannerHost` 以 `can('K3','view')` 作為發出請求的
  前置條件」）。**審查 `R-03`（Major）更正**：初版把這個 0 歸因於 `BR21.3`，
  而 `BR21.3` 是**重試**規則——其語意是「403 永久失敗本工作階段**不再**發請求」，
  要先發一次並收到 403 才知道，故在那個機制下實際計數是 **1**，`UIP-2` 的 e2e 會紅。
  兩條規則並存不衝突：`can()` 擋住「本來就沒權限」的情形（計數 0），
  `BR21.3` 處理「發出後才發現 403」與「有權限但失敗」的殘餘情形。
  實測三個缺 `K3 view` 的角色為 `SRE`／`Ops_Lead`／`Platform_Engineer`
  （`rbac_seed_data.py:343-345`）。
- **不新增節流或去重**：那會引入一層狀態，而該狀態就是 `[N2]`=B 的快取、
  其跨分頁不一致正是被排除的理由。節流與快取在本單元的後果同形。

如實記載：這是一個**已知且未設界**的量，不是已處置的量。

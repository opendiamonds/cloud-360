## 一、`[FD1]` 共同守門的不變量到底是「至少一位管理者」還是「至少一位成員」？

### 為什麼必須問

`K-16` 要求三條路徑共用**同一個上游守門**，但已核可文件對那個守門的**主詞寫了兩種**：

| 來源 | 逐字 | 主詞 |
|---|---|---|
| `K-16` 的 `last_admin_guard.rule` | 「專案不得失去**最後一位管理者**」（錯誤型別名亦為 `LastAdminGuard`） | **管理者** |
| `AC12.3.1`（自我降級） | 「我是某專案**唯一的專案管理者**」 | **管理者** |
| `FR12.5`（`requirements.md:329`） | 「被移除的 `project_owner` 是某專案的**唯一成員**時」 | **成員** |
| `AC12.3.2`（自我移出） | 「我是某專案**唯一的成員**」 | **成員** |
| `AC12.3.3`（停用帳號） | 「一位使用者是某些專案的**唯一成員**」 | **成員** |

**兩者不是同一件事**，而一個守門只能判一個謂詞。具體分歧的情境：
某專案有兩位成員，`X` 是唯一的管理者，`Y` 是一般成員。停用 `X` 時——

- 以「至少一位管理者」判 → **擋下**（`X` 是最後一位管理者）
- 以「至少一位成員」判 → **不擋**（`X` 不是唯一成員，`Y` 還在）

後者會留下一個**沒有任何管理者**的專案：沒人能邀人、沒人能改角色，
而該專案的成員仍看得到它。前者則會讓 `AC12.3.3` 的 409 列出一個
「`X` 並非唯一成員」的專案——與該 AC 的 Given 字面不符。

### 選項

| 選項 | 不變量 | 後果 |
|---|---|---|
| **A（建議）** | **至少一位管理者**（單一謂詞，三條路徑共用） | 專案永遠至少有一位管理者，故也永遠至少有一位成員——**A 在數學上涵蓋成員那一面**，不需第二個謂詞。代價：停用路徑的 409 條件比 `FR12.5` 的字面**更嚴**（會擋下「最後一位管理者」而不只是「唯一成員」），故 `AC12.3.3` 的 Given 措辭需在本站標為對齊修正並指派回補。這是三個選項裡唯一不會產生「無管理者專案」的 |
| **B** | **至少一位成員**（單一謂詞） | 與 `FR12.5`／`AC12.3.2`／`AC12.3.3` 的字面完全相符，409 條件最窄。代價：**違反 `AC12.3.1`**——唯一管理者自我降級時成員數不變，守門不會擋，而該 AC 要求擋下。且會產生無管理者的死專案 |
| **C** | **兩個謂詞都判**（`≥1 管理者` **且** `≥1 成員`，錯誤訊息指出命中哪一個） | 字面上最完整。但因 A 涵蓋 B，第二個謂詞在實際上**永遠不會獨立命中**——那是一段永遠不執行的程式，而 `project.md` 記過「不可達的規則是死碼，卻在文件上長得像已解決」 |
| **D** | **依路徑參數化**（停用→成員；自我降級→管理者；自我移出→成員） | 每條路徑都符合自己 AC 的字面。代價：這**正是 `K-16` 與 `[US:D-06]` 禁止的形狀**——三條路徑各判一次，守門不再是單一上游判定，`functional-design:c34` 記過它會把違規挪位置而非消除 |

[Answer]: A 至少一位管理者
<!-- 作答時間 2026-10-06T22:35:49Z，取自 audit shard 的 QUESTION_ANSWERED 列而非估計 -->

**後果（本站據此設計）**：

1. 守門為**單一謂詞**，位於三條路徑的共同上游，命名維持 `LastAdminGuard`
   （與 `K-16` 的錯誤型別名一致）。
2. **`AC12.3.3` 的 Given 措辭與本定案不一致**，須標為對齊修正並指派回補：
   該 AC 寫「唯一**成員**」，而本定案下 409 的條件是「最後一位**管理者**」。
   **不回改已核可的 `stories.md`**；指派落點見 `functional-spec.md`。
3. **「至少一位成員」不另立謂詞**——它是本不變量的推論而非獨立規則，
   寫成第二個檢查會是永不獨立命中的死碼（`project.md` 記過該形狀）。

## 二、`[FD2]` `remove_member` 對「已不是成員」回成功還是回查不到？

### 為什麼必須問

`K-16` 的 `retry_and_idempotency` **逐字把這件事留給實作**：

> `remove_member` 冪等（已不是成員時視為成功還是 NotFound，**由實作定但須一致**）

契約只要求「一致」，沒說要哪一種。而這個選擇會被 `U24`（成員頁）看見：
它決定按下「移出專案」後在競態下（兩位管理者同時移除同一人）第二個請求
看到的是成功還是錯誤畫面。

### 選項

| 選項 | 行為 | 後果 |
|---|---|---|
| **A（建議）** | **回成功**（冪等，`204`／`None`） | 競態下兩個請求都成功，畫面一致地顯示「已移出」。重試安全，符合 `DELETE` 的 HTTP 語意（`api-design-guide` 的 `DELETE` 為 idempotent）。代價：呼叫端無法分辨「我移出了他」與「他本來就不在」——但對這個操作而言兩者的使用者意圖相同 |
| **B** | **回 `MembershipNotFound`**（→ 404） | 呼叫端能分辨兩種情況。代價：競態下第二位管理者看到錯誤，而他的意圖已經達成；且與 `DELETE` 的冪等語意相左，`U24` 需要額外處理「404 其實是成功」 |

[Answer]: A 回成功（冪等）
<!-- 作答時間 2026-10-06T22:35:49Z，取自 audit shard 的 QUESTION_ANSWERED 列而非估計 -->

**後果**：`remove_member` 對「已非成員」回 `None`／`204`，不 raise。
`U24` 因此不需要處理「404 其實是成功」。契約要求的「須一致」由一條規則固定。

## 三、`[FD3]` 人工角色變更的稽核寫進 `reselection_events`，還是另立一張表？

### 為什麼必須問

這是 `nfr-design` 記下的 `OPEN-ND18-3`，而本站是它第一次**必須**有答案的地方
——`K-16` 的 `auditing.rule` 逐字要求「**角色變更**與自動改選**皆**須留稽核
（誰、何時、對誰、舊角色、新角色）」，而 `AC12.2.2` 的 Then 要求成員詳情頁的
變更紀錄顯示「誰在何時把角色由什麼改為什麼」。

**目前唯一存在的稽核實體是 `reselection_events`**（`U18` 已交付 DDL），
而它的名稱與 `components.md:819` 的描述把它限定在「`project_owner` 帳號被停用時
**自動改選**的事件紀錄」。它的欄位集合（`promoted_user_id`／`previous_owner_user_id`／
`previous_role`／`new_role`／`occurred_at`／`acknowledged_at`）**恰好就是**人工角色
變更需要的那一組。

`U18` 已為此預留：該表的 `previous_role`／`new_role` **刻意沒有 CHECK**，
理由逐字是「`OPEN-ND18-3` 尚未決定本表是否同時承載人工的 `FR12.2` 角色變更，
而封閉列舉會替那個決定先下結論」。

### 選項

| 選項 | 做法 | 後果 |
|---|---|---|
| **A（建議）** | **一般化既有表**：新增一個事件類型欄（如 `cause`，值為 `auto_reselection`／`manual_role_change`），兩種變更寫同一張表 | `AC12.2.2` 的變更紀錄是一次查詢、一個來源，兩種來源天然按時間合併。代價：`U18` 的 DDL 要加一欄並改表 COMMENT（本單元不擁有該表，屬**跨單元回補**，須在本站標為指派）；`acknowledged_at` 對人工變更無意義，需以 COMMENT 說明它只對 `auto_reselection` 有效 |
| **B** | **另立 `role_change_events` 表** | 語意乾淨，兩種事件互不污染，`U18` 的表不需改。代價：成員詳情頁的變更紀錄要 **UNION 兩張表**並自行合併排序；且兩張表的欄位幾乎相同，違反 `team.md` 的「單一真實來源」——新增副本須同一個 PR 補上鎖住一致性的測試 |
| **C** | **本輪只做自動改選的稽核**，人工角色變更的稽核順延 | 範圍最小。代價：**`AC12.2.2` 永遠紅燈**——它的 Given 逐字是「我改了某人的角色」（人工），而本輪不為它留任何紀錄。這等於讓一條已核可的 AC 不可滿足 |

[Answer]: A 一般化既有表，加 cause 欄
<!-- 作答時間 2026-10-06T22:35:49Z，取自 audit shard 的 QUESTION_ANSWERED 列而非估計 -->

**後果**：
1. `reselection_events` 新增 `cause`（`auto_reselection`／`manual_role_change`），
   兩種角色變更寫同一張表；成員詳情頁的變更紀錄是**一次查詢、一個來源**。
2. **跨單元回補指派**：該表由 `U18` 擁有，故加欄與改表 COMMENT 屬 `U18` 的 DDL 變更。
   本站**不改** `U18` 的產出，指派落點見 `functional-spec.md`。
3. `acknowledged_at` 只對 `cause = 'auto_reselection'` 有意義
   （橫幅只為自動改選而發），須以 COMMENT 與一條規則寫明。
4. `OPEN-ND18-3` 由本站**關閉**。

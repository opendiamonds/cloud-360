# 觀測需求 — `U19 membership-service`

> 本單元是 `service`，故五個 NFR 類別**全部適用**（前三個 `spec` 單元只有 security）。
>
> **本站引入新的 parent id `NFR12`，理由先寫在這裡。** 上游 `requirements.md` 的
> `NFR1`–`NFR11` 逐一讀過（`:400`／`:430`／`:482`／`:500`／`:510`／`:520`／`:531`／
> `:537`／`:547`／`:553`／`:563`），**沒有一條是關於 per-project 授權、成員關係或
> 其併發正確性**——它們分別涵蓋意圖識別準確率、上下文保留率、首字回應時間、狀態
> 外部化、WebSocket 契約閘門、記憶 schema 隔離、episodic 保存稽核、部署設定完整性、
> 成本、路由模型可替換性、頁面切換次數。`NFR12` 在該檔的命中數為 **0**（實測）。
>
> 故本單元的 NFR 是**本站新增**而非承接，並**指派回補**（見 `traceability.json`
> 的 `OPEN-N19-1`）。不把它們硬掛到某個不相干的 parent 之下——那會讓追溯表看起來
> 有上游依據而實際沒有。


## 〇、本單元的觀測面有兩個載體，而它們刻意不同

| 載體 | 對象 | 誰讀 | 規則 |
|---|---|---|---|
| **稽核列**（`reselection_events`） | 成功的角色變更（人工 ＋ 自動） | **使用者**（成員詳情頁的變更紀錄，`AC12.2.2`） | `BR5.1`–`BR5.6` |
| **結構化 log** | 被拒的授權、鎖等待、自動改選的執行 | 維運者 | 本檔 |

**把兩者混在一起是本單元最容易犯的錯**：`BR5.2` 禁止稽核只寫 `logger.info`
（UI 讀不到），而拒絕事件**不是**稽核列——`reselection_events` 的 `cause` 只有
`auto_reselection` 與 `manual_role_change`，沒有「被拒」。`[N2]`=A 正是這條界線。

## 一、拒絕事件（`[N2]`=A）

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR12.6`** | per-project 授權被拒時寫一筆 **WARN 級結構化 log**，欄位含 `story_id`／`action`／`projectId`／`principal` | 四個欄位齊備 |
| **`NFR12.7`** | 拒絕事件**不寫入** `reselection_events`，**不新增任何表** | 該表 `cause` 仍只有兩個值；本單元 schema diff 為空 |
| **`NFR12.26`** | log 不得包含 token、密碼或任何憑證 | 欄位集合即上述四項，無其他 |

`NFR12.26` 的來源是 `team.md ## Forbidden`「不得把敏感資料寫進任何 log」。
`principal` 寫入的是**身分識別**（user id），不是其憑證。

## 二、鎖等待（`[N1]`=A 引入的新觀測對象）

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR12.27`** | 成員變更取得 `projects` 列鎖的等待若發生，記一筆 **WARN 級** log，含 `projectId` | 該 log 點存在 |

**為什麼它需要自己的一條**：`[N1]`=A 是 repo 的**第一個**列鎖
（`with_for_update` 原本全樹零命中）。鎖等待的失敗模式是**延遲而非錯誤**——
請求會成功，只是慢。沒有這個 log，一個退化的鎖競爭情況不會留下任何痕跡。
形狀與 `U5` 的 `occurredAt` 索引是同一類：失敗模式是效能而非正確性，故不會有測試抓到它。

## 三、自動改選（系統發起，無人按按鈕）

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR12.28`** | 每一次自動改選**執行**時記一筆 **INFO 級** log，含 `projectId`／被選中者／被停用的 owner | 該 log 點存在 |
| **`NFR12.29`** | 自動改選因冪等檢查而**跳過**時也記一筆 INFO log | 該 log 點存在 |

`NFR12.29` 的理由：`BR4.3` 的冪等檢查是一條**靜默的**分支——它什麼都不做。
沒有 log 時，「改選沒跑」與「改選跑了但選錯人」在維運上無法區分。
注意這是 log 而非稽核列：**跳過**不是一次角色變更，寫進 `reselection_events`
會讓 `AC12.2.2` 的變更紀錄出現一筆「什麼都沒改」的列。

## 四、刻意不設的目標（附理由，不留空白）

| 不設 | 理由 |
|---|---|
| 分散式追蹤（trace span） | repo **沒有任何追蹤基礎設施**（無 OpenTelemetry、無 X-Ray）。為單一元件引入它是獨立的工具鏈決策，不由本單元夾帶 |
| metrics／儀表板 | 同上：repo 無 metrics 管線。`team.md` 已記載觀測學科尚未落地，而 `project.md` 的 `## Deployment` 把 observability 列為「Operations 中尚未落地的維運學科」之一 |
| 告警門檻 | 沒有 metrics 就沒有可設門檻的對象。`org.md` 要求告警門檻須設在 SLO 破線之前，而本單元沒有 SLO（見 `reliability-requirements.md` §四） |
| SLI／SLO 定義 | 同上。零新進程、無獨立可用性面 |

**這一節是本檔最重要的部分**：四項全部不設，而理由**不是「不重要」而是「沒有承載機制」**。
把它們寫成需求會產生四條沒有任何東西能驗證的宣告——而 `team.md` 已為
「80% 覆蓋率」記過同形問題（「既無法量測也無法強制，是宣告而非閘門」）。

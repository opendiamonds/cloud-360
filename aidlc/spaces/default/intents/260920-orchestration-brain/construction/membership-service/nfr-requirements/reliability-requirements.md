# 可靠性需求 — `U19 membership-service`

> 本單元是 `service`，故五個 NFR 類別**全部適用**（前三個 `spec` 單元只有 security）。
>
> **本站引入新的 parent id `NFR12`，理由先寫在這裡。** 上游 `requirements.md` 的
> `NFR1`–`NFR11` 逐一讀過（`:400`／`:430`／`:482`／`:500`／`:510`／`:520`／`:531`／
> `:537`／`:547`／`:553`／`:563`），**沒有一條是關於 per-project 授權、成員關係或
> 其併發正確性**——它們分別涵蓋意圖識別準確率、上下文保留率、首字回應時間、狀態
> 外部化、WebSocket 契約閘門、記憶 schema 隔離、episodic 保存稽核、部署設定完整性、
> 成本、路由模型可替換性、頁面切換次數。`NFR12` 在該檔的命中數為 **0**（實測）。
>
> 故本單元的 NFR 是**本站新增**而非承接，並**指派回補**（見 `traceability.json`
> 的 `OPEN-N19-1`）。不把它們硬掛到某個不相干的 parent 之下——那會讓追溯表看起來
> 有上游依據而實際沒有。


## 〇、本單元的可靠性面集中在交易邊界，不在可用性

零新進程、零新監聽埠，故沒有獨立的 SLA／SLO／故障轉移面——它隨既有 backend
一起可用或一起不可用。真實內容是**哪些寫入必須原子**，以及**哪些操作可以安全重試**。

## 一、交易邊界（本檔最重要的一節）

| id | 需求 | 二元判準 | 來源 |
|---|---|---|---|
| **`NFR12.15`** | `inviteMember` 的授權檢查、全域權限前置檢查與寫入在**單一交易**內 | 被拒時 `project_members` 的列數不變 | `K-16` 的 `invite_member.note` 逐字 ＋ `AC12.5.3` ＋ `BR3.2` |
| **`NFR12.16`** | `changeRole` 的角色更新與稽核寫入在**單一交易**內 | 稽核列數與角色變更次數相等 | `BR5.1`／`functional-spec.md` §2.5 |
| **`NFR12.17`** | 自動改選的角色升級與稽核寫入在**單一交易**內 | 同上 | `BR5.1`／`functional-spec.md` §2.7 |
| **`NFR12.18`** | 建立專案與其建立者成員列在**同一交易**內 | 不存在零成員的專案（**對本單元上線後新建的專案**） | `BR3.1` ＋ `components.md:538-539` 逐字 |

**`NFR12.16`／`NFR12.17` 的失敗模式是靜默的**：角色改了而稽核沒寫，
`AC12.2.2` 的變更紀錄就漏一筆，而沒有任何東西會報錯——畫面只是少一列。

**`NFR12.18` 的括號是重要的限定**：它只保證**上線後新建**的專案。
既有專案的零成員狀態是另一個問題，見 §三。

## 二、重試安全性（承 `K-16` 的 `retry_and_idempotency`，本站給二元判準）

| 方法 | 冪等 | id | 二元判準 |
|---|---|---|---|
| `resolveProjectRole` | 是（唯讀） | **`NFR12.19`** | 連續兩次呼叫回傳相同，且 `project_members` 無變化 |
| `listMembers` | 是（唯讀） | 同上 | 同上 |
| `assertCanDeactivate` | 是（唯讀、不取鎖） | 同上 | 同上 ＋ 無鎖語句（`NFR12.3`） |
| `inviteMember` | **否** | **`NFR12.20`** | 對已是成員者呼叫被拒，且**不**建立第二列（`BR3.3`） |
| `removeMember` | 是 | **`NFR12.21`** | 對已非成員者呼叫**回成功**（`[FD2]`=A／`BR3.4`） |
| `changeRole` | 否（每次寫一筆稽核） | **`NFR12.22`** | 重複呼叫同一目標角色會產生第二筆稽核列——**這是正確行為**，不是缺陷：它記錄的是「有人執行了一次變更動作」 |
| 自動改選 | **必須是** | **`NFR12.23`** | 該專案已有其他 `project_admin` 時重跑**不執行、不寫事件**（`BR4.3`） |

**`NFR12.23` 是本節唯一有具體失敗故事的一條**：部分失敗後的重跑若不冪等，
會產生**第二次改選事件**，使橫幅重複出現且稽核多一筆不曾發生的變更。

## 三、既有專案的零成員狀態（審查 `R-02` 的 Critical，本站承接）

`project_members` 是全新表（`K-15` 的 `observable_side_effects` 逐字「不含任何資料寫入」），
而既有專案全部由 `hierarchy_migration.py` 建立且**從未寫過成員列**。
故**每一個既有專案今天都是零成員**。

後果鏈：`resolveProjectRole` 對既有專案的任何使用者（**包括該專案真正的 owner**）
查無列 → 回 `None` → `BR1.6` 要求當成拒絕 → 任何消費端（`U20`／`U13`／`U24`）
上線時，既有專案的擁有者會被判定為非成員而被拒絕存取自己的專案。

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR12.24`** | 必須有一次性回填：為每個既有專案的 `owner_user_id` 寫一列 `role = 'project_admin'` 的 `ProjectMember` | 回填後 `projects` 的列數 ≤ 有至少一位 `project_admin` 的專案數 |
| **`NFR12.25`** | 回填**必須先於**任何消費端上線 | 部署順序文件中載明此依賴 |

**這是本站新增的需求，不是承接的** ——`functional-spec.md` §九 的風險 5／7 只涵蓋
「新建路徑沒有寫入端」，**完全沒有提既有專案的回填**。審查以 Critical 指出它，
本站接受並把它寫成兩條可判定的需求。承載形式（獨立腳本 vs 啟動補丁）**本站不預選**
——`U18` 的 `[P1]`=A 已為同類問題定下「獨立腳本、大聲失敗、不動啟動路徑」的先例，
而本項是否沿用該先例屬 `code-generation` 的決定。記為 `OPEN-N19-4`（`blocking-downstream`）。

## 四、刻意不設的目標

| 不設 | 理由 |
|---|---|
| 可用性 SLA／SLO 百分比 | 零新進程；本單元隨既有 backend 一起可用。`org.md` 要求 SLO 須量化，而對一個沒有獨立可用性面的元件設一個百分比是宣告而非需求 |
| 備份／災難復原 | 兩張表隨既有 PostgreSQL 的備份策略一起處理，本單元不新增備份面 |
| 降級路徑 | 授權判定**不得降級**——`BR1.6` 要求查無列即拒絕。「資料庫不可用時放行」是一個安全漏洞而不是降級 |

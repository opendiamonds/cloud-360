## 一、`[N1]` `BR2.1` 的守門在併發下會被繞過——要用哪一種機制關掉這個競態？

### 這是實地查證出來的，不是假設

| 查證項 | 結果 |
|---|---|
| `create_engine` 有沒有設 `isolation_level`？ | **沒有**（`backend/database.py:37` 逐字 `engine = create_engine(db_url)`）→ PostgreSQL 預設 **READ COMMITTED** |
| repo 有沒有用過列鎖？ | **`with_for_update` 全樹零命中**——零前例 |
| 上游有沒有定過本單元的併發行為？ | **沒有**。`requirements.md` 的併發條款（`FR13.1`／`FR13.2`）是**agent 進度事件**的隔離，與成員關係無關；`K-16` 只為**邀請**定了「單一交易」 |

### 競態的具體軌跡

某專案有兩位管理者 `A` 與 `B`。`A` 把 `B` 降級，`B` 同時把 `A` 降級：

| 時間 | T1（`A` 降 `B`） | T2（`B` 降 `A`） |
|---|---|---|
| 1 | 讀管理者集合 → `{A, B}`，數量 2 | |
| 2 | | 讀管理者集合 → `{A, B}`，數量 2 |
| 3 | 判定：移除 `B` 後剩 1 → **放行** | |
| 4 | | 判定：移除 `A` 後剩 1 → **放行** |
| 5 | 更新 `B` 的 role → commit | |
| 6 | | 更新 `A` 的 role → commit |
| 7 | **該專案管理者數 = 0** | |

**兩個交易改的是不同列**，故 READ COMMITTED 與 REPEATABLE READ 都不會產生寫入衝突
——PostgreSQL 的快照隔離只在**同一列**的寫寫衝突上報錯。
`BR2.1` 的不變量因此在併發下不成立，而它正是 `[FD1]`=A 選來避免「無管理者死專案」的那一條。
同一條軌跡也適用於「兩位管理者同時自我移出」與「兩個停用請求同時命中同一專案的兩位管理者」。

### 選項

| 選項 | 機制 | 代價與風險 |
|---|---|---|
| **A（建議）** | **對父列加鎖**：任何成員關係變更（`invite`／`remove`／`changeRole`／自動改選）在交易開始時先 `SELECT ... FOR UPDATE` 鎖住該 `projects` 列，使同一專案的成員變更**序列化** | 零新依賴、改動最小、語意最窄（只序列化同一專案，不影響其他專案）。代價：**repo 零前例**（`with_for_update` 從未用過），故它需要自己的併發測試；且 `assertCanDeactivate` 是跨專案的唯讀掃描，須明確寫它**不**取鎖（否則一次停用會鎖住該使用者的全部專案） |
| **B** | **`SERIALIZABLE` 隔離 ＋ 序列化失敗重試** | 正確性最強，資料庫會主動偵測這類幻讀。代價：要為這組操作改 session 設定並加重試迴圈；`autocommit=False, autoflush=False` 的既有 `SessionLocal` 是全域共用的，為子集改隔離等級會引入兩種 session 形狀；重試迴圈本身需要測試 |
| **C** | **資料庫層的 deferred constraint trigger**：在 commit 時計算每個專案的管理者數，為 0 即中止 | 與應用程式碼無關，任何路徑都擋得住（連直接 `UPDATE` 也擋）。**但它會與既有資料正面衝突**：目前每一個既有專案的 `project_members` 都是**零列**（審查 `R-02` 的 Critical），故該 trigger 會讓**任何**碰到既有專案的交易失敗，直到回填完成為止 |
| **D** | **接受並記載這個競態** | 零成本。代價是 `BR2.1` 的不變量在併發下為假，而它是 `[FD1]`=A 的全部理由；`project.md` 記過「不可達的規則是死碼」，而一條在併發下不成立的不變量比死碼更糟——它看起來成立 |

[Answer]: A 對父 projects 列加 FOR UPDATE
<!-- 作答時間 2026-10-06T23:09:55Z，取自 audit shard 的 QUESTION_ANSWERED 列而非估計 -->

**後果（本站據此寫成 NFR）**：

1. **鎖的對象是父 `projects` 列，不是 `project_members` 的任何一列。** 鎖子列擋不住
   這個競態——兩個交易改的本來就是不同子列。鎖父列才能序列化「對同一專案的成員變更」。
2. **`assertCanDeactivate` 明文不取鎖**：它是跨專案的唯讀掃描，取鎖會讓一次停用鎖住
   該使用者的全部專案。它的回傳是**那一刻**的事實，而真正的保護在被鎖保護的寫入路徑上。
3. **repo 零前例**（`with_for_update` 全樹零命中），故它需要自己的併發測試；
   測試不得以 `sleep` 製造交錯（`unit-of-work.md` 對 `U22` 已記過
   「一個 flaky 的併發測試等於沒有測試」），須以 barrier 釘住順序。
4. 不改 `SessionLocal` 的隔離等級，故不引入兩種 session 形狀。

## 二、`[N2]` per-project 授權被拒時要留下什麼痕跡？

### 為什麼問

`U18` 把它記為 `OPEN-P4` 並指派本單元（`U19` 的 `H-8`）：
**拒絕事件目前不留任何痕跡**。一位管理者反覆嘗試邀請缺權限的人、或一個非成員反覆
嘗試讀取某專案，三張表都不留紀錄。

而 `BR5.2` 禁止的是**稽核**只寫 `logger.info`（因為 `AC12.2.2` 要使用者看得到），
**拒絕事件不是稽核列**——`reselection_events` 的 `cause` 只有 `auto_reselection` 與
`manual_role_change` 兩個值，沒有「被拒」這一類。所以這題不是重問 `BR5.2`。

### 選項

| 選項 | 做法 | 代價 |
|---|---|---|
| **A（建議）** | **結構化 log（WARN 級）**，欄位含 `story_id`／`action`／`projectId`／`principal`，**不新增表、不進 UI** | 零 schema 變更、零新表。拒絕是高頻事件（每個非成員的每次嘗試都算一次），寫進資料庫會讓稽核表被拒絕事件淹沒。`team.md` 已記載既有結構化 log 管線。代價：UI 讀不到——但沒有任何 AC 要求使用者看得到拒絕紀錄 |
| **B** | **寫進 `reselection_events`**，新增第三個 `cause` 值（如 `denied`） | 與 `AC12.2.2` 的變更紀錄同一張表、同一查詢。代價：① 拒絕不是「角色變更」，`previousRole`／`newRole` 兩欄對它無意義，會製造第三種欄位語意（`BR5.4` 已經有兩種）；② 高頻寫入會讓成員詳情頁的變更紀錄查詢被無關列拖慢；③ 又一次 `U18` 的跨單元 DDL 回補 |
| **C** | **本輪不做**，`OPEN-P4` 繼續開著 | 零成本。代價：`U18` 已經把它指派給本單元，再往下推就是第二次轉手，而 `project.md` 記過「指派落空比空著更糟」 |

[Answer]: A 結構化 WARN log，不新增表
<!-- 作答時間 2026-10-06T23:09:55Z，取自 audit shard 的 QUESTION_ANSWERED 列而非估計 -->

**後果**：拒絕以 WARN 級結構化 log 記錄，欄位為 `story_id`／`action`／`projectId`／
`principal`；**不新增表、不進 UI、不寫進 `reselection_events`**。
`OPEN-P4` 由本站**關閉**，並寫明它與 `BR5.2` 不衝突的理由：`BR5.2` 約束的是
**稽核列**（`AC12.2.2` 要求使用者可見），而拒絕不是稽核列。
殘留限制如實記載：**拒絕紀錄 UI 讀不到**，而目前沒有任何 AC 要求它可見。

## 三、`[N3]` `assertCanDeactivate` 的查詢形狀——效率優先還是共用守門優先？

### 為什麼問：審查 `R-03` 把這件事變成一個取捨

審查 `R-03`（Major）指出三條路徑的守門在文件上**沒有證明它們共用同一個實作**，
並要求寫出那個共用函式。而 `assertCanDeactivate` 的職責是
「找出該使用者**是最後一位管理者**的**全部**專案」——跨專案，形狀與另兩條不同。

| 選項 | 做法 | 代價 |
|---|---|---|
| **A（建議）** | **單一聚合查詢**（一次 `GROUP BY project_id HAVING count(*) = 1` 找出該使用者獨任管理者的專案），另兩條路徑用**同一個判定函式**處理單一專案 | 一次查詢而非 N 次，停用是管理者動作但不應隨專案數線性變慢。代價：**兩種形狀並存**，故必須在設計文件明寫「不變量只有一個、判定邏輯只有一處（那個 `HAVING` 的語意即單專案判定的集合版）」，否則正中 `R-03` 的指控 |
| **B** | **逐專案呼叫共用函式**（取該使用者的全部專案，對每個呼叫同一個 `assertStillHasAdmin`） | `R-03` 要的「共同上游」在程式層一眼可見，零解釋成本。代價：N 次查詢。一位使用者的專案數目前無上界（`hierarchy_migration.py` 為每位持圖使用者建一個預設專案，但之後可自由建立），故停用一個帳號的延遲隨其專案數線性成長 |
| **C** | **A ＋ 一條鎖住兩者等價的測試**（對隨機成員集合比對聚合查詢與逐專案判定的結果） | 兼得效率與可驗證的等價性。代價：多一條測試，且它需要資料庫（不是純函式，故不是 PBT 的作用對象——與 `selectSuccessor` 不同） |

[Answer]: C 聚合查詢加等價測試
<!-- 作答時間 2026-10-06T23:09:55Z，取自 audit shard 的 QUESTION_ANSWERED 列而非估計 -->

**後果**：
1. `assertCanDeactivate` 用**一次**聚合查詢（`GROUP BY project_id HAVING count(*) = 1`）
   找出該使用者獨任管理者的全部專案；另兩條路徑呼叫**同一個**單專案判定函式。
2. **加一條鎖住兩者等價的測試**：對隨機成員集合比對「聚合查詢的結果」與
   「逐專案呼叫判定函式的結果」是否相同。它需要資料庫，**故不是 PBT 的作用對象**
   ——與 `selectSuccessor` 不同（那一個才是純函式）。
3. 這直接回應審查 `R-03`：等價性由測試而非散文承載。

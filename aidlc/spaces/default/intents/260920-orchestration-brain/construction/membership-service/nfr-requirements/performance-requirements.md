# 效能需求 — `U19 membership-service`

> 本單元是 `service`，故五個 NFR 類別**全部適用**（前三個 `spec` 單元只有 security）。
>
> **本站引入新的 parent id `NFR12`，理由先寫在這裡。** 上游 `requirements.md` 的
> `NFR1`–`NFR11` 逐一讀過（`:400`／`:430`／`:482`／`:500`／`:510`／`:520`／`:531`／
> `:537`／`:547`／`:553`／`:563`），**沒有一條是關於 per-project 授權、成員關係或
> 其併發正確性**——它們分別涵蓋意圖識別準確率、上下文保留率、首字回應時間、狀態
> 外部化、WebSocket 契約閘門、記憶 schema 隔離、episodic 保存稽核、部署設定完整性、
> 成本、路由模型可替換性、頁面切換次數。`NFR12` 在該檔的命中數為 **0**（實測）。
>
> 故本單元的 NFR 是**本站新增**而非承接，並**指派回補**（見 `traceability.json`
> 的 `OPEN-N19-1`）。不把它們硬掛到某個不相干的 parent 之下——那會讓追溯表看起來
> 有上游依據而實際沒有。

## 〇、本單元的效能面只有兩個真實標的

本單元零新進程、零新監聽埠（`embedded`，`unit-of-work.md:307`），
故沒有啟動時間、記憶體佔用或吞吐量這類進程層指標。真實標的是兩條查詢路徑。

## 一、`resolveProjectRole`：最熱的路徑

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR12.8`** | 單次判定為**一次**索引查詢，不得有 N+1 | 該方法的 SQL 執行次數為 1（以查詢計數斷言） |
| **`NFR12.9`** | 本輪**不加快取** | 程式中無 cache／memo 結構 |

**為什麼一次查詢就夠**：查詢形狀是 `WHERE project_id = ? AND user_id = ?`，
而 `U18` 已交付的 `uq_project_members_project_user` 唯一約束提供以 `project_id`
為前導欄的 btree 索引，**完全覆蓋**這個查詢（`U18` 的 `security-design.md §四之一`
已逐項列出已覆蓋的查詢，並刻意不把它們報成缺口）。

**為什麼不加快取（`NFR12.9`）**：per-project 角色是**授權結論**，快取它會引入
「權限已撤銷但快取未失效」的窗口——而撤銷（`removeMember`／`changeRole`）正是本單元
的核心功能。一個索引命中的單列查詢不值得用授權正確性去換。
若日後實測顯示它是瓶頸，正確的下一步是 per-request memo（請求生命週期內有效，
不跨請求），而不是跨請求快取。

## 二、`assertCanDeactivate`：`[N3]`=C 的聚合查詢

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR12.10`** | 以**一次**聚合查詢（`GROUP BY project_id HAVING count(*) = 1`）找出該使用者獨任管理者的全部專案，**不得**逐專案迴圈 | 該方法的 SQL 執行次數為 1，與該使用者的專案數無關 |
| **`NFR12.11`** | 另兩條路徑（`removeMember`／`changeRole`）呼叫**同一個**單專案判定函式 | 兩者的程式中都出現該函式名 |
| **`NFR12.12`** | 一條測試鎖住「聚合查詢的結果」與「逐專案呼叫判定函式的結果」**相同** | 該測試存在且綠燈 |

**`NFR12.10` 與 `NFR12.11` 看似矛盾，實際不矛盾**，而這一點必須寫下來：
不變量只有一個（`BR2.1`），判定邏輯只有一處；聚合查詢的 `HAVING` 語意就是
**單專案判定的集合版**。`NFR12.12` 的等價測試是讓這句話可被驗證而不只是宣稱
——**它直接回應審查 `R-03`**，該發現指出三條路徑在文件上沒有證明共用同一實作。

**為什麼不逐專案迴圈**：一位使用者的專案數目前**無上界**
（`hierarchy_migration.py` 為每位持圖使用者建一個預設專案，之後可自由建立），
故逐專案會讓停用一個帳號的延遲隨其專案數線性成長。

## 三、刻意不設的目標（附理由，不留空白）

| 不設 | 理由 |
|---|---|
| 絕對延遲數字（如 P50 ≤ N ms） | 本 repo **沒有任何延遲量測機制**；設一個無法量測的數字是宣告而非需求。`NFR3`（首字回應時間 P50 ≤ 2 秒）的量測落點是 `build-and-test`，而它量的是**大腦的串流**，不是本單元 |
| 吞吐量目標 | 零新進程；本單元的請求量是既有 FastAPI process 的一部分，沒有獨立的吞吐面 |
| 鎖等待逾時 | `[N1]`=A 的鎖只序列化**同一專案**的成員變更，而同一專案的並行管理動作在本系統的使用情境下是罕見事件。設一個逾時值需要競爭資料，而我們沒有 |

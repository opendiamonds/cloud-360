# 可靠性設計 — `U19 membership-service`

> 本站設計上游 `nfr-requirements` 的 **29 條 `NFR12.x`** 的承載形式。
> 本站**不複寫** `functional-design` 的 29 條 `BR` 規則（`team.md` 的單一真實來源）。
>
> `U19` 是 `service`，故六份設計產出全部適用（`U5`／`U18` 只有 `security-design`）。


## 〇、本檔的實質內容是交易邊界與回填的形狀

零新進程故無獨立可用性面（`reliability-requirements.md §四` 已說明為何不設 SLA）。
本站設計的是：四條交易邊界各自的範圍、鎖與交易的關係、以及 `[ND1]`=A 與回填的形狀。

## 一、四條交易邊界的範圍與鎖的位置（`NFR12.15`–`NFR12.18`）

| 操作 | 鎖 | 交易內含 | 來源 |
|---|---|---|---|
| `inviteMember` | 鎖父 `projects` 列 | 授權檢查 ＋ 全域權限前置檢查 ＋ 寫 `project_members` | `NFR12.15` ＋ `AC12.5.3` |
| `removeMember` | 鎖父 `projects` 列 | 授權 ＋ 守門 ＋ 刪列 | `NFR12.1` ＋ `BR2.1` |
| `changeRole` | 鎖父 `projects` 列 | 授權 ＋ 守門 ＋ 改 role ＋ **寫稽核列** | `NFR12.16` |
| 自動改選（單一專案） | 鎖父 `projects` 列 | 冪等檢查 ＋ 升級 role ＋ **寫稽核列** | `NFR12.17` ＋ `BR4.3` |
| `create_project_with_owner` | **無鎖**（專案尚不存在） | `U7` 建專案 ＋ 寫建立者成員列 | `NFR12.18` ＋ `[ND1]`=A |

**鎖必須在交易**內**取得且在交易結束時釋放**——這是 `FOR UPDATE` 的語意，
寫下來是因為它決定了「鎖的持有時間 = 交易的長度」，故交易內不得有外部呼叫
（LLM、webhook、HTTP）。本單元的五條路徑都沒有外部呼叫，故這個約束自然成立；
**但若日後有人在 `changeRole` 裡加一個通知呼叫，鎖的持有時間就會變成那個呼叫的延遲**。
記為設計約束而非待辦。

## 二、`[ND1]`=A 的交易形狀（`NFR12.18`）

```
U19.create_project_with_owner(principal, name):
  ├─ U7.HierarchyFacade.create_project(principal, name=name)
  │     └─ 注意：U7 的 hierarchy_service.create_project(:98) **自己會 db.commit()**
  └─ 寫 ProjectMember(..., role='project_admin')
```

### 2.1 本站查出一個會讓 `NFR12.18` 落空的實作細節

`U7` 的 `hierarchy_service.create_project`（`:98`）**在函式內自己 `db.commit()`**
（本站已開檔核對：`:117` 的 `db.add(project)` 之後即 `db.commit()`）。
故**天真的 `[ND1]`=A 實作不會是同一交易**：`U7` 先 commit，`U19` 再寫成員列並 commit，
兩者之間若失敗就留下一個零成員專案——**正是 `[ND1]` 要修的那個狀態**。

| 設計要求 | 內容 |
|---|---|
| **交易邊界必須由 `U19` 擁有** | `U19` 的方法開啟交易，而被呼叫的 `U7` 路徑**不得自行 commit** |
| **可行的形狀（本站不預選其中一種，但兩種都要求同交易）** | ① `U7` 的 service 層新增一個不 commit 的變體供組合使用；② `U19` 不經 `U7` 的 service 而在自己的交易內以 `U7` 的 model 建列（但這會繞過 `U7` 的驗證邏輯，**不建議**） |
| **為什麼不預選** | 它需要改 `U7` 已交付的函式簽章或新增變體，屬 `U7` 的介面決定；本站的義務是**指出天真實作會落空**並要求交易邊界歸 `U19` |

記為 `OPEN-ND19-5`（`blocking-downstream`）。**這一項若漏掉，`[ND1]`=A 的修法
會產生它本要消除的那個狀態**，而 `NFR12.18` 的二元判準（「不存在零成員的專案」）
在部分失敗時為假。

## 三、既有專案回填的設計形狀（`NFR12.24`／`NFR12.25`）

| 設計 | 內容 |
|---|---|
| **承載形式** | 沿用 `U18` 的 `[P1]`=A 先例：**獨立腳本**、大聲失敗（非零碼）、不動啟動路徑、`DEPLOY.md` 記步驟 |
| **為什麼沿用而非另立** | `U18` 的 `[P1]`=A 已為「既有環境需要一次性資料動作」定下形狀，而本項是同一類問題的第三次出現（`U4` 的階層遷移、`U5`＋`U18` 的新物件、本項的成員回填）。三支腳本同形比三種形狀便宜 |
| **內容** | 對每個 `projects` 列，若該專案無任何 `project_members` 列，則插入一列 `(project_id, owner_user_id, 'project_admin', now())` |
| **冪等** | 以「無任何成員列」為條件，故重跑安全 |
| **自我終檢** | commit 前斷言「`projects` 中無成員列的專案數為 0」；不為 0 即 rollback ＋ 非零碼 |
| **順序前置條件** | 必須在 `U18` 的 `run_meta_schema_migration.py` 之後（表要先存在），且在任何消費端上線之前（`NFR12.25`） |

**本站仍不預選「是否與 `U18` 的腳本合併成一支」**——合併的好處是部署步驟不再增加，
壞處是把 DDL 與資料動作混在一支腳本裡（`U18` 的腳本目前**純 DDL、無資料寫入**，
而那是它能單一交易並自我終檢的前提）。屬 `code-generation` 的決定，記為 `OPEN-N19-4`（承接）。

## 四、刻意不設計的（附理由）

| 不設計 | 理由 |
|---|---|
| 重試機制 | `NFR12.19`–`NFR12.23` 已定各方法的冪等性；鎖等待由資料庫處理，死鎖由 §一之二 的排序預防。**唯一需要重試的是死鎖後的中止**，而那屬 `code-generation` 的錯誤處理，不是本站的 pattern |
| 降級路徑 | 授權**不得降級**（`reliability-requirements.md §四`）：「資料庫不可用時放行」是漏洞不是降級 |
| 備份／復原 | 兩張表隨既有 PostgreSQL 的備份策略；本單元不新增備份面 |
| 熔斷器／bulkhead | 本單元無外部依賴邊界（零外部呼叫，見 §一） |

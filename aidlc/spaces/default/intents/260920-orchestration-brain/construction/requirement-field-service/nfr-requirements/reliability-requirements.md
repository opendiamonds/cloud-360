# 可靠性需求 — `U20 requirement-field-service`

## 〇、本單元的可靠性面集中在交易邊界與資料表收斂，不在可用性

本單元的可用性等於既有後端的可用性（embedded，零新進程）。真正會壞的地方有兩處：
一次寫入只寫了一半，以及資料表收斂敘述在重跑時改壞資料。

## 一、交易邊界

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR20.19`** | 每次寫入或清空為**單一交易**；任何一步失敗即回滾，該欄維持呼叫前的值與 `filledState`（`BR46.2`） | 案例：讓寫入在 commit 前拋錯（mock），之後重讀該欄 → 值與 `filledState` 與呼叫前相同 |
| **`NFR20.20`** | 授權與驗證失敗發生在任何寫入之前（`BR41.5`），故拒絕不留下任何部分狀態 | 同 `NFR20.7`：拒絕案例中對該表的寫入敘述數為 0 |

## 二、重試安全性（承 `K-17` 的 `retry_and_idempotency`，本站給二元判準）

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR20.21`** | `write_field` 冪等：以相同參數重送，最終狀態相同（值與 `filledState`） | 連送兩次相同 `PUT`，兩次皆 200、列數為 1、值相同 |
| **`NFR20.22`** | `clear_field` 冪等：對已清空或從未填過的欄位清空為 no-op，`cleared_at` 與 `updated_by` 不變（`BR43.3`／`BR43.4`） | 連送兩次 `DELETE`，第二次後 `cleared_at` 與第一次後相同 |

## 三、資料表收斂的重跑安全（`BR47.2`，含 `review-02` R-01／R-02 的帶入項）

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR20.23`** | `updated_on_behalf_of` 的收斂敘述**只在欄位仍為舊型別（integer）時**才轉型並清值；**只在外鍵存在時**才移除（名稱以 `pg_constraint` 查，不寫死自動產生的名稱） | 在已收斂的資料庫上寫入一筆代寫值，再執行一次 `J)` 區塊 → 該值仍在 |
| **`NFR20.24`** | 收斂可由舊定義資料庫驗證，不只由全新資料庫驗證 | 一個測試或 CI 步驟：先以舊定義（integer＋外鍵）建表，執行 `J)` 兩次，斷言型別為 `character varying`、該欄無外鍵、第二次執行不改動任何資料 |
| **`NFR20.25`** | 收斂失敗必須**大聲失敗**，不得被吞掉 | `run_meta_schema_migration.py` 的後條件包含欄位級檢查（型別、無外鍵），不符即非零結束碼 |

**為什麼這三條比上面的更重要**：`review-02` 查出，若收斂寫成無條件的「轉型並清值」，
`run_meta_schema_migration.py` 每次重跑都會把已寫入的代寫溯源清成空，**而且不會有任何
錯誤**——這正是 `U18` 的已知約束「既有環境的演進路徑全部吞掉失敗」會讓它無聲發生的形狀。

**型別轉換在 PostgreSQL 會取 `ACCESS EXCLUSIVE` 鎖並重寫表**：`NFR20.23` 的前置條件同時
避免了它在已收斂的資料庫上每次重跑都發生。首次收斂時表內實際無代寫值（全樹只有
`schema_rbac.sql` 兩處引用此欄），鎖的時間可忽略。

## 四、依賴失敗

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR20.26`** | 資料庫或上游 facade 失敗時回 5xx 而非偽造成功；不得回傳部分組或錯誤的計數 | 案例：讓資料查詢拋錯 → 回應非 2xx，且回應本體不含 `unfilledCount` |

## 五、刻意不設的目標

| 不設 | 理由 |
|---|---|
| 可用性 SLO（如 99.9%） | 本單元沒有獨立的可用性；它等於既有後端，而 repo 尚無可用性量測（`project.md ## Deployment`：observability／SLO 仍是真實待辦） |
| RTO／RPO | 沿用既有 PostgreSQL 的備份與還原，本單元不新增資料儲存 |
| 值的歷史版本與復原 | `ADR-015` 定「只保留最新值」，`domain-design` 已核可 |

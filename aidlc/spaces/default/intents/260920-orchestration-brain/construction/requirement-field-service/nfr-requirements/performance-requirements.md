# 效能需求 — `U20 requirement-field-service`

> **本站引入新的 parent id `NFR20`，理由先寫在這裡。** 上游 `requirements.md` 的
> `NFR1`–`NFR11` 分別涵蓋意圖識別準確率、上下文保留率、首字回應時間、狀態外部化、
> WebSocket 契約閘門、記憶 schema 隔離、episodic 保存稽核、部署設定完整性、成本、
> 路由模型可替換性、頁面切換次數，**沒有一條關於需求欄位的讀寫、授權或資料完整性**。
> 故本單元的 NFR 是**本站新增**而非承接，比照 `U19` 為成員關係另立 parent id 的先例，以單元號
> 命名為 `NFR20`，不硬掛到不相干的 parent 之下。唯一承接上游的是部署設定完整性
> （`NFR8` → `NFR8.120`，見 `security-requirements.md` 第四節）。

## 〇、本單元的效能面只有一個真實標的

本單元零新進程、零新監聽埠（`unit-of-work.md:308`，embedded），故沒有啟動時間、
記憶體或吞吐量這類進程層指標。真實標的是**每次請求發出的查詢數**：它決定延遲是否會
隨欄位數或組數成長，而且是 repo 現有工具（`unittest` ＋ SQLAlchemy 事件計數）能二元
判定的。

## 一、讀取（`read_fields`）

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR20.1`** | 對 `system_requirement_fields` 的資料查詢**恰為一次**，與已宣告欄位數、組數、既有列數皆無關（`BR44.4`） | 以 SQLAlchemy `before_cursor_execute` 事件計數：對該表的 SELECT 次數為 1；在「0 列」與「7 列＋1 列定義外的保留列」兩種資料下皆為 1 |
| **`NFR20.2`** | 授權前段（`BR41.1`–`BR41.4`）的查詢數為**常數**，不隨欄位數成長——不得逐欄檢查權限 | 同一計數器：「0 列」與「7 列」兩種資料下，整個請求的總查詢數相等 |
| **`NFR20.3`** | 不提供「只回計數」的端點，總覽籤與需求籤共用同一次 `GET` | `openapi.json` 中本 router 只有一個 GET 操作 |

## 二、寫入與清空

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR20.4`** | `write_field` 的資料寫入為**單一** upsert 敘述，不得先查後寫（`BR43.5`） | 計數器：對該表的 INSERT／UPDATE 敘述各寫入請求恰為 1，且無對該表的 SELECT |
| **`NFR20.5`** | 寫入與清空的回應**不重算**整個系統的計數（只回單一 `FieldView`）；畫面所需的新計數由 `U23` 重讀 `GET` 取得（`OPEN-RF20-3`） | 寫入請求中對該表的 SELECT 次數為 0（清空允許 1 次讀該列，見 `BR43.3`／`BR43.4`） |

## 三、不加快取

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR20.6`** | 本輪**不加**任何跨請求快取（欄位值、計數、授權結論皆然） | 程式中無 cache／memo 結構；`grep -n "lru_cache\|cache" ` 於本單元新增檔案為 0 |

**理由**：讀的是使用者剛寫入的值與授權結論。快取欄位值會讓「剛儲存、切到總覽籤
卻看到舊計數」——正是 `AC11.3.2` 要防的失敗；快取授權結論會引入「已移出專案仍可讀」
的窗口。每次讀取是一次以 `uq_system_requirement_fields_group_key` 前導欄命中的索引查詢，
不值得用正確性去換。

## 四、刻意不設的目標（附理由，不留空白）

| 不設 | 理由 |
|---|---|
| 絕對延遲數字（如 p95 ≤ N ms） | 本 repo 沒有延遲量測機制；設無法量測的數字是宣告而非需求。以查詢次數（`NFR20.1`／`NFR20.2`／`NFR20.4`）代替，它是延遲不隨規模成長的必要條件 |
| 吞吐量目標 | 寫入來源是人在畫面儲存與大腦代寫，頻率遠低於任何既有端點；無上游流量數據可依據 |
| 回應大小上限 | 可算出上界：7 欄 × 每欄值上限 2000 字（`BR42.4`），約 14,000 字元＋固定欄位；不需另設 |

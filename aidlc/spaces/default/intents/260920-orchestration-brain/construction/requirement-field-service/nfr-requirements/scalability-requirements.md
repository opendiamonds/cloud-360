# 擴展需求 — `U20 requirement-field-service`

## 〇、本單元不是獨立的擴展單位

embedded：同一 FastAPI process 的新 router（`unit-of-work.md:308`），隨既有後端一起擴展，
沒有自己的副本數、佇列或背景工作。本檔只處理**資料成長**與**併發寫入**兩件事。

## 一、資料成長（可算，不估）

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR20.15`** | 每個系統的有效列數上界為**當前已宣告的欄位數**（第一版為 7，`entities.md` 的 `field_definitions_v1` 腳本實算）；定義外的保留列只在定義移除後出現，且不被讀取計入（`BR44.3`） | 對同一系統重複寫入同一欄位 N 次後，該系統的列數仍為 1（upsert，`BR43.5`） |
| **`NFR20.16`** | 列數**只增不減**（`ADR-015` 已接受）：本單元沒有任何刪除列的操作；系統刪除時由 `U18` 的 `ON DELETE CASCADE` 一併移除 | 本單元新增程式中無對該表的 DELETE；系統刪除後該系統的列數為 0（既有外鍵行為，回歸案例） |

**為什麼不需要分頁**：一次讀取的列數上界是一個系統的已宣告欄位數，不是使用者可無限
增加的集合。新增一組定義（新 agent 上線）會讓上界增加該組的欄位數，仍是程式碼控制
的常數。

**索引**：`U18` 已交付的 `uq_system_requirement_fields_group_key` 以 `system_id` 為前導欄，
同時覆蓋 `read_fields` 的 `WHERE system_id = ?` 與 upsert 的衝突判定，**不需新增索引**
（`schema_rbac.sql` 的 `J)` 區塊註解已逐字記載）。

## 二、併發寫入

| id | 需求 | 二元判準 |
|---|---|---|
| **`NFR20.17`** | 同一欄位的併發寫入以「最後寫入者勝」收斂，**不得**回 500（`BR43.5` 的 upsert） | 案例：先以直接插列造出「列已存在」，再呼叫 `write_field` 走首寫路徑的程式碼 → 不拋 `IntegrityError`、結果為新值 |
| **`NFR20.18`** | 清空與寫入同時發生時，結果必為兩者之一的合法狀態，不得出現「有值且已清空」 | 由 `U18` 的 `ck_system_requirement_fields_cleared_has_null_value` 在資料庫層保證；本站不加鎖 |

**不加鎖的理由**：與 `U19` 不同，本單元沒有跨列不變量（`U19` 要守「至少一位管理者」，
需要鎖父列）。每個欄位是獨立的一列，單列的最後寫入者勝不會破壞任何其他列的正確性；
後存者覆蓋前者的使用者面後果已揭露為 `OPEN-RF20-2`。

## 三、刻意不設的目標

| 不設 | 理由 |
|---|---|
| 並發使用者數目標 | 本單元不持有連線或工作者；併發上限即既有後端的上限 |
| 資料量成長率（GB／月） | 可算出量級：每系統 7 列 × 每列值上限 2000 字元，系統數由 `U7` 控制；遠小於既有架構圖 XML 的儲存量，不需單獨規劃 |

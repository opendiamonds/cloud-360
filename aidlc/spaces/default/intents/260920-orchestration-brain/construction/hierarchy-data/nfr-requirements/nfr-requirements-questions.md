## 前言：本站問什麼、不問什麼

本單元是 `spec` 類：交付資料模型與一次性遷移程序，**沒有端點、沒有畫面、
沒有 LLM 呼叫**。`produces_kinds` 據此把 performance／scalability／reliability／
observability 四份產出濾掉，本站只產出 `security-requirements.md`、
`tech-stack-decisions.md`、`traceability.json` 三份。

### 上游已定案、本站不重問（每項附可引用的依據）

### 本站查證到的事實（供題幹引用，非來源標籤）

1. **`AC9.1.2` 的 Given 在乾淨資料庫裡不可達**。`stories.md:413–419` 逐字：兩個環境走
   不同的 schema 路徑，「`AC9.1.2` 的 Given（一張在本 intent 之前建立的架構圖）在每個
   自動化環境裡**都不可達**——每個環境的 DB 都是新的」。
2. **`NFR6` 已經要求一個真實 PostgreSQL CI job**，但它的**範圍逐字限於**「schema 建立、
   grant 邊界、跨 schema 查詢」，講的是 `FR4.2` 的記憶層獨立 schema（`U5`）。
   `U4` 的表在預設 schema，不在該範圍的字面內。
3. **既有演進路徑全部吞掉失敗**。`K-04` `context_why_migration_is_the_only_path` 逐字：
   `schema_rbac.sql` 只在空 volume 執行、且含裸的 `DELETE FROM role_permissions;`；
   既有環境的唯一演進路徑是 `database.py` 的 `_ensure_*` 補丁，「而它們**全部吞掉失敗**」。
4. **`DiagramChangeRecord` 沒有任何保存期或清除規則**。同 intent 的 episodic memory 有
   `FR4.5` 的 90 天與 `FR4.7` 的刪除稽核；本表只寫不讀（`Q2=A`），且無人清。
5. **`BR1.3` 的兩個唯一約束在並行插入時會讓其中一方的寫入被拒**，而遷移目前沒有任何
   關於「被拒之後怎麼辦」的敘述——`BR2.2` 的冪等講的是**依序重跑**，不是同時執行。

## Q1 — `U4` 的真實 PostgreSQL 驗證，跟 `NFR6` 的那個 job 是同一個嗎？而 `AC9.1.2` 的前置狀態怎麼造出來？

`K-04` 要求真實 PostgreSQL 驗證，`NFR6` 也要求一個真實 PostgreSQL CI job——但後者的
範圍逐字只涵蓋記憶層的獨立 schema（事實 2）。而且不論共用與否，都還有第二個問題：
**乾淨的 CI 資料庫裡沒有「本 intent 之前建立的圖」**（事實 1），所以在新 DB 上跑一次
遷移只證明得了「不變量在空資料上成立」，證明不了 `AC9.1.2`。

- **A（建議）— 共用同一個 job，並要求它**先寫入一批「前置狀態」**（沒有 `system_id` 的
  既有圖 ＋ 多位使用者）再跑遷移，然後查不變量**。一個 job、一份 service container 設定；
  前置狀態由測試程式自己寫入，正是 `BR2.4` 的可匯入入口讓它做得到。
- **B — 兩個獨立 job**：`NFR6` 的管記憶層 schema，另開一個管 `U4` 的遷移。
  隔離較乾淨，但兩份 `postgres:16-alpine` service container 設定要各自維護，
  且 CI 時間加倍。
- **C — 共用 job，但不造前置狀態**：只在空資料庫上跑遷移並查不變量為 0。
  成本最低，但 `AC9.1.2`（遷移後圖仍能開啟並編輯）**仍然不可驗證**——
  這正是 `stories.md` 已經點名的那個洞，等於承認不修它。

## Q2 — 遷移在什麼時候跑？

`K-04` 只說必須有可被 unittest 匯入呼叫的入口，**沒說它在正式環境何時執行**；
<!-- 更正（iteration 1 審查 R-09）：這句話把契約說得比實際更沉默。K-04 的
     authorization_responsibility 逐字是「DDL 與遷移在部署／啟動路徑執行」——
     **「／啟動」三個字在原文裡**，也就是契約對兩條路都是開放的，不是沒提。
     是 Q2=A 把它收窄成只走部署的獨立指令。本題的定案不變，改的是這句前言的準確度。 -->
functional-design 也明文把「執行位置」留給下游。但這個選擇直接決定了它的失敗面，
所以在這裡定，而不是留到寫程式時順手決定。

- **A（建議）— 只做獨立指令，不掛啟動路徑**。部署時以一個明確步驟執行；
  失敗就是部署失敗，看得見。不會因為多個 backend 實例同時啟動而並行執行。
  代價：部署流程多一個步驟，且**必須記進 `DEPLOY.md`**（本來就是 blocking 規則）。
- **B — 掛在啟動路徑（`init_db()` 之後）**：部署不用多一步，環境自己會升級。
  代價：它與既有 `_ensure_*` 補丁同一條路徑，而那條路徑的既有形狀是**全部吞掉失敗**
  （事實 3）；而且多實例同時啟動即並行執行（見 Q3）。
- **C — 兩者皆可（啟動路徑呼叫，也能手動跑）**：`K-04` 的 entrypoint 措辭不排除這個。
  彈性最大，但把 A 與 B 的失敗面**同時**買下來。

## Q3 — `DiagramChangeRecord` 要不要保存期？

本表只寫不讀、無人清（事實 4）。同一個 intent 的 episodic memory 有 90 天保存與刪除稽核
（`FR4.5`／`FR4.7`），而本表承載的 `requirement_summary` 同樣是使用者輸入的需求文字。

- **A（建議）— 現在就定一條保存期，與 episodic memory 對齊（90 天），但本單元只定規則、
  不實作清除機制**，清除的承載方式列為具名待補項（`project.md` 禁止以 repo 內程式承載
  無人值守排程，所以它必須走 gh-aw 或 Actions，那是獨立決定）。
- **B — 明確不設保存期，並寫下理由**：本表是稽核資料，稽核資料通常要留久；
  `FR4.5` 的 90 天是對話歷程的規則，不該照抄到稽核表上。風險是它無限成長且無人察覺。
- **C — 本站不定案，指派給後續單元**：與 `OQ-H2`／`OQ-H3` 同形狀，列為 `OQ-H4`。
  誠實但把問題往後推，而本表**在本 intent 內就會開始寫入**。

## 收齊答案後的模糊語、矛盾與覆蓋檢查（Step 4，必做）

### 模糊語檢查

三個答案皆為可判定的具體選項，無「夠快」「高可用」「安全」這類不可量測措辭。
`Q3=A` 的「90 天」為明確數值，與 `FR4.5` 同值，可被查詢驗證。

### 跨題矛盾檢查

| 組合 | 判定 | 說明 |
|---|---|---|
| `Q1=A` × `Q2=A` | **相容且互相強化** | CI job 匯入 `BR2.4` 的入口呼叫遷移；部署的獨立指令呼叫**同一個**入口。兩條路徑共用一個實作，故 CI 驗的正是部署會跑的東西 |
| `Q1=A` × `NFR6` 的字面範圍 | **需要擴充上游，不是矛盾** | `NFR6` 的範圍逐字只有「schema 建立、grant 邊界、跨 schema 查詢」。`Q1=A` 讓同一個 job 多出「U4 遷移 ＋ 前置狀態 ＋ 不變量查詢」。**本站不改已核可的 `requirements.md`**，改列為具名待補項 `S-6` |
| `Q2=A` × 並行執行風險 | **風險大幅收斂，但不為零** | 選 B 才會有「多個 backend 實例同時啟動即並行」的暴露面；`Q2=A` 之後只剩「有人手動跑兩次」。`BR1.3` 的兩個唯一約束會讓第二次的寫入被拒——**但被拒之後必須大聲失敗**，這一條在上游沒有任何規則涵蓋，故本站寫成 `U4-V4`（iteration 1 審查 R-01 後由 `NFR6.4` 改編號——它沒有 inception NFR 父項）|
| `Q2=A` × `project.md` blocking 規則 | **相容，且加重了義務** | 多一個部署步驟 → `DEPLOY.md` 必須記載。該檔本來就因新增資料表而必須同步（functional-spec `§七` 已判定 5 個觸發條件命中 4 個），本答案讓它再多一項內容 |
| `Q3=A` × `project.md ## Forbidden` | **相容，但逼出一個新的承載決定** | 該條禁止以 repo 內程式承載**無人值守**的流程自動化。90 天清除正是無人值守排程，故它**不得**寫成 `scripts/` 下的 Python，必須走 gh-aw 或 GitHub Actions。這是獨立決定，列為 `S-5` |
| `Q3=A` × `S-4`（加密） | **不重疊** | `S-4` 管 `requirement_summary` 的**靜態加密**（落點 `nfr-design`）；`Q3=A` 管它的**保存期**。兩者可各自定案 |

### 覆蓋檢查（把已定的驗證計畫對照最高風險失敗模式）

最高風險的失敗模式在上游已被逐字點名兩次：**遷移的回填失敗被靜默吞掉**
（`K-04` 的「而它們**全部吞掉失敗**」、`stories.md:426` 的「直接否掉照抄既有
`logger.warning` 形狀的實作」）。

- `Q2=A` 讓它**不在**吞掉失敗的那條路徑上（獨立指令，失敗即部署失敗）；
- `Q1=A` 讓它在 CI 上**被實際執行過一次且驗過不變量**；
- `U4-V4` 讓「約束拒絕寫入」這個次要失敗模式也不得被吞掉。

三者與該失敗模式有交集，覆蓋檢查通過。**未被涵蓋的殘餘**：`AC9.1.3`
（既有頁面行為不變）在 CI 上仍無斷言——它需要前端 e2e，而本單元不交付任何畫面。
記入 `traceability.json` 的 `reverse` 與安全需求檔的殘餘風險段。

## Q4（追問，iteration 2 審查 R-12 逼出）— 遷移跑的時候，應用還能不能接流量？

`S-8` 把遷移的交易邊界定為逐使用者一個交易，於是它跨越多個 commit。這讓一個上游從未
討論的競爭浮現：**應用與遷移之間**的競爭（既有的並行敘述全部在講「遷移與它自己」）。
若遷移進行中有人透過既有 A1 頁面新建一張圖，那張圖不帶 `system_id`，`BR2.1` 的終檢
計數就不為 0——**而那不是遷移的錯**。

- **A（建議）— 要求靜止：遷移期間不接流量**。`AC9.1.4` 因此不需要改寫範圍
  （它逐字是「查詢架構圖表中 `system_id IS NULL` 的列數」，沒有限定範圍，而靜止讓這個
  無限定的說法成立）。
- **B — 允許並行，改寫不變量的範圍**：只管「遷移開始時已存在的列」。代價是改一條已核可的 AC。
- **C — 不定案，記為已接受風險**：誠實，但 `U4-V3` 的不變量在 staging 上的意義就是不確定的。

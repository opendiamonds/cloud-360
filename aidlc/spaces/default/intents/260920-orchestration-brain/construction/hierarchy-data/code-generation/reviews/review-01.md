### Summary

**A. The rules, one by one.** `BR1.1`/`BR1.2` land as `systems.project_id` and `user_diagrams.system_id` both `ON DELETE RESTRICT`, in all three DDL copies, and the test drives both layers *and* the release path (clear `system_id` → delete works), so it cannot pass against an unenforced FK or an unconditional block. `BR1.3` is genuinely two independent partial unique indexes, each referencing only its own table: `uq_projects_default_per_owner` on `(owner_user_id) WHERE is_default` and `uq_systems_default_per_project` on `(project_id) WHERE is_default` — `systems` has no owner column, the unbuildable single-constraint form is absent, and the test's last step (a default system under a *non*-default project succeeds) is exactly the assertion that pins the scope to `project_id`. `BR2.1` raises `HierarchyMigrationError` with the residual count; there is no `logger.warning` fallback anywhere on that path. `BR2.2` is the `WHERE system_id IS NULL` guard plus get-or-create. `BR2.3` is honoured structurally, not by discipline: the write is `sqlalchemy.text()` precisely because `models.UserDiagram.updated_at` carries `onupdate=func.now()`. `BR2.5` resolves the default project first and then scopes the system lookup to that project id, and `_users_holding_diagrams` joins `users`, so diagram-less users get nothing. `BR2.6` returns three counts and logs them. Every rule this unit owns has a line of code behind it that I could point at.

**B. The two declared deviations.** Deviation 1 (DDL in two places) is correct and its argument survives verbatim checking against `K-04` — indeed `K-04`'s own `entrypoint` clause forbids the single-copy alternative. The mitigation is *partially* sufficient: it catches the one class it was built for (a column added on one side only, confirmed by mutation M6) and nothing else — see R-03 for the exact drift list, and note that the index checks are substring-presence only, so uniqueness and the partial predicate are not locked in the SQL file. Deviation 2 checks out: the two extra cases are the ones claimed, `TestHierarchySchema` at 7 is inside the Standard 5–8 band, and both extras are defensible (one is demanded by `team.md`; the other covers a self-authored `raise` branch that would otherwise rot). `TestHierarchyMigrationData` sits at 3, below the band — but the approved plan already disclosed that, so it is not a new finding.

**C. The `CASCADE` decision.** Not re-litigated. The cost is recorded accurately in `code-summary.md §七.2` and nothing in the schema depends on those rows surviving; the gap is that it is absent from `traceability.json` and that the disclosure never connects to `SEC-4(3)`'s own stated principle — the *disappearance* of audit data must itself leave a count (R-05).

**D. Tests that cannot fail.** All three named traps are genuinely armed. The final-check test asserts `assertRaises` **and** the residual count in the message **and** that already-committed work survived — a warning-only implementation fails it. The rerun test really invokes the migration twice, then counts rows in both tables, counts `is_default` rows in both tables, and compares every diagram's `system_id` to a pre-recorded baseline — the "looks successful" failure mode `BR2.2` describes is caught. The BR2.3 test snapshots four columns per row and compares value by value, with `updated_at` pinned to a fixed past timestamp specifically to defeat SQLite's second-granularity `CURRENT_TIMESTAMP`. Spot-checking two mutation claims against the test bodies rather than the table: **M1** (raise → warning) would fail `test_final_check_raises_…` and `test_rerun_after_a_failure_…` on `assertRaises` and `test_standalone_command_…` on the exit code — the three cases claimed; **M5** (single transaction) would leave the per-user work uncommitted when the final check raises, so both `test_final_check_raises_…` (alice's diagrams asserted non-null after `rollback()`) and `test_rerun_after_a_failure_…` (projects/systems counts asserted at 2 after `rollback()`) fail — the two cases claimed. Both claims hold.

**E./F. Security and traceability.** `SEC-1`–`SEC-4`, `construction.md`'s error-surfacing rule and `team.md`'s naming/logger/dependency rules all check out mechanically (table above). The `U4-V*` family is graded honestly — five of six `Deferred` with the missing CI carrier named — and I found no `OK` that should be `Deferred`; the two recording defects are R-05 and R-06.

**G. What I expected and did not find.** The per-user transaction boundary **is** a real transaction (both writes share one session transaction, one `commit()` at the end, `rollback()` before re-raising), and interruption between users is a documented, recoverable state with a test that proves the earlier users survived the raise. The two real gaps a careful reviewer finds are the asymmetric constraint guard (R-01) and the rollback SQL (R-02) — and the rollback SQL's own safety check is unreachable, which is the shape `project.md`'s "先推導 X 是否可達" correction exists for.

Upstream problem surfaced but mishandled: 0 — every upstream gap I could find (`diagram_id` `ON DELETE` unspecified, `entities.md`'s `owner_user_id` vs physical `user_id`, the plan assigning all DDL to `schema_rbac.sql`, `schema_rbac.sql`'s missing `users.authorization_status`) is surfaced in `code-summary.md §七`/`§六.8` with a disposition and a reason, and none was absorbed silently. **What the human should weigh at the gate, ranked.**
1. **R-01** — the one place where a claimed database-level guarantee (`BR1.3`, and through it `BR2.2`'s whole idempotency argument) can be silently absent while the migration reports success. The fix is a few explicit `CREATE UNIQUE INDEX IF NOT EXISTS` lines or one `get_indexes()` check; cheap now, and it removes the only asymmetry in an otherwise disciplined module.

It is safe today only because nothing but the migration can write `projects`/`systems`; it destroys user assignments and its own guard is dead code the moment `U7` ships. 4. **R-03/R-04** — decide whether a third, partial, unlocked DDL copy in `schema.sql` is worth keeping at all; deleting its `H)` block would close R-04 and shrink R-01's supply side in one move.

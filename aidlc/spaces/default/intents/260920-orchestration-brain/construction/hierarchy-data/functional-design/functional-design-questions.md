## 前言：本站問什麼、不問什麼

`U4` 交付的是**資料模型與一次性遷移程序**：`projects`／`systems`／`diagram_change_records`
三表、`user_diagrams.system_id` 欄位、遷移程序，以及
「遷移後 `system_id IS NULL` 計數為 0，不為 0 就**大聲失敗**」這條不變量。

本站只問四件事，全部是上游**明文指派或明文留下**的缺口。

## Q1 — `DG-2`：刪除 `System`（或 `Project`）時，其下架構圖的 `system_id` 怎麼辦？

**這是 `domain-design` 明文指派到本站的缺口**（`K-04` `known_threat_to_the_invariant`，
`landing: functional-design`）。`decisions.md:134–137` 逐字：

> 「該不變量在執行期可被打破：遷移後若有人刪掉一個 `System`，其下架構圖的
> `system_id` 會懸空，`AC9.1.4` 要求計數為 0 的條件即不再成立……本 ADR 只保證
> 遷移程序本身，**不保證遷移之後的維持**。」

四個選項都以事實 1 的既有慣例為對照，不是憑空發明：

- **A（建議）— `ON DELETE RESTRICT`：系統底下還有圖就不准刪**。
  不變量**由構造保持**——不可能出現懸空的 `system_id`，因為產生懸空的那個動作被擋住了。
  刪系統前必須先把圖移走或刪掉，那是一個**使用者看得見、且必須明確做**的決定。
  代價：刪除流程多一步，且錯誤訊息要說清楚「還有 N 張圖」——否則使用者只會看到
  一個不明所以的 500。**與慣例的關係**：repo 目前沒有 `RESTRICT` 先例，這是新形狀。
- **B — `ON DELETE SET NULL`**：沿用 `users.last_opened_diagram_id` 的先例（事實 1）。
  **但它正好打破 `AC9.1.4`**——那條不變量要求的就是 `system_id IS NULL` 計數為 0，
  而本選項的整個機制就是把它設成 NULL。選它等於接受「不變量只在遷移當下成立」。
- **C — `ON DELETE CASCADE`**：沿用多數先例（5 處中的多數）。刪系統連帶刪掉其下全部架構圖。
  不變量保持，代價是**架構圖是使用者的核心資產**，一次誤刪系統就連帶消失，
  且 `user_diagrams` 目前對 `users.id` 的 FK 連 `ondelete` 都沒有（事實 2）——
  本選項會讓「刪系統」比「刪使用者」更具破壞性。
- **D — 軟刪除**：`systems` 加 `deleted_at`，刪除只是標記，圖的 `system_id` 不動。
  不變量保持且零資料損失。代價：**每一個讀取端都要記得過濾 `deleted_at IS NULL`**，
  漏一處就是一個看得到已刪系統的畫面；而本 repo 目前**零軟刪除先例**，
  等於為此引入一套新慣例。

## Q2 — `DG-3`：`DiagramChangeRecord` 目前沒有讀取端，怎麼處置？

`domain-design` 自檢查出「`DiagramChangeRecord` 無讀取端」並指派本站。
一張只有寫入端的表是本 repo 反覆在意的形狀：它會一直長大、沒有人看，
而「有沒有正確寫入」永遠不會被任何人發現。

- **A（建議）— 本輪只建表並只寫入，但在本站產出中明文指名未來的讀取端與觸發時機**，
  並把「無讀取端」記為**已接受的狀態**而非遺漏。
  理由：讀取面（例如架構圖的變更歷程畫面）**不在本 intent 的已核可範圍內**——
  `scope-document.md` 的能力 9 逐字只有「專案 → 系統 → 架構圖 階層」，
  硬給它一個讀取端就是本站自行擴大範圍。
  代價：這張表在本 intent 結束時確實是隻寫不讀的。
- **B — 現在就給它一個讀取端**。要指名是哪個單元、哪個畫面。
  代價：那是新增的使用者可見面，`scope-document.md` 未涵蓋，需回補；
  且它會落在已經最重的 `U14` 上。
- **C — 本輪不建這張表**，等讀取端的需求成立時再建。
  最誠實，但 `K-04` 的 `tables` 逐字列了 `diagram_change_records`，
  且 `components.md` 把「架構圖變更紀錄」列為 `ProjectHierarchy` 的責任之一——
  選它等於推翻兩份已核可產出，需明確的回頭修訂。

## Q3 — 遷移的冪等判準：怎麼認定一張圖「已經掛好了」？

`K-04` 逐字要求「**遷移本身必須冪等**：重跑時已掛好的圖不得被重新指派，
否則部分失敗後的重跑會產生第二組預設專案／系統」。但它沒說**怎麼判定「已掛好」**，
而這個判準決定了部分失敗後重跑會發生什麼。

- **A（建議）— 以 `system_id IS NOT NULL` 為判準，且「預設專案／系統」以
  唯一約束保證每人至多一組**。

       `(owner_user_id, is_default)` 且對 Project 與 System 都套用。

       而唯一性約束無法以另一張表 join 來的值為範圍——照初版描述做不出來。

## Q4 — `DiagramChangeRecord` 的寫入涵蓋面：只有大腦路徑，還是含既有 A1 編輯路徑？

**這是本站查證時新發現的，不是上游指派的。** 事實 4：這張表唯一的寫入端是
`U12 WorkOrchestrator`，而它是大腦的交辦層；經既有 A1 頁面直接編輯的圖**不經過它**。

於是命名與實際涵蓋面不符：表叫「變更紀錄」，承諾的是全部變更；實際拿得到的
只有大腦發起的那些。這不是實作細節——它決定這張表**能不能回答「這張圖為什麼變成這樣」**。

- **A（建議）— 收窄語意，改名為「大腦交辦紀錄」之類，明寫它只涵蓋大腦路徑**。
  零額外工作量，且讓表名說真話。代價：`K-04` 的 `tables` 與 `components.md`
  都寫 `diagram_change_records`／「架構圖變更紀錄」，改名需在本站標明是收窄而非新增。
- **B — 維持語意，並在既有 A1 的儲存路徑也加寫入**。
  表名說真話，但**動到既有頁面的行為**——而 `AC9.1.3` 逐字要求
  「我使用既有的架構圖頁面，其行為不變」。加一筆寫入是否算「行為改變」需要裁決；
  更實際的是它讓本單元從「加表」變成「改既有寫入路徑」，範圍明顯擴大。
- **C — 維持現狀不處理**，把落差留給下游。
  代價：下一個讀這張表的人會以為它是完整的變更歷程，而它不是——
  而那種誤解**在資料上看不出來**（表裡有列，只是少了一半）。

### Q4=A 的子決定（本站就地收斂，並在摘要向使用者揭露）

使用者選的是「讓表名說真話」。直接改實體表名會牴觸 `K-04` 的 `tables` 清單
（已核可契約），製造一個本來不存在的衝突。**改採的做法**：

- **實體表名維持 `diagram_change_records`**，使 `K-04` 的 `tables` 逐字仍然成立；
- **語意由資料自己宣告**：新增一個必填的 `source` 欄位，值域為封閉列舉，
  本輪唯一合法值為「大腦交辦」。表的每一列都自己說明它的來源，
  涵蓋面因此是**機器可讀的**，不只是散文裡的一句話；
- 未來若 A1 儲存路徑也要寫入，只需新增一個列舉值，**不需要 schema 遷移**。

**這比改名更接近「說真話」**：改名只是換一個標籤，而 `source` 讓「這張表涵蓋什麼」
成為可查詢的事實。但**這是我對選項的具體化，不是使用者選的字面內容**，
故在彙整摘要中明白揭露，供更正。

### Q1=A 製造的新交接義務（**必須指名，否則會靜默落空**）

`RESTRICT` 讓刪除在資料庫層被擋下，但**擋下之後要對使用者說什麼，不屬本單元**——
`US9.2`（建立／修改／刪除）由 story map 指給 `U7`／`U16`／`U3`。

| 義務 | 落點 | 不做的後果 |
|---|---|---|
| 刪除被 `RESTRICT` 擋下時，回傳可理解的錯誤（指出「還有 N 張圖」與下一步） | **`U7 hierarchy-service`**（`K-07` facade） | 使用者只看到一個不明所以的 500，而資料庫層的保護會被誤讀為系統壞掉 |
| 刪除前的前置動作（把圖移出系統 / 先刪圖）需要一個使用者路徑 | **`U7`** 的介面面；畫面面在 `U16` | 不變量保住了，但使用者沒有任何方法刪掉一個空不掉的系統 |

本站**不設計**那個錯誤訊息或那條路徑——只把義務寫進產出並指名落點。

### 三項本站**不定案**的新發現

**第一項（`OQ-H1`）**：`RESTRICT` 讓一個既有缺口浮上來——**刪除使用者時，他擁有的 `projects` 怎麼辦？**
`user_diagrams.user_id` 目前對 `users.id` 的 FK **連 `ondelete` 都沒有**（事實 2），

若設 `CASCADE`，刪使用者會連帶刪掉專案，而專案底下的系統若還有圖又會被 `RESTRICT` 擋住
——兩者相加的行為需要一次獨立的裁決。

**第二項（`OQ-H2`，iteration 2 審查 R-08 逼出來的）：遷移之後，誰保證新建的圖有 `system_id`？**

`system_id` 在本設計裡**永遠可為空**，而 `BR1.2` 只擋「刪除 System」這一條路。
於是遷移跑完之後，既沒有規則禁止把一張已掛好的圖的 `system_id` 改回空，
也沒有規則要求新插入的圖必須帶 `system_id`——**既有 A1 存圖路徑正是後者**，
它不知道 `system_id` 的存在（而 `AC9.1.3` 逐字要求它的行為不變）。

`AC9.1.4` 本身不受影響：它的 Given 是「遷移已執行」，問的是那一刻的列數，
遷移終檢（`BR2.1`）確實讓它成立。受影響的是 `SM-1` 原本寫的絕對句
（「`Assigned` 永不回到 `Unassigned`」）與「這句話就是 `DG-2` 的解」。

把欄位收成 `NOT NULL` 可以一次關掉兩條路，**但它與 `AC9.1.3` 直接衝突**：
既有頁面的插入不帶 `system_id`，收緊之後那條插入會失敗。所以這是一次獨立裁決，
**本站不自行定案**：收緊的前置條件是每一個寫入端都先供值。落點 `U7`（生命週期）
與 `U16`（畫面面），並在 `functional-spec.md §八` 以 `OQ-H2` 登錄。

**第三項（`OQ-H3`，iteration 2 審查 R-11 逼出來的）：共享工作階段有多位參與者時，

行動者是哪一位」取決於 `WorkOrchestrator` 的內部設計，不屬本單元。**本站不定案**，

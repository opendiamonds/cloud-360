## Q1 — `OQ-3`／`S-4`：`requirement_summary` 與 `requirement_label` 要不要欄位級加密？

這兩欄承載使用者輸入的需求文字。`OQ-3` 自身文字只涵蓋 episodic memory（`U5`），
`S-4` 把範圍擴及本單元——**而本站就是 `OQ-3` 的落點，再往後推就沒有承接站了**。

**跨單元一致性的提醒**：`U5` 的 episodic memory 會在它自己的 `nfr-design` 回合回答同一題。
若本站答「不加密」而 `U5` 答「加密」，兩份同類資料會有兩種待遇——那不一定錯（量體與
可識別程度不同），但**必須是被看見之後的選擇，不是各答各的結果**。

- **A（建議）— 不做欄位級加密；以網路封閉 ＋ 主機磁碟為界，並誠實寫下殘餘風險**。
  理由：資料庫不對外（事實 2），連線在 compose 內部網路；欄位級加密會讓這兩欄
  不可查詢、不可索引，而且需要一把新的金鑰——直接牴觸 `SEC-2`「不得引入第二個憑證」的精神。
  代價：**靜態加密實際上不存在**，主機磁碟被取得即明文；這一點要寫進殘餘風險表，
  不能用「已依 ADR-0006 處理」帶過。
- **B — 以 `pgcrypto` 做欄位級加密**。靜態保護最強。代價：新增一把金鑰（新憑證、新環境變數，
  與 `SEC-2` 衝突需要例外）、兩欄不可查詢、且本 repo 零先例（事實 3），
  等於為一張**沒有讀取端**的表引入一套金鑰管理。
- **C — 本站不定案，往後推**。**不建議**：本站就是 `OQ-3` 的指定落點，往後推等於讓它
  沒有承接站——這正是 `S-4` 當初被具名的理由。

## Q2 — 遷移的資料庫連線要不要 TLS？

遷移是一次特權的 DDL ＋ 跨使用者資料寫入，而現況連線是明文（事實 1）。
`ADR-0006` 的 encryption 面向要求傳輸加密要有明確立場，**不是有沒有做，而是有沒有想過**。

- **A（建議）— 不加 TLS，並寫下理由與界線**：連線兩端都在 compose 內部網路，
  資料庫不發佈 port（事實 2），加 TLS 需要在單機部署裡管憑證與續期，
  防護增益與成本不成比例。**界線**：這個結論**只在資料庫與應用同主機、且 db 不對外時成立**；
  任何一天 db 被搬到獨立主機或發佈 port，本結論即失效——這句話要寫進設計檔。
- **B — 要求 `sslmode=require`**：傳輸加密到位。代價：憑證的產生、掛載與續期在
  `deploy/` 裡目前完全沒有先例，且 `DATABASE_URL` 是 compose 內插的字串，改它會牽動
  `render-env.sh` 與 `.env.example`（`validate_env_contract.py` 會檢查）。
- **C — 本站不定案**：可以，但 `ADR-0006` 的 encryption 面向就只能寫「未表態」。

## Q3 — `actor_user_id` 認不出行動者時，該寫什麼？

`entities.md:196` 把它定為 `required: true`，而 `OQ-H3` 說多參與者下「行動者是哪一位」
由 `U12` 決定、本站不定案。但**必填欄位一定會被填進某個值**，所以「認不出來的時候怎麼辦」
是一條**稽核完整性**的規則，而本單元擁有這張表與它的必填性——這一題是本站的。

- **A（建議）— 認不出就讓變更紀錄的寫入失敗，並讓整個異動失敗**。稽核與事實綁在一起：
  沒有可信的行動者就不留下「圖被改了」這件事。代價：`U12` 必須先解出行動者才能動圖，
  這是對 `U12` 的實質約束（要寫進 `OQ-H3`）。
- **B — 寫入工作階段擁有者，並以一個欄位標記「非確證」**。異動不會被擋住，但需要多一個欄位。

## 收齊答案後的模糊語、矛盾與覆蓋檢查（Step 3，必做）

### 模糊語檢查

三題皆為可判定的結論。`Q1` 是自由文字但方向明確（「不需要做任何加密」），
且經一次窄化確認把它與「判定要不要照寫」分開處理，沒有留下「大概」「看情況」這類措辭。

### 跨題矛盾檢查

| 組合 | 判定 | 說明 |
|---|---|---|
| `Q1=X` × `Q2=A` | **一致** | 兩題都是「不加密」；`Q2` 的界線子句是它誠實的限定，不是反悔 |
| `Q1=X` × `SEC-2` | **一致且互相強化** | 不加密＝不需要金鑰＝不需要第二個憑證，正是 `SEC-2` 要的 |
| `Q1=X` × **`U5` 的同一題** | **未綁定，需具名** | `OQ-3` 的另一半（episodic memory）會在 `U5` 自己的 `nfr-design` 回合作答，**不受本站答案約束**。若 `U5` 答「加密」，兩份同類資料會有兩種待遇——那不必然錯，但必須是被看見之後的選擇。列為 `S-10` |
| `Q3=A` × `entities.md:196`（`required: true`） | **一致** | 必填 ＋ 認不出就整體失敗，是連貫的：不會有「填了一個不可信的值」這種中間狀態 |
| `Q3=A` × `SEC-4` 的條件性 | **把 `SEC-4` 變強了** | 原本 `SEC-4` 的稽核保證「在 `OQ-H3` 定案前不成立」。`Q3=A` 給了它一個定義好的失敗模式，於是保證變成：**要麼有可信的行動者，要麼這次異動根本沒發生**。這比原來強 |
| `Q3=A` × `OQ-H3`／`U12` | **約束而非解決，需具名** | 本站沒有回答「多參與者下誰是行動者」（那仍是 `U12` 的），但加了一條它必須滿足的前置：**動圖之前必須先解出行動者**。這是對 `U12` 流程的實質約束，列為 `S-11` |

### 覆蓋檢查（把已定的設計對照最高風險失敗模式）

本站主題下最高風險的失敗模式**不是**被攻擊，而是**「不加密」在下游被讀成「加密已經考慮並處理過了」**——
那會讓任何後來評估這張表的人以為有保護。處置：`§一` 的 `ADR-0006` 判定表把結論、理由與
殘餘風險三者並列寫出，不用「已依 ADR-0006 處理」這類措辭。

第二個風險是 `Q3=A` **新增了一條使用者可見操作的失敗路徑**（認不出行動者→整個異動失敗）。
它必須對 `U12`／`U16` 可見，不能只活在本檔——已具名 `S-11`。

**未被涵蓋的殘餘**：主機磁碟被取得即明文（`Q1=X` 的直接後果，已記入殘餘風險表）。

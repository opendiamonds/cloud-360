# Reliability Design — `U11 intent-router`

> 承接 `nfr-requirements/reliability-requirements.md`（含其修訂 1 對 circuit breaker
> 論證的更正）。主軸不變：**把「不知道」如實往上傳，而不是把它變成一個看起來
> 正常的錯誤答案。**

## 一、失敗分類：四種，而它們必須在型別上分得開

`NFR3.74` 要求失敗率按錯誤型別分計。設計上的前提是**四種失敗在程式裡是四個型別**，
不是四個訊息字串：

| 型別 | 觸發 | 使用者看到 | 依據 |
|---|---|---|---|
| `LlmUnavailable` | 連線失敗、5xx、429、逾時 | 「請再說一次」 | `NFR3.68`；`K-10` 的 `raises` |
| `LlmBudgetExceeded` | 供應商回報用量上限 | 同上 | 同上 |
| `EmptyCandidates` | 分類器回空清單 | 同上 | `NFR3.69`；`BR2.4` |
| `MalformedRouting` | JSON 不合、`capability` 不在列舉、`slot` 不連續、超出上界 | 同上 | `NFR3.70`；`[D1]`=A 的解析層驗證 |

**四個型別、一種使用者體驗**：使用者分不出來也不需要分，但**維運必須分得出來**
——`LlmUnavailable` 是供應商的事，`MalformedRouting` 是我們的 prompt 或 schema
壞了。混成一個 `RoutingError` 會讓這兩件事在圖表上長得一樣。

## 二、`MalformedRouting` 的五道驗證（`[D1]`=A 的直接後果）

扁平 schema 把兩層的還原放在我方，所以**驗證也在我方**。五道，缺一則 **`EC6`
與 `EC7`** 不成立（**`EC8` 不在這五道的射程內，見 §二之二**）：

| # | 驗證 | 違反時 |
|---|---|---|
| V-1 | `candidates` 非空 | `EmptyCandidates`（`BR2.4`） |
| V-2 | 每個 `capability` 在封閉列舉內 | `MalformedRouting`（`BR2.2`） |
| V-3 | `slot` 自 **0 連續**、最大值 ≤ 3（即 ≤ 4 槽位） | `MalformedRouting`（`performance-design.md` §三） |
| V-4 | 每個 slot 分組至少一個候選；組內 `rank` 自 1 連續且唯一 | `MalformedRouting`（`EC1`／`CandidateIntent.rank`） |
| V-5 | `score` 全有或全無（跨**整張清單**，非每組） | 整張清單視為無分數（`EC2`）——**這一條不是失敗，是降級到 `BR3.3` 分支** |

**V-5 刻意不是失敗**，這是 `[IR1]`=A 的設計收益：模型只給部分分數時，
系統不壞，只是走無分數分支。**V-3 與 V-4 則必須是失敗**——它們壞掉代表
槽位結構錯了，而靜默修補（補齊、截斷）正是 `R-01` 查出的那個失敗模式。

## 二之二、`EC8` 不是輸入驗證，它是一個**輸出構造**的設計決定（修訂 1，審查 `R-06`）

**原文宣稱「五道驗證缺一則 `EC6`–`EC8` 不成立」，那是過度宣稱。** 逐條核對：
V-1～V-5 **全部**作用於「解析 Jev 回應」這一步（§二的標題自己寫「`[D1]`=A 的
直接後果」），而 `EC8` 約束的是**另一個完全不同的步驟**——`below_threshold` 為真時，
把**所有不可單選槽位**的候選攤平成 `IntentDecision.candidates`，並要求每個
`label` 帶出它屬於哪一件事。**沒有任何一道輸入驗證會碰到這個輸出構造。**

### 設計決定：`label` 的出處由**程式附加**，不依賴模型

| 項目 | 決定 |
|---|---|
| **誰做** | **L5 predicate**（它已經在做 `BR4.2` 聚合，攤平是同一步的延伸） |
| **怎麼做** | 攤平時**以程式**把該槽位的任務描述前綴到 `ClarifyCandidate.label`，形如 `「改架構圖」：加一層 Redis 快取` |
| **槽位的任務描述從哪來** | 同一次 tool call 的 schema 另帶一個 `slot_labels` 欄位（每槽位一句人話），與 `candidates` 平行。**它仍是扁平的**，不違反 `[D1]`=A |
| **為什麼不依賴模型自己把出處寫進 `label`** | 那是一個**無法驗證**的要求：模型寫了什麼都像是合理的 `label`，沒有任何斷言能判定「它有沒有帶出處」。程式附加則可被直接斷言 |

**可構造的失敗情境（若不做這件事）**：使用者一句話含兩個不可單選的意圖，
畫面上出現 4 個候選，而使用者**看不出哪兩個是同一件事**——`EC8` 要防的就是這個，
而本檔原本以為它已被五道驗證涵蓋。

**這一項不給編號 `V-6`**，因為它不是輸入驗證；它是 L5 的構造責任。

## 三、不設 circuit breaker — 設計面的最終判定

`nfr-requirements/reliability-requirements.md` 修訂 1 已刪除原本不成立的
「與 `NFR3.67` 直接衝突」論證。本站確認該結論並補上設計面的理由：

| 項目 | 內容 |
|---|---|
| **收益** | 供應商系統性故障時，避免每個請求各自等滿 5 秒 |
| **成本** | 斷路器狀態必須跨行程共享（否則 N 個行程各自計數，門檻形同除以 N），故需 Redis；而**本單元目前對 `U10` 只有唯讀依賴**（`BR7.4`），加它會新增一個寫入方向 |
| **判定** | **本單元不建**。正確落點是共用的出站層 `langgraph_runtime`——它已經是所有 LLM 路徑的共同入口，在那裡建一次所有路徑都受益，而本單元建一個只保護自己 |
| **替代** | `NFR3.74` 的分類失敗率按型別分計：供應商系統性故障會在 `LlmUnavailable` 的曲線上一眼看出 |

## 四、健康檢查：本單元**不提供**，而這需要一句話

本單元是 `in-process`、無端點（`SEC-2`），所以它沒有自己的 `/health`。
但「路由層可不可用」是一個真實的維運問題。

**首要理由是結構性的，不是品質判斷**（修訂 1，審查 `R-09`）：`SEC-2` 逐字
「模組不建立 `APIRouter`，不被 `main.py` `include_router`」——**建一個健康檢查端點
本身就違反它**。亦即本單元**從來沒有「要不要建」這個選項**。

**次要理由（即使不受 `SEC-2` 所限也不會建）：它會說謊。** 一個 `/health` 若只檢查
「模組載入成功、設定齊全」，它在 Jev 掛掉時仍會回綠——那比沒有更糟。
真正能回答「路由層可不可用」的只有**真實流量的失敗率**（`NFR3.74`）。

**啟動期檢查是另一回事，而它有**：`BRAIN_ROUTER_CONFIDENCE_THRESHOLD` 缺值即
啟動失敗（`BR3.4`），其餘四個設定缺值取預設並記 WARN。這是 `NFR8.60`
在本單元的落法——**啟動期驗設定，執行期驗流量，不做中間那種會說謊的探測**。

## 五、降級路徑：一條，且刻意不經 `done`

```
模型失敗 ──▶ raise ──▶ U13 以 error 事件終止該輪 ──▶ 使用者看到「請再說一次」
```

**不得**把失敗塞進 `prompt_guard` 的固定拒絕訊息路徑——那條路徑以 `done` 結束
（`BR1.3`），而把失敗塞進去會讓「系統正確地拒絕」與「系統壞了」在畫面上長得一樣。
這一條在 `functional-spec.md` 的狀態機已經畫出來，本檔重申它在設計層的落法：
**`refused` 與 `failed` 是兩個不同的終止事件型別，不共用程式路徑。**

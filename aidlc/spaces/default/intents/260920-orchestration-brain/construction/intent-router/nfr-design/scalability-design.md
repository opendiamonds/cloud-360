# Scalability Design — `U11 intent-router`

> 承接 `nfr-requirements/scalability-requirements.md`。該檔已確立本單元**沒有可由
> 自己解決的擴展瓶頸**（無狀態、`in-process`、上界在模型供應商側），本檔只設計
> **讓那個性質成立且可被驗證**的做法。

## 一、無狀態是一個要被守住的設計性質，不是現況描述

`NFR3.67` 禁止行程內共享可變狀態；`NFR4.70` 說本單元重啟後無東西可還原。
**這兩條會被日常開發自然侵蝕**——加一個計數器、加一個 memo、加一個「上次用過的
模型 client」都很合理。設計上的守法是**把它變成可機械檢查的**：

| 做法 | 內容 |
|---|---|
| **S-1 模組層只允許不可變綁定** | 模組層只能有：`Final` 常數、`dataclass(frozen=True)` 型別、函式。**不得**有 module-level `dict`／`list`／`set`／可變物件 |
| **S-2 唯一的例外是 client factory 的連線重用** | 它不持有請求間的語意狀態（見 `performance-design.md` §二 P-4 的界線說明）。**這個例外必須在程式碼裡被註記為例外**，否則下一個人會以它為先例 |
| **S-3 結構斷言** | 測試掃模組層 AST，斷言沒有可變的 module-level 綁定（白名單排除 S-2 的 factory） |

**S-3 是本站的設計決定，而它的價值在於時間**：無狀態這個性質在**第一天**是真的，
它會不會在第三十天還是真的，取決於有沒有一個會變紅的測試。

## 二、水平擴展：本單元隨 backend 走，沒有自己的旋鈕

```
            ┌─ backend 行程 1 ─┐   ┌─ backend 行程 2 ─┐
            │  U13 → U11 → …   │   │  U13 → U11 → …   │
            └────────┬─────────┘   └────────┬─────────┘
                     └──────────┬───────────┘
                                ▼
                        OpenRouter / Jev
                   （真正的併發上界在這裡）
```

- 本單元是 `in-process`（`K-10`），**沒有自己的部署單位**。加 backend 行程即加路由容量。
- `U10` 的 Redis 讓 session 跨行程共享，所以兩個行程服務同一個使用者的不同輪次**不需要黏著性**。
  **本單元因為無狀態，自動繼承這個性質**——這是設計上的收益，值得寫下來。

## 三、容量推算是一道除法，而本站只能寫到這裡

`NFR3.62`（每輪恰 1 次呼叫）讓推算變成：

```
每秒模型呼叫數 = 每秒入口頁送出數
```

**本站不填目標併發數**（`nfr-requirements` 已說明理由：inception 沒給使用者規模，
填一個就是編造）。但本站補一件設計面的事：**讓那個數字在它存在的那天可以直接量到**
——`observability-design.md` 的 `len(slots)` 分佈與 `classify` 速率指標即為母體。

## 四、達到上界時的行為（這是設計，不是容量數字）

| 情境 | 行為 | 依據 |
|---|---|---|
| OpenRouter 回 429（速率限制） | raise `LlmUnavailable`，**不重試、不排隊** | `NFR9.62`；`NFR3.63` |
| 輸出超過 `maxItems` 8 或槽位超過 4 | 走 `BR2.4` 失敗路徑，**不截斷** | `performance-design.md` §三 |
| prompt 逼近 Jev 的 context 32000 | 由 `NFR9.61` 的最少上下文在**組裝時**就避免；若仍超過，失敗而非截斷歷程 | `NFR9.61` |

**三者的共同形狀：到了上界就失敗，不降級。** 這與 `reliability-design.md` 的主軸
一致——降級會讓使用者拿到一個看起來正常的錯誤結果。

## 五、本單元對其他單元的擴展性影響（一項，必須寫明）

**本單元每輪必然呼叫一次 `MemoryFacade.search`（指涉詞解析時）。**
那是對 `U8` 的讀取負載，而 `U8` 走 PostgreSQL ＋ 向量檢索。

| 事實 | 影響 |
|---|---|
| 每輪 1 次 `search`，與模型呼叫同量級 | `U8` 的讀取 QPS ≈ 入口頁送出 QPS |
| `search` 的 `limit` 由本單元決定 | **本站定 `limit` 小（建議 5）**：指涉詞解析需要的是最相關的幾筆術語，不是全文檢索 |

**這一項之所以要寫在本檔**：本單元自己沒有擴展瓶頸，但它會**對別人產生負載**，
而那個負載的大小由本單元的一個參數（`limit`）決定。不寫下來，`U8` 的容量規劃
會少掉一個來源。**承接**：`U8` 的 `nfr-requirements` 已完成，故記為交接事項
給 `build-and-test`（量測時把本單元的 `search` 呼叫納入 `U8` 的負載母體）。

# Performance Design — `U11 intent-router`

> 本檔把 `nfr-requirements/performance-requirements.md` 的**目標值**轉成**做法**。
> 設計階段：程式片段一律 ≤15 行、介面層級，完整實作屬 `code-generation`。

## 一、整體形狀：一次呼叫、一個 schema、兩層在我方還原

`NFR3.62` 定死**每輪最多 1 次模型呼叫**，所以 N 個槽位必須在**同一次**回應裡取得。
`[D1]`=A 決定該回應是**扁平的 `candidates` 陣列 ＋ `slot` 索引欄位**。

```
user text ──▶ prompt_guard ──▶ 組裝最少上下文 ──▶ 單節點 StateGraph
                  │                                      │
              命中即止                            1 次 tool call（Jev）
            （不呼叫 LLM）                               │
                                            扁平 candidates[] + slot
                                                        │
                                          依 slot 分組 ＋ 驗證（我方）
                                                        │
                                          ClassificationResult.slots
                                                        │
                                   can_single_out 逐槽位 ＋ BR4.2 AND 聚合
```

**兩層的還原在我方，不在模型。** 理由見 `[D1]`：repo 零結構化輸出前例、
且無金鑰無法先驗 Jev 的 schema 支援度，雙重未知下選對模型要求最低的形狀。

## 二、`NFR3.60`（P50 ≤ 800 ms）的四個做法

| 做法 | 內容 | 對應 |
|---|---|---|
| **P-1 最少上下文** | prompt 只帶：當前作業對象（三層識別的人話名稱）、**該段歷程的最後 K 則**（K 由設定、預設遠小於 200）、能力列舉清單。**不帶**完整 `messageHistory` | `BR6.1`／`NFR9.60`／`NFR9.61` |
| **P-2 單次合併請求** | 意圖分類、槽位拆解、指涉詞解析**在同一個 tool schema 內一起回**，不拆成三次呼叫 | `BR6.2`／`NFR3.62` |
| **P-3 輸出長度上界** | tool schema 對 `candidates` 設 `maxItems`（建議 8）、對 `label` 設長度上界。輸出 token 數是延遲的直接因子 | `BR6.1`；Jev max completion 28800 遠高於所需 |
| **P-4 連線重用** | HTTP client 由模組層的 factory 建立一次並重用，**不是每輪新建**。這不違反 `NFR3.67`——它禁的是**可變狀態**，連線池是不可變的基礎設施 handle | `NFR3.67` 的界線在此釐清 |

> **P-4 需要一句話的界線說明**，因為 `NFR3.67` 的字面提到「連線池」。
> 該條禁的是「**把行程內共享可變狀態當成擴展手段**」（快取結果、計數器）。
> HTTP 連線重用不持有任何請求間的語意狀態，且每個 backend 行程各自一份——
> 它不是擴展手段，是不重複付 TLS 握手成本。**這條界線若被讀成禁止連線重用，
> 每輪會多一次 TLS 握手，直接吃掉 800 ms 預算的一部分。**

## 三、純函式層的效能：不在預算內，但有一個上界要寫下來

述詞 `can_single_out` 是純函式（`BR3.6`／`NFR3.65`）。它的成本是
`O(len(slots) × len(candidates))`，而兩者都有上界（槽位由輸入句子決定、
候選由 `maxItems` 上界 8）。**不設門檻，但設結構性上界**：

| 項目 | 上界 | 來源 |
|---|---|---|
| `len(candidates)` 每槽位 | **8**（schema `maxItems`） | P-3 |
| `len(slots)` | **4**（schema 層以 `slot` 的最大值驗證） | 本站新定，見下 |

**`len(slots)` 需要一個上界，理由是它缺了會變成一個攻擊面**：
`slot` 是模型填的整數，沒有上界時一個惡意或失控的回應可以宣告 1000 個槽位，
而 `U12` 會據此建 1000 個工作項。**「要有上界」是確定的；「取 4」不是**——

> **修訂 1（審查 `R-08`，Minor）：`4` 改列為待覆核的交接事項，不是已定案的數字。**
> 它的依據只是把 `FR5.1` 的唯一官方例子（2 個意圖）乘以一個我沒寫出來的安全係數，
> 而**超界的後果是整輪失敗、不是降級**——使用者一句話列五件事並不難想像
> （「幫我把這五個系統都加上監控、備份、擴容、告警跟成本分析」），屆時他得到的
> 既不是部分成功也不是反問，而是整輪失敗。**而沒有任何上游文件對「5 個意圖該怎麼辦」
> 表達過意見。** 本站把 `[D1]`（schema 形狀）升級為使用者問題，卻把同屬
> 「選錯會在 `code-generation` 才爆出來」性質的這一項放進自行定案清單——標準不一致。
> **處置**：`4` 為**暫定值**，承接 `U11` 的 `code-generation`（實作時以真實使用型態
> 覆核）與 `build-and-test`（標註集跑完後看槽位數分佈的實際尾端，`NFR3.73` 正是
> 為此而設）。比照 `D-3`／`D-4` 的交接事項格式，已列為 `D-7`。

暫定 4 的依據是 `FR5.1` 的官方例子是 2 個意圖；
**超過上界即走 `MalformedRouting` 的失敗路徑**（`reliability-design.md` §二 的
`V-3`）**，不是截斷**——截斷會靜默丟掉意圖，正是 `functional-design` 審查 `R-01`
查出的那個失敗模式。

> **修訂 1（審查 `R-04`，Major）：原文誤寫成「走 `BR2.4` 的失敗路徑」。**
> `BR2.4` 的逐字定義是「分類器回**空候選清單**」，與「`slot` 超出上界」是完全不同
> 的條件；而 `reliability-design.md` 的 `V-3` 自己已正確分類為 `MalformedRouting`。
> **這個誤引會直接污染 `NFR3.74` 的分型失敗率**——把「供應商吐出一個失控的大槽位數」
> 與「供應商真的吐空清單」計進同一條曲線，而分型正是本單元反覆強調的設計主軸
> （`reliability-design.md` §一：「四個型別、一種使用者體驗，但維運必須分得出來」）。
> **我在同一份產出的兩個檔案裡，對同一個檢查點指派了兩個不同的失敗型別。**

## 四、預算的歸因（承接 `nfr-requirements` 的兩個缺口）

`performance-requirements.md` 修訂 1 記下兩個歸因缺口，本站的設計面處置：

| 缺口 | 設計面處置 |
|---|---|
| 交接膠水時間無預算歸屬 | **本站在 `classify` 的進出點各打一個計時標記**，使「本單元耗時」可從端到端耗時中減出來。有了這兩個標記，膠水時間即使沒有預算，也**可被量測**——`U13` 的 `nfr-requirements` 要分配它時才有數字 |
| 輪詢型下游（C1）無「第一個 token」 | 不屬本單元。本站只確保本單元的標記存在，使該段可被單獨減出 |

**這是本站能做的全部**：預算分配是上游的事，但**可量測性**是設計決定，而它現在被設計進去了。

## 五、不做的事

| 不做 | 理由 |
|---|---|
| **不快取分類結果** | `classify` 非冪等（`BR8.1`），且同一句話在不同 session 的正確答案不同（指涉詞依賴該段作業對象）。快取鍵必須含整個上下文，命中率趨近零而失效風險真實 |
| **不預熱模型** | 無伺服器端 warm pool 可控；Jev 由 OpenRouter 託管 |
| **不做串流** | `K-10` 回傳 `IntentDecision` 是一次性結果，`U12` 要拿到完整的槽位集合才能交辦。串流一個結構化決策沒有消費者 |

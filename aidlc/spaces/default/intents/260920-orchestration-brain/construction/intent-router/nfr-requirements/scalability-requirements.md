# Scalability Requirements — `U11 intent-router`

> ID 帶 `.60+`。**本檔先講一件事**：inception 層**沒有**一條專講 scalability 的
> `NFR{n}`（`NFR1`–`NFR11` 逐條核對：準確率、上下文保留率、首字時間、狀態外部化、
> WS 契約閘門、記憶 schema、episodic 稽核、部署設定、成本原則、模型可替換性、
> 頁面切換次數——**沒有一條是負載或容量**）。本檔因此把需求錨在**最近的兩條**
> （`NFR3` 延遲在併發下的行為、`NFR9` 成本隨量成長）並**明說**這是錨定而非覆蓋，
> 不替 inception 發明一條新的 `NFR`。

## 本單元的擴展性形狀：無狀態，所以它不是瓶頸

| 性質 | 事實 | 依據 |
|---|---|---|
| **無狀態** | `classify` 每次呼叫自成一輪，本單元不持有任何跨輪狀態；`ClassificationResult` 隨該輪結束消失 | `functional-spec.md` §二「本單元不持有這個狀態」；`BR8.1` |
| **水平擴展隨 backend 走** | 本單元是 `in-process` 的（`K-10`），沒有自己的部署單位。加 backend 行程即加路由容量 | `K-10` 的 `in-process` 宣告 |
| **真正的上界在外部** | 併發上界由 **OpenRouter 的速率限制**與 **Jev 的 context 32000／max completion 28800** 決定，不由本單元的程式碼決定 | 問題檔 V4c（實測中繼資料） |

**結論：本單元沒有可由自己解決的擴展瓶頸。** 這不是「不適用」——它是一個需要
被寫下來的事實，因為它決定了容量規劃該看哪裡（看模型供應商，不看本單元）。

## 容量規劃：本站能說的與不能說的

**能說的**：

- 本單元的 CPU 成本可忽略——述詞是純函式（`BR3.6`），對 ≤ N 槽位 × ≤ M 候選做常數級比較。
- 記憶體成本可忽略——無狀態、無快取（`NFR3.67`）。
- 每輪**恰好 1 次**出站呼叫（`NFR3.62`），所以「每秒請求數」直接等於「每秒模型呼叫數」。這讓容量推算變成一道除法，而不是一個模型。

**不能說的（刻意不填，因為填了就是編造）**：

- **目標併發數**。inception 沒有給使用者規模，本 intent 也沒有任何一條需求提到
  同時上線人數。`NFR1` 的量測母體是 ≥50 筆**標註集**（離線），不是線上併發。
  本站**不自行設定**一個併發目標——那會變成一個沒有依據的數字，而
  `requirements.md:400-428` 的校正程序正是為了治這種數字而存在。
- **OpenRouter 對本帳戶的實際速率限制**。無金鑰、未實測（問題檔 V4g）。

**承接**：併發目標與供應商速率限制的實測同屬 **`build-and-test`（3.6，`ALWAYS`）**
——與 `OQ-10`（`[N3]`=A）、`NFR1` 的準確率量測、`NFR3` 的延遲量測同站同批。
這不是四個分開的指派，是同一次實測的四個讀數。

## 預算切分的算式（這是本站做的唯一一次分配）

```
NFR3 的端到端預算            P50 ≤ 2000 ms
  ├─ 路由層（本單元）         P50 ≤  800 ms   ← NFR3.60（本站定）
  └─ 下游能力 agent 首字       P50 ≤ 1200 ms   ← 本站不擁有，記為對下游的預算宣告
```

**為什麼路由層拿比較少的那一半**：使用者等的是**內容**，不是分類。下游是實際
產出內容的那一段，把它壓到 800 ms 而讓分類拿 1200 ms（`[N2]` 的選項 B）是與
使用者感知相反的分配。

**為什麼硬逾時取 5 秒而不是 2 秒**：2 秒是 **P50 目標**，5 秒是**尾端切斷點**。
取 5 秒讓「慢但會回」與「壞掉」在紀錄上可區分；使用者在 2 秒後看到的是等待指示，
不是錯誤訊息。取 2 秒會把一次正常的長尾變成一次假故障。

**為什麼重試 0 次**：`classify` **非冪等**（`BR8.1`，`K-10` 逐字），而重試會把
P50 預算直接翻倍。這條路徑上重試的代價高於它的收益——使用者寧願看到「請再說一次」
也不願意等兩倍時間拿到一個可能不同的答案。

## 預算切分的兩個歸因缺口（修訂 1，審查 `R-05`，Major）

審查正確指出 `800 + 1200 = 2000` 這個算式**至少有兩段時間沒有被分配到**。兩項皆已複驗：

### 缺口一：交接膠水時間懸在兩個預算之間

`NFR3.60` 的量測邊界是「**進入 `classify` → 回傳 `IntentDecision`**」，而 `NFR3` 的
量測邊界是「**送出 → WebSocket 收到第一個內容 token**」。兩者之間還有：

- `U13` 收到 WS 訊息 → 呼叫 `classify` 之前的處理（解包、session 載入、授權）
- `classify` 回傳 → `U13` 轉交 `U12`
- `U12` 建立工作項 → 分派到實際能力 agent

這三段**既不在本單元的 800 ms 內**（它們不在 `classify` 裡），**也不在下游的
1200 ms 內**（本檔自陳那是「對下游能力 agent 首字」的宣告）。它懸著。

**處置**：本站**不自行把它劃給誰**——`U13` 與 `U12` 的設計站尚未跑到，憑推論
替它們分配預算會是上游替下游做決定。本檔把它**列為第三段**並指派：

| 段 | 預算 | 擁有者 |
|---|---|---|
| 路由層 `classify` | P50 ≤ 800 ms | **本單元**（`NFR3.60`） |
| 交接膠水（`U13` 解包／授權 → `U12` 建項 → 分派） | **未分配** | **`U13` 的 `nfr-requirements`**（3.2，`CONDITIONAL`；轉移目標 `U13` 的 `code-generation`，3.5，`ALWAYS`） |
| 下游能力 agent 首字 | P50 ≤ 1200 ms（含上一段時即為 1200 ms 減去它） | 各能力自身 |

### 缺口二：至少一個已核可的下游**結構上不產生 token**

`contract-summary.md:1128-1131` 的 `x-streaming-rule` 逐字：「**不得對成本做 token
級巢狀串流轉送**」「C1 的『串流』是**每秒輪詢 DB 的狀態事件**，真正的 LLM 呼叫是
同步 invoke——來源端沒有逐字可轉」。

亦即對 C1 這條路徑，使用者看到的第一個「內容」在架構上就有 **0–1000 ms 的輪詢
粒度延遲**，與 Jev 或 C1 的實際運算時間無關。**1200 ms 的下游預算假設的是一個
能產出「第一個 token」的串流下游，而 C1 不是。**

**處置**：對輪詢型下游，「首字」必須重新定義為**第一個 `progress` 事件抵達 WS 的
時刻**。本檔記下這個等價定義的需求，實際定義落 `build-and-test` 設計量測點時。

### 為什麼這兩項重要：它們決定了預算切分有沒有診斷力

不補這兩項，`build-and-test` 會出現一個**無法歸因**的結果：
`NFR3.60`（本單元 800 ms）標 `Met`，而端到端的 `NFR3` 標 `Not Met`，
中間沒有任何一列能解釋差額跑到哪裡去了。**預算切分的價值就在歸因**，
沒有歸因力的切分等於沒切。

## 量測機制的落點

全部落 **`build-and-test`（3.6，`ALWAYS`）**，與 `NFR1`／`NFR2`／`NFR3` 的量測
機制同站。這不是本站推諉：`NFR3` 自己逐字把量測機制指派給那一站，而本站定的是
**目標值**。

## 未達標時的處置

四個數值全部納入 `requirements.md:400-428` 的**共用校正程序**：首次實測未達標時
**不自動改寫門檻**，由決策者在 `build-and-test` 的核可關卡三選一（接受實測值為新
門檻／維持原值要求改善後重測／判定門檻設錯並重定）。**連動條款同樣適用**：
`NFR3.60` 若因換模型而調整，必須同時檢視 `NFR1` 的 80% 與 `FR1.7` 的 0.7。

## [N1] `OQ-4` ＋ `OQ-10` 合併定案：路由層用什麼模型，信心值從哪裡來

**這兩題必須一起答**（`requirements.md:791` 逐字「須與 `OQ-4` 的模型定案一併決定，
不得分開處理」），因為「能不能產出可比較的信心值」是模型能力問題。

### 選項

- **A（建議）— `google/gemini-3.7-flash` ＋ 結構化輸出的「模型自評分數」，並明記它未校準。**
  沿用 V1 的既有預設模型（零新依賴、零成本意外），分類請求要求模型回一段
  JSON：候選清單 ＋ 每個候選的 `score`（0–1）。`scoresAvailable = true`，
  `BR3.2`（最高分 ≥ 門檻）成為主要求值分支。
  - **誠實的限制**：這個分數是**模型自己報的，不是校準過的機率**。它可比較
    （同一次呼叫內的相對高低有意義），但它的絕對值不等於「正確的機率」。
    產出必須逐字寫明這一點，否則下游會把 0.7 當成「七成會對」。
  - **`BR3.3` 仍然保留**：模型漏給分數、或只給部分候選分數時（`EC2` 規定整張
    清單視為無分數），自動落到無分數分支。這是 `[IR1]`=A 的直接收益。
  - **0.7 的處置**：維持為**初版設定值**，依 V6 的校正程序在 `build-and-test`
    以 ≥50 筆標註集實測後裁決，且**與 NFR1 的 80% 連動調整**。
  - **代價**：V3 顯示 repo 零結構化輸出前例，本單元會是第一個；
    需要一條「模型回了不合格 JSON」的失敗路徑（落到 `BR2.4`：分類失敗，不是反問）。
- **B — 同一個模型，但**不取分數**，只要排序。**
  `scoresAvailable` **恆為 false**，`BR3.3`（第一名與第二名不並列）成為唯一求值
  分支，`FR1.7` 的 0.7 **正式不適用**（`FR1.6` 自己的替代表達逐字允許）。
  - **好處**：不必假裝有一個未校準的數字是「信心值」；少一條 JSON 解析失敗路徑。
  - **代價**：**`FR1.6` 這條 Must 等於被判定不成立**，`AC1.2.4`（「帶有定義域
    0–1 的信心值可與門檻比較」）必須改寫；`NFR1` 的校正程序失去「調門檻」這個
    旋鈕（只剩換模型或改 prompt）。而「並列」本身也要有判準——模型只給排序時，
    「第一名與第二名是否並列」同樣得由模型宣告，問題只是換個名字。
- **C — 採上游候選 `typesafe/jev-1.13`。**
  - **本站無法負責任地選它**：V4 顯示它在 repo 零命中，而本站**沒有**它在
    OpenRouter 上的可用性、延遲或計價的任何實測。`NFR10` 自己逐字要求
    「**在有實測準確率與延遲基準後**決定」——那個基準不存在。
  - 若選此項，誠實的處置是把它記成**待實測項**而非定案，實質等於再往下游推一站。
- **D — 用 `logprobs` 取真實 token 機率當信心值。**
  - 這會是**唯一有校準意義**的來源，但 V3 顯示 repo 零前例，且**本站未查證**
    OpenRouter 對 Gemini 系列是否回傳 `logprobs`。選它等於把本題換成一個
    技術試探，而試探沒有承接站。

## [N2] 路由層的延遲預算、逾時與重試上限（`N-18` 的數值）

V9 把這三個數值明文指派給本站。V5 的 **P50 ≤ 2 秒**是整條鏈的預算，而路由層是
**第一段**——使用者看到的第一個字在分類完成**之後**才會出現，所以路由層的耗時
是 `NFR3` 的直接扣項。V2 的現行預設 **60 秒逾時**是該預算的 **30 倍**，對這條
路徑而言等同沒有逾時。

### 選項

- **A（建議）— 路由層 P50 ≤ 800 ms、硬逾時 5 秒、每輪最多 1 次模型呼叫、重試 0 次。**
  - **800 ms**：留 1.2 秒給下游能力 agent 產出第一個 token，兩段相加符合 `NFR3`。
  - **硬逾時 5 秒**：超過即 `LlmUnavailable`（`BR8.2`：大聲失敗，不降級猜測）。
    取 5 秒而非 2 秒，是為了讓「慢但會回」與「壞掉」在紀錄上可區分；
    使用者在 2 秒後看到的是等待指示，不是錯誤。
  - **重試 0 次**：沿用 V2 的 `max_retries=0`。分類非冪等（`BR8.1`），
    而重試會把 P50 預算直接翻倍——這條路徑上重試的代價高於它的收益。
  - **每輪 1 次呼叫**：`BR6.2`（互不相依的判斷合併為一次請求）在本單元的具體值。
  - 四個數值**全部可設定**（`BR6.3`），且全部屬 V6 的校正程序涵蓋範圍。
- **B — P50 ≤ 1200 ms、硬逾時 10 秒、重試 1 次。**
  對模型更寬容，但把下游 agent 的首字預算壓到 800 ms，而下游是實際產內容的那一段
  ——這個分配方向與「使用者感知」相反。重試 1 次在逾時情境下使最壞情況達 20 秒。
- **C — 不設子預算，只設逾時，實測後再分配。**
  `NFR3` 仍可量測（它是端到端的），但「超標時該怪哪一段」沒有依據，
  而 V5 已經指出路由層是主要扣項。等於把一個已知的分配問題留到事後。
- **D — 路由層 P50 ≤ 500 ms、硬逾時 3 秒。**
  最保守的使用者體驗，但 500 ms 對一次需要產出結構化 JSON 的模型呼叫而言，
  以現行 `gemini-3.7-flash` 多半達不到——會讓 `NFR3` 在第一次實測就紅燈，
  而紅的原因是預算切得太細，不是系統慢。

[Answer]: A（P50 ≤ 800 ms、硬逾時 5 秒、每輪 1 次呼叫、重試 0 次）

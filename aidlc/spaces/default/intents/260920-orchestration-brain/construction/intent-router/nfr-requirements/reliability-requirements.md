# Reliability Requirements — `U11 intent-router`

> ID 帶 `.60+`。

## 本單元的可靠性形狀：**失敗是正常的，猜測不是**

本單元依賴一個**外部、付費、非冪等**的第三方模型。它的可靠性設計只有一條主軸：
**把「不知道」如實往上傳，而不是把它變成一個看起來正常的錯誤答案。**

`functional-spec.md` 的 `W8` 第 3 步逐字記下要防的最壞版本：降級猜測**比交辦錯誤
更糟**——使用者連候選都看不到，無從察覺系統其實不知道。

## 刻意不做的兩件事，與理由

### 不設 circuit breaker

`nfr-design-guide.md` 把 circuit breaker 列為「外部服務呼叫」的預設模式。本站
**不採用**，理由是三項已定參數讓它沒有保護對象：

- **重試 0 次**（`NFR3.63`）——circuit breaker 要防的「重試風暴」不存在。
- **硬逾時 5 秒**（`NFR3.61`）——「快速失敗」已由逾時達成，不需要斷路器代勞。
- **每輪 1 次呼叫**（`NFR3.62`）——單一請求不會自己放大。

剩下的唯一收益是真實的：**供應商系統性故障時，不要讓每一個請求都各自等滿 5 秒**。
本站選擇**這一輪不做**，並把它交給共用的出站層（`langgraph_runtime`）評估。

> **修訂 1（審查 `R-04`，Major）：原本這一段用了一個不成立的論證，已刪除。**
> 原文寫「加一個斷路器就等於加回行程內狀態，與 `NFR3.67` 直接衝突」。
> **那是錯的**——`NFR3.67` 是本檔自己定義的，它逐字只禁止「**行程內**的共享可變
> 狀態」，並**明文開放**「需要跨行程共享的狀態一律走 `U10` 的 Redis」。斷路器的
> 失敗計數與半開時鐘完全可以放 Redis，那正是 `NFR3.67` 自己給的逃生門。
> 寫成「直接衝突」會讓實作者以為斷路器在架構上不可能，而真正的理由只是
> 「這一輪不在本單元做」。**誠實的版本是：三項已定參數讓它的收益變小，剩下的
> 那一項收益存在但不夠大到值得本單元引入 Redis 依賴（本單元目前對 `U10` 只有
> 唯讀的 `SessionContext` 依賴，加斷路器會讓它多一個寫入方向）。**

### 不設 fallback 模型

`[N1]`=C 定案單一模型。「Jev 掛掉就改用 gemini」聽起來便宜，但它會讓
**`NFR1` 的準確率量測失去母體**——同一組標註集跑在兩個模型上得到的數字不可合併，
而使用者不會知道自己這一次是哪個模型判的。`NFR10` 要的是**可替換**（設定值換得掉），
不是**自動切換**。可替換性落為 `tech-stack-decisions.md` 的 `TS-2`。

## 降級路徑：本單元有且只有一條

```
模型失敗 ──▶ raise ──▶ U13 以 error 事件終止該輪 ──▶ 使用者看到「請再說一次」
```

**沒有第二條**。特別是：不以 `prompt_guard` 的固定拒絕訊息當作降級出口——
那條路徑的終止事件是 `done` 而非 `error`（`BR1.3`），把失敗塞進去會讓
「系統正確地拒絕」與「系統壞了」在畫面上長得一樣。

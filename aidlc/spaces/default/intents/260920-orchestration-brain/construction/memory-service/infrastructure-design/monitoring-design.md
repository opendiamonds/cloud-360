# 監控設計 — `U8 memory-service`

> 本 repo 的可觀測性現況已由 `U9` 逐一查證：**有 logs、無 metrics、無 traces**，
> 告警的唯一既有管道是 GitHub Issues。本檔**不發明不存在的承載機制**。
>
> 本單元零新基礎設施，故本檔談的是**既有日誌管道要承載什麼**
> ——而 `[D1]`=A 讓其中一項從「稽核義務」升格為「唯一的偵測面」。

## 一、四支柱現況（沿用 `U9` 的查證，不重新推導）

| 支柱 | 現況 | 本單元能做什麼 |
|---|---|---|
| **Logs** | 有：stdout → 容器日誌 | 全部的可觀測性都落在這裡 |
| **Metrics** | **無** | 無承載機制 |

## 二、本單元要求既有日誌管道承載的四件事

| id | 內容 | 落點 |
|---|---|---|
| `NFR7.30` | 每次授權拒絕留一筆結構化日誌（principal、`memoryId`、`reason`） | `MemoryFacade` |
| `NFR7.31` | 日誌**不得含** `content`、`embedding`、整個模型物件 | 全部四層 |

**全部以既有 logger 承載**（`logging.getLogger("cloud360.memory_<layer>")`），
零新 logging 基礎設施、零新轉送、零新保留規則。

## 三、`[D1]`=A 之後，日誌是枚舉偵測的唯一面

刪除路徑的對外回應收斂為 404 之後：

| 情境 | 對外 | 日誌 |
|---|---|---|
| 擁有者誤刪已刪除的記憶 | 404 | **不含** `reason="owner"` |
| 非擁有者探測存在的記憶 | 404 | **含** `reason="owner"` |

**故 `NFR7.30` 不再只是稽核義務。** 若日誌也收斂，枚舉行為完全不可見
——而那正是 `[D1]`=A 要防的攻擊。

### 3.1 偵測判準已寫下，但**本單元不建它**

| 判準 | 單一 principal 在短時間內大量產生帶 `reason="owner"` 的 404 |
|---|---|
| 需要什麼 | 日誌聚合與時間窗計數 |
| repo 有嗎 | **沒有**（無 metrics、無日誌聚合） |
| 本單元的處置 | **只保證資料在日誌裡**，不建偵測。判準寫下來使它日後可被實作而不需重新推導 |

**這是誠實的限定而非藉口**：`[D1]`=A 關閉了 oracle（枚舉者再也拿不到答案），
所以偵測是「想知道有人試過」而非「阻止它」。
前者缺席不會讓資料洩漏，故不阻擋本輪。記為 `I8-1`。

## 四、Metrics、SLI/SLO、Alerts：皆無，理由具體

| SLI | SLO | 窗口 |
|---|---|---|
| — | — | — |

**無 SLO**（承 `nfr-requirements` 的三項理由）：

1. **沒有 metrics 承載機制**——在沒有時間序列儲存的情況下宣告百分位 SLO，
   等於宣告一個沒有人會量的數字；
2. `NFR3.20`／`NFR3.23` 是**一次性量測的需求**（落點 `build-and-test`），
   不是持續量測的誤差預算；
3. 本單元不是獨立服務，沒有可用性面。

**不新增告警**：本單元的失敗模式是請求層級的（403／404／500），
由呼叫端立即看到；沒有「什麼都沒發生」那種需要外部偵測的失敗
——**那是 `U9` 的情形（排程漏跑），不是本單元的**。

**候選 SLI（待承載機制）**：`search` 延遲百分位、授權拒絕率、
帶 `reason="owner"` 的 404 率。

**`N8-10` 的出處（承審查 `R-03`）**：定義在
`nfr-requirements/observability-requirements.md §二`（逐字「候選 SLI 是
`search` 的延遲百分位與授權拒絕率，但那需要先有承載機制。記為 `N8-10`」），
並由 `nfr-design/observability-design.md §五` 承接。
**它是本單元自己開的待追蹤項，不是更早 intent 的 id**；
審查認為它「查無出處」是因為本檔初稿只寫了 id 而沒給檔案與章節
——缺的是引用，不是定義。
**承接狀態如實記載**：它**沒有承接站**——引入 metrics 管線屬獨立的
基礎設施決策，本 intent 的 24 個單元沒有一個擁有它。

## 五、本單元監控不到的三件事（如實記載）

| # | 內容 | 為什麼 |
|---|---|---|
| 1 | **HNSW 索引是否真的被使用** | 只有 `S14` 的 `EXPLAIN` 斷言在 CI 檢查；**生產環境無持續監看**。索引失效（誤刪、opclass 改錯）的表現是效能退化而非錯誤，而本 repo 無延遲 metrics |
| 2 | **檢索結果的品質**（是否回了「對」的記憶） | 無相關性量測機制。`NFR7.34` 只能區分「空結果的三種成因」，不能判斷非空結果好不好 |
| 3 | **跨單元的因果關聯** | `U11` 經同進程 facade 呼叫 `search` 時，該次檢索的日誌與觸發它的對話無法關聯（`D8-6`，承接 `U13`） |

**第 1 項值得特別記**：`[N2]`=B 的整個理由是效能，
而效能退化在本 repo **沒有任何偵測面**。
索引的價值因此完全依賴 CI 的 `S14` 斷言——若它被移除或改弱，
生產環境不會有任何跡象。記為 `I8-2`。

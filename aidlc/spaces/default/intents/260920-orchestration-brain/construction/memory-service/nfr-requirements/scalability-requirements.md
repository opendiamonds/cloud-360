# 擴充性需求 — `U8 memory-service`

> 本單元**不新增任何進程或容器**：它是既有 FastAPI 進程內的
> router → service → facade 三層。故本檔談的不是「怎麼擴容」，
> 而是**資料成長**與**候選集合大小**這兩個會隨使用量變化的量。

## 〇、上游依據

| 上游 | 本檔用到它的什麼 |
|---|---|
| `requirements.md` `NFR7` | 90 天保存期——它是本單元資料成長的**唯一上界機制** |
| `functional-design/rules.md` | `BR7.1`（每輪對話一筆 episodic）、`BR7.2`（每個工作項一筆 procedure）、`BR7.3`（semantic 手動） |
| `memory-purge/`（`U9`，已交付） | 清除的實際承載形式與其漏跑偵測（`NFR7.13`） |

## 一、擴充性需求

| id | 需求 | 二元判準 | 來源 |
|---|---|---|---|
| **`NFR7.27`** | `memory_records` 的成長必須有**可運作的**上界機制，且該機制漏跑時可被偵測 | `U9` 的清除 workflow 存在且其 watchdog 存在（**已交付**）；本單元不新增機制，只宣告依賴它 | `NFR7`；`U9` 的 `NFR7.13` |
| **`NFR7.28`** | 列出路徑必須分頁，不得一次回傳某使用者的全部記憶 | `GET /api/memory/records` 接受分頁參數且有預設上限；回應不隨列數線性成長 | 本站（見 §二） |
| **`NFR7.29`** | 檢索的 `limit` 必須有**伺服器端上限**，呼叫端指定超過時收斂到該上限而非照辦 | 以超大 `limit` 呼叫 `search`，回傳筆數不超過伺服器上限 | 本站；`K-08` 的 `search` 簽名含 `limit: int` |

## 二、`NFR7.28` 的理由：本單元有一條沒有上界的讀取路徑

`K-08` 的 `search` 帶 `limit` 參數，**但列出路徑（`GET /api/memory/records`）
在契約裡沒有任何分頁宣告**——它的 summary 逐字只有
「列出當前使用者可見的記憶（三種 kind 分區）」。

| 事實 | 後果 |
|---|---|
| `BR7.1` 讓 `U13` 每輪對話寫一筆 episodic | 單一使用者 90 天內的 episodic 列數隨使用量線性成長 |
| 列出路徑無分頁 | 回應大小與該使用者的列數成正比，且 `content` 是 `TEXT` |
| `U15` 的記憶頁三區 | 三區同時載入 → 單次回應可能很大 |

**repo 內已有分頁先例**：`/api/auth/list` 有分頁（`U19` 的
`test_user_list_endpoint.py` 即測它的分頁欄位）。照該形狀即可，不需新機制。

**本站不改 `K-08` 的契約**（那是已核可產出），而是把分頁列為本單元的需求並
記為交接 `N8-8`：`code-generation` 實作時必須加分頁，而該變更會讓
`openapi.json` 與 `K-08` 的 OpenAPI 半邊產生落差——後者需在下一輪契約修訂追認。

## 三、不適用的擴充性面向（逐項附理由，不留空白）

| 面向 | 判定 |
|---|---|
| 水平擴充／自動擴縮 | **N/A**：本單元在既有單一 FastAPI 進程內，本 intent 不引入多實例。整個 repo 的部署模型是單主機 compose（ADR-0007） |
| 連線池 | **N/A，且刻意不動**：沿用 `database.py` 既有的 engine 與其池設定。本單元新增的是查詢而非連線來源 |
| 分割／分片 | **N/A**：90 天保存期使單表規模有上界；在本輪的使用量下無分割需求，且分割屬 `U5` 的 schema 範圍 |
| 快取 | **N/A 且刻意不加**：記憶的讀取受擁有者與可見範圍約束（`BR2.2`），而快取一個**按呼叫者過濾**的結果集需要把 principal 納入快取鍵，容易做成跨使用者洩漏。本輪不引入 |

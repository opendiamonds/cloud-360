# 可靠性設計 — `U8 memory-service`

> 本單元不是獨立服務，沒有自己的可用性面。本檔設計的是
> **交易邊界**、**失敗時的行為**、以及**為什麼刻意不加韌性 pattern**。

## 一、交易邊界設計（`NFR4.21`）

**兩個操作各自是一個交易，且稽核與資料變更不可分離。**

| 操作 | 交易內容 | 不可拆的理由 |
|---|---|---|
| `delete` | 寫 `deleted_by_user` 稽核 ＋ 刪除記憶列 | 拆開會產生「記憶沒了但沒稽核」，直接違反 `FR4.7`，且**事後無法補救**（已經不知道刪了什麼） |
| `widen_scope` | 更新 `visibilityScope` ＋ 寫 `scope_changed` 稽核（帶前後值） | 拆開會產生「範圍改了但沒紀錄誰改的」，而 `AC4.3.1` 正是要答這個問題 |

**實作形式**：以單一 SQLAlchemy 交易包住兩個敘述；任一失敗則整個交易回滾。
**不以兩次 `commit()` 實作**——那正是上面兩列要防的事。

**與 `U9` 的同一條紀律**：`U9` 的清除以 data-modifying CTE 把稽核與刪除綁成
一個敘述。本單元**不需要走到 CTE**，因為它一次只處理一列、
且稽核列的 `memoryId` 來自請求參數而非 `RETURNING`——
單一交易內兩個敘述已足夠。寫下這個差異以免被讀成不一致。

## 二、`write` 的失敗設計（`NFR4.22`）

| 步 | 失敗時 |
|---|---|
| 取向量（`U6`） | 拋 `EmbeddingProviderUnavailable`，**列尚未建立**，故失敗不留痕跡 |
| 建立列 | 交易回滾 |

**取向量在建立列之前是刻意的**（`functional-spec.md §1.1` 的步 5–6 在步 7 之前）：
反過來會留下一列沒有向量、且無人知道該不該重試的記憶。

**提供者不可用時不得降級**（`BR3.5`）：靜默改用 fulltext 會讓整批記憶
以錯的提供者寫入，之後因 `BR3.2` 的分群**永久不可被檢索到**。
故錯誤必須含提供者名與可選值（`NFR7.32`）。

## 三、刻意不加的韌性 pattern（`NFR4.23`）

| pattern | 為什麼不加 |
|---|---|
| **retry／backoff** | `write` **非冪等**（`K-08` 逐字）——重試會在一次網路抖動後留下兩筆一樣的記憶，而使用者看不出哪一筆是多的。`search` 唯讀冪等，重試由呼叫端決定 |
| **circuit breaker** | 本單元的依賴是同一主機的資料庫與 `U6`。資料庫失敗的正確反應是讓請求失敗；`U6` 的失敗行為已由 `BR3.5` 定為大聲失敗 |
| **fallback／降級** | `BR3.5` 明文禁止（見 §二） |
| **bulkhead** | 無多實例、無執行緒池可隔離 |

`nfr-design-guide.md` 的這些 pattern 是為「呼叫會失敗的外部依賴」而設。
**本單元沒有那種依賴。**

## 四、`NFR4.20`：無行程內狀態

| 設計 | 本單元新增的四個模組中**不得有模組層可變容器**（dict／list／set）承載跨請求狀態 |
|---|---|
| 為什麼需要明說 | repo 內有**三處既有行程內狀態容器**（`collab_router` 的連線字典、`advice_orchestrator` 的 `_executor`／`_progress`／`_inflight`、`pricing_client` 的磁碟快取），而 `NFR4` 明確把它們排除在本 intent 之外。**本單元不得照抄那個形狀** |
| 判準 | 重啟後查詢結果不變；且新增模組的模組層無可變容器 |

## 五、健康檢查與備份

| 項目 | 設計 |
|---|---|
| 健康檢查 | **不新增**——本單元在既有 FastAPI 進程內，沿用既有的健康檢查 |
| 資料耐久性 | 完全依賴既有 PostgreSQL 的備份策略 |
| **誠實記載** | **本站查不到任何備份需求或機制的記載**（`N8-9`）。「90 天的個人對話歷程沒有已記載的備份策略」是一個事實；它不屬本單元（部署面），但不應該被這份設計的沉默掩蓋 |

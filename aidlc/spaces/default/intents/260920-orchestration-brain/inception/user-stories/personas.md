## 來源與邊界

`stakeholder-map.md`（intent-capture，已核可）確認 **4 類**關係人，本檔不增不減。
每一則故事都必須引用下列其中一個 persona；若某則故事對不上任何一個，
依 `product-guide.md` 的判準，**不是故事錯就是 persona 少了一個**——而 persona
清單已由 `[Q2]` 鎖定，故那種情況一律當成故事寫錯。

「關注的事」逐字取自 `[Q2]` 所選選項，未另行擴寫（`stakeholder-map.md` 亦如此
聲明）。「技術熟練度」與「使用頻率」兩欄**是本站新增的推斷**，上游未確認，
故逐欄標記 `[assumption]`——它們只用於幫助判斷 AC 的措辭深度，不用於支撐任何
需求主張。

## P-1 架構設計者（直接服務）

| 欄位 | 內容 |
|---|---|
| **角色** | 在架構圖工作區畫圖、改圖的人 |
| **關注的事** | 「在架構圖工作區畫圖、改圖；需求從對話變成圖的過程要反覆切換工具與頁面」[Q2] |
| **第一版定位** | **直接服務**；共享工作階段涵蓋其使用的頁面（入口頁 ＋ `/workspace`）[Q2][Q7] |
| **目標** | (1) 把一句需求變成一張圖，不必自己決定該去哪一頁；(2) 改圖時不必重講作業對象；(3) 一個需求需要多個功能接力時，系統自己拆 |
| **痛點** | 目前 `/workspace`（A1 產圖）是獨立入口，換到 `/assessment` 或 `/cost` 後脈絡斷掉，要重講一次 [Q1] |
| **技術熟練度** | 高——熟悉 drawio 與雲端服務命名 `[assumption]` |
| **使用頻率** | 高，是本 intent 最主要的使用者 `[assumption]` |
| **對應能力** | 1、2、3、5、6、8、9（Must 的主要消費者） |

## P-2 評估／稽核者（直接服務）

| 欄位 | 內容 |
|---|---|
| **角色** | 使用 Well-Architected 檢視的人 |
| **關注的事** | 「使用 Well-Architected 檢視；看完結果後要自己把發現帶回架構圖或成本討論」[Q2] |
| **第一版定位** | **直接服務**；共享工作階段涵蓋其使用的頁面（入口頁 ＋ `/assessment`）[Q2][Q7] |
| **目標** | (1) 看完檢視結果後，帶著同一個對象直接回到架構圖或問成本，不重講；(2) 讓「發現 → 改動」之間不再是手動搬運 |
| **痛點** | 檢視結果與後續動作之間沒有任何連結機制，全靠自己記住在看哪個系統 [Q1] |
| **技術熟練度** | 高——熟悉 WA 六大支柱與既有 Lens 規則 `[assumption]` |
| **使用頻率** | 中，評核是週期性活動而非每日 `[assumption]` |
| **對應能力** | 1、2、6、8；能力 9 提供其「指得出是哪個系統」的基礎 |
| **重要邊界** | 其目標 (2)「讓『發現 → 改動』之間不再是手動搬運」在本 intent **只被滿足一半**：共享脈絡讓他帶著同一個對象換頁（`US2.2`），但**把某條 WA 發現轉成一次架構圖改動**並非本 intent 的能力——那要 A3 與 A1 之間的內容層整合，不在 `[Q9]` 確認的 10 項能力內。如實記載，比照 `P-3` 的邊界處理（設計師建議） |

## P-3 成本／FinOps 關注者（直接服務）

| 欄位 | 內容 |
|---|---|
| **角色** | 關心系統花多少錢、跨雲怎麼比的人 |
| **關注的事** | 「想問『這個系統花多少、跨雲怎麼比』」[Q2] |
| **第一版定位** | **直接服務**；其成本問題由統一入口辨識後交給**既有的**成本／FinOps 能力回答，答案**就地在入口頁呈現**，不需離開入口頁 [Q2][Q12][Q14] |
| **目標** | (1) 在入口頁問一句就得到成本答案；(2) 答案有結構、能點進去看完整分析 |
| **痛點** | 目前得自己走到 `/cost` 頁、自己知道要看哪個 estimate set [Q1] |
| **技術熟練度** | 中——熟悉計價概念，未必熟悉架構圖 `[assumption]` |
| **使用頻率** | 中低，多為特定時點的查詢 `[assumption]` |
| **對應能力** | 1、10、8；**不含**能力 2 的 `/cost` 頁共享（`/cost` 不在共享範圍，`[Q7]`／`[Q14]`） |
| **重要邊界** | 本 intent **不新建**成本計算，也**不納入**「跨雲分析（by 專案）」[Q12]——因此「跨雲怎麼比」這半個關注點在第一版**不被滿足**，如實記載 |

## Persona 優先順序

依 `[Q2]` 的定位與 `intent-backlog.md` 的交付序：

1. **P-1 架構設計者** — 消費最多 Must 能力，且是交付序前段（階層、意圖識別、串流）的主要受益者
2. **P-2 評估／稽核者** — 與 P-1 共用同一組能力，差別在進入路徑
3. **P-3 成本／FinOps 關注者** — 其能力（10）在交付序第 9 位
4. **P-4 管理者／平台維運者** — 間接服務；主要落點是能力 4 的稽核面，另出現在 `US1.4` 與 `US4.5`（本站修訂 1 更正，原寫「僅一項能力的一個面向」）

此排序**不是** MVP 邊界。MVP 邊界由 `delivery-planning`（2.9）決定；本排序只表達
「若必須取捨，哪個 persona 的體驗先被滿足」。

## Assumptions & Open Questions

- 四類 persona 為**角色**，非具名個人；每個角色實際對應哪些人、共有多少人，
  上游未確認（`stakeholder-map.md` 已如此聲明）[assumption]
- 每個 persona 的「技術熟練度」與「使用頻率」兩欄為本站推斷，上游未確認；
  僅用於判斷 AC 的措辭深度 [assumption]
- P-4 在哪一個後續階段會變成直接服務對象，上游未確認 [assumption]
- P-3 的「跨雲怎麼比」在第一版不被滿足（`[Q12]` 明確不納入跨雲分析）。
  這不是缺口而是已核可的範圍決定，但它意味著 P-3 的關注點只有一半被覆蓋 [assumption]

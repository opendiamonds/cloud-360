## 讀法與來源標籤

**AC 的紀律**：每一條 AC 描述**系統行為**，必須能真的失敗。本檔**沒有**
「Then 存在某某測試」形式的 AC——那種 AC 驗的是有沒有寫測試，不是功能對不對；
測試義務寫在各群的 Definition of Done。

**優先度**沿用 `scope-document.md`，本站不重新分級。`Could`／`Won't Have` 兩類
為空（`[S5]`＝A）——本檔若出現任一則，即代表本站擅自擴大或排除了範圍。

## US1 — 統一入口的意圖識別與工作交辦（能力 1，**Must**）

`[US:U4]`＝A 定案拆四則。四則各自對應線框的不同節，AC 各 3–5 條。

### US1.1 說出需求就被交辦

**身為** 架構設計者 `[P-1]`，**我想要** 在入口頁說出一句需求就被交給對的功能，
**以便** 不必自己先判斷該去哪一頁。`[FR1.1][FR1.2][FR1.5][Q1]`

| AC | Given / When / Then |
|---|---|
| **AC1.1.1** | **Given** 我在入口頁且脈絡列已指向一個系統，**When** 我輸入「把付款服務的架構圖加一個 Redis 快取」，**Then** 畫面出現一個工作項，標示它被交給架構設計能力，且狀態為 `處理中` |
| **AC1.1.2** | **Given** 工作項已建立，**When** 我查看它，**Then** 它的狀態是 `處理中`／`等待中`／`完成`／`失敗`／`已停掉` 五者之一，不是其他值 `[FR1.2][線框 §8]` |
| **AC1.1.3** | **Given** 我輸入的內容意圖操弄平台自身（例如要求讀取資料庫連線字串或金鑰），**When** 我送出，**Then** 系統**不呼叫 LLM**，並回覆固定的拒絕訊息 `[FR1.5]` |
| **AC1.1.4** | **Given** 交辦已完成，**When** 我切到架構圖生成頁，**Then** 我看到該次交辦的結果，不需要重新輸入需求 |
| **AC1.1.5** | **Given** 脈絡列顯示「尚未選定」，**When** 我輸入一句**內含對象名稱**的需求（例如「把**訂單系統**的圖加一個快取」），**Then** 脈絡列更新為該系統，且工作項針對它建立 `[user-flow Flow 1 第 3 步][線框 §2]` |

> **AC1.1.5 是本站修訂 1 補入的，由設計師查出。** 已核可的 `user-flow.md`
> Flow 1 第 3 步逐字寫「大腦辨識為架構類意圖，**並從敘述中認出作業對象**」，
> 而線框第 2 節的引導文字對使用者明白承諾了它——但原稿 18 則故事**零 AC**
> 涵蓋這一步。它同時是 `P-3`（「未必熟悉架構圖」）能走通自己唯一故事的前提：
> 沒有它，`AC10.1.1` 的 Given「脈絡列已指向一個系統」要求他先自己選對象。

**INVEST**：Independent（不依賴其他 US1.* 故事）· Negotiable · Valuable（這是整個
intent 的核心價值）· Estimable · Small（5 條 AC）· Testable（每條都有可觀察的結果）

### US1.2 判不出來的時候先問我，不要亂做

**身為** 架構設計者 `[P-1]`，**我想要** 系統在判不準我的意思時先問我，
**以便** 它不會擅自做出我沒要的東西。`[FR1.3][FR1.6][FR1.7][線框 §12]`

| AC | Given / When / Then |
|---|---|
| **AC1.2.1** | **Given** 我輸入一句語意不明確的話，**When** 路由層輸出的信心值 `< 0.7`，**Then** 系統**不建立任何工作項、不產生任何結果**，改列出候選判讀並反問我 `[FR1.3][FR1.7]` |
| **AC1.2.2** | **Given** 系統列出了候選判讀，**When** 我選定其中一個，**Then** 系統依該候選交辦，流程回到 US1.1 的第一步 |
| **AC1.2.3** | **Given** 系統列出了候選判讀，**When** 我選「都不是，我再講一次」，**Then** 回到輸入狀態，且脈絡列與作業對象**不變** `[線框 §12]` |
| **AC1.2.4** | **Given** 任何一次意圖判定，**When** 路由層回應，**Then** 它帶有一個定義域 0–1 的信心值可與門檻比較 `[FR1.6]` |

**INVEST**：Testable 的前提是 AC1.2.4 成立——若路由層不輸出信心值，AC1.2.1 的
觸發條件永不成立。這是**刻意寫成一條獨立 AC**，而非藏在前提裡。
`[FR1.6]` 已把它升為獨立需求，落點見 `requirements.md` 的 OQ-10。

### US1.3 交辦錯了，我把它導回來

**身為** 架構設計者 `[P-1]`，**我想要** 在系統判斷錯的時候逐項更正，
**以便** 不必整段重講也不必擔心它留下半成品。`[FR1.4][線框 §13]`

| AC | Given / When / Then |
|---|---|
| **AC1.3.1** | **Given** 畫面上有一個 `處理中` 的工作項，**When** 我說「不是這個」，**Then** 該工作項轉為 `已停掉`，且畫面明講它**有沒有留下東西** `[FR1.4][線框 §13]` |
| **AC1.3.2** | **Given** 畫面上有多個工作項，**When** 我更正其中一項，**Then** 其餘工作項的狀態**不受影響** `[FR1.4][FR5.2]` |
| **AC1.3.3** | **Given** 我更正了一項，**When** 系統改交給正確的功能，**Then** 新的工作項與被停掉的那項**同時可見**，且各自帶著自己的狀態 `[線框 §13]` |

**本故事不承諾的**：系統是否真能做到「停掉時不留半成品」屬實作層的原子性問題，
線框已明確不承諾；AC1.3.1 只要求畫面**把實情講出來**。

### US1.4 沒有權限的人不會落在一個用不了的頁面

**身為** 任一使用者 `[P-1][P-2][P-3][P-4]`，**我想要** 登入後落在我確實有權限用
的頁面，**以便** 不會停在一個我打不開的入口。`[FR1.8][R8]`

| AC | Given / When / Then |
|---|---|
| **AC1.4.1** | **Given** 我持有入口頁的 story 權限且我的帳號已核准，**When** 我登入並造訪 `/`，**Then** 我落在入口頁 |
| **AC1.4.2** | **Given** 我**不**持有入口頁權限但持有架構圖權限，**When** 我登入並造訪 `/`，**Then** 我落在 `/workspace`，且 Sidebar **不顯示**入口項目 `[FR1.8]` |
| **AC1.4.3** | **Given** 我的帳號**尚未核准**（`authorization_status` 非 approved），**When** 我登入並造訪 `/`，**Then** 我落在 `/waiting-approval`——**即使我持有入口頁權限** `[FR1.8][本站修訂 1：U8＝A]` |
| **AC1.4.4** | **Given** 某個角色的權限矩陣被調整為不具任何落地權限，**When** 該角色的使用者造訪 `/`，**Then** 他落在 `/403`——既有的「全無權限」處置**不被繞過** `[FR1.8][R8]` |

> **AC1.4.3 是本站修訂 1 新增的守門 AC，來源是 `[US:U8]`＝A。**
> **原瑕疵**：`requirements.md` 的 `FR1.8`（源自 `[R8]`＝A 的「置於瀑布之首」）
> 照**字面**實作，會把入口頁的判斷插在 `App.tsx:21` 的
> `if (isPending) return <Navigate to="/waiting-approval" />` **之前**——
> **未核准的帳號會落進入口頁**，繞過等待授權頁。`[R8]` 的衝突描述只列了五個
> 權限判斷與 `/403`，沒有涵蓋 `isPending` 這個分支。
> **本 AC 是對齊修正，不是本站的新定案**：`FR1.8` 的實質意圖是「入口頁優先於
> 其他權限落地」，而非「優先於帳號核准檢查」。依 `project.md` 的既有教訓，
> **上游的 `requirements.md` 不回改**；`FR1.8` 的措辭應理解為「置於**權限判斷**
> 之首、在 `isPending` 之後」。純比對兩份文件者請讀本註，不要判為迴歸。

> **AC1.4.4 取代了原本的 AC1.4.3。** 原稿寫「Given 我不持有上述任何一項權限」
> ——品質工程師查出、lead 以 308 列 seed 實算複驗：**11 個角色全部具備 A1
> view**，而 `App.tsx:22` 的第一道權限判斷就是 `canArch('view')`。因此原 Given
> 在**預設 seed 下不可達**，那是一條不可能失敗的 AC。改寫後的 Given 以「權限
> 矩陣被調整過」為前提，該狀態可由管理者在權限頁實際造出，故可達可測。

**仍不寫成 AC 的一項**：「無權限者看到的入口頁長什麼樣」——該狀態**不可達**
（`[R8]` 明寫不存在無權限的入口頁）。

**Definition of Done（US1 全群）**：`role_permissions` seed 變更須有 allow/deny
雙向測試（`team.md` A 規則）；`schema_rbac.sql` 與 `DEPLOY.md` 同步（`project.md`
blocking）。兩者皆為交付條件，非 AC。

## US2 — 跨功能共享的對話脈絡與自動切換（能力 2，**Must**）

### US2.1 換頁之後不用重講

對象，**以便** 不必把專案與系統再講一次。`[FR2.1][FR2.2][FR2.3][R3]`

| AC | Given / When / Then |
|---|---|
| **AC2.1.1** | **Given** 我在入口頁且脈絡列顯示「電商平台／訂單系統／主架構圖」，**When** 我切到 `/workspace`，**Then** 該頁的脈絡列顯示**逐欄相同**的三元組 `[FR2.2]` |
| **AC2.1.2** | **Given** 我在 `/workspace`，**When** 我切到 `/assessment`，**Then** 脈絡列仍顯示同一個三元組 `[FR2.1]` |
| **AC2.1.3** | **Given** 我在共享對話中，**When** 我造訪 `/cost` 或任一 `/admin/*` 頁，**Then** 該頁**不顯示**共享脈絡列——這兩處不在共享範圍內 `[FR2.1][Q7]` |
| **AC2.1.4** | **Given** backend 重啟過，**When** 我回到入口頁，**Then** 我的對話脈絡與作業對象**完整還原** `[NFR4]` |

### US2.2 看完檢視結果，帶著同一個系統回去改圖

| **AC2.2.3** | **Given** 我從未選定任何作業對象，**When** 我切換頁面，**Then** 脈絡列顯示「尚未選定」而非空白或錯誤 |

## US3 — 子功能頁另開新對話（能力 3，**Must**）

### US3.1 在子頁面開一段不相干的新對話

**身為** 架構設計者 `[P-1]`，**我想要** 在子功能頁另開一段獨立對話，
**以便** 手上這段討論不被新的問題打斷。`[FR3.1][FR3.2][FR3.3][R6][RA:R4]`

| AC | Given / When / Then |
|---|---|
| **AC3.1.1** | **Given** 我在 `/workspace` 的共享對話中，**When** 我由脈絡元件選「改為獨立對話」，**Then** 該頁進入一段新對話，且入口頁的脈絡**不受影響** `[FR3.1][R6]` |
| **AC3.1.2** | **Given** 我開了獨立對話，**When** 我查看它的訊息歷程，**Then** 它**不含**共享對話的任何訊息 `[FR3.2]` |
| **AC3.1.3** | **Given** 我開了獨立對話，**When** 我的第一則訊息說「這張圖」，**Then** 系統正確指向**切換前**的那張架構圖——作業對象**沿用** `[FR3.2][RA:R4]` |
| **AC3.1.4** | **Given** 我在獨立對話中，**When** 我選擇切回共享對話，**Then** 共享對話的訊息歷程與作業對象與我離開時相同 `[FR3.3]` |

**本故事的已知未決**：切回共享後，獨立那段的內容如何處置（保留／捨棄／可回溯）
未定——`requirements.md` 的 OQ-1 指派 `domain-design`（2.6）。AC3.1.4 只斷言
**共享那一段**不被影響，刻意不對獨立那段的去向下斷言。

## US4 — 長短期記憶（能力 4，**Must**）

> **本群於本站修訂 1 由 3 則拆為 5 則**（`[US:U7]`＝A）。原 `US4.1` 一則獨佔
> 獨立 schema（零前例、SQLite 測不到）、grant 邊界與整套檢索，INVEST 的
> 「Small」（1–5 天）不成立；且 FR4 的 10 條子需求只拆 3 則，而 FR1 的 8 條
> 拆了 4 則，切分軸不一致。拆出的兩則為 `US4.4`／`US4.5`，`US4.2`／`US4.3`
> 維持原 id 不動（id 是永久追溯鍵）。
>
> **編號不連續是刻意的**（本站修訂 2）。拆分當下先寫成 `US4.1a`／`4.1b`／`4.1c`，
> 但框架的 id 文法是 `US\d+\.\d+`（`.claude/tools/aidlc-sensor-traceability.ts:61`）
> 與 `AC\d+\.\d+\.\d+`（同檔 62 行），**帶字母後綴者一個都比對不到**——不只
> traceability sensor，`units-generation` 與 `domain-design` 也都用同一組 pattern
> 從本檔解析上游 id，那三則故事與其 9 條 AC 會對下游全部隱形。改用文法內的編號後，
> 新序號接在群組尾端而非重排 `US4.2`／`US4.3`：後兩者已被本站三份 contribution
> 檔引用 11 處，重排會讓那些引用靜默指向另一則故事。因此群組 4 的文件順序為
> `US4.1 → US4.4 → US4.5 → US4.2 → US4.3`。
>
> 附帶發現（**不回改上游**，依 `project.md` 的 `refined-mockups:c3`）：
> `requirements.md` 的 `FR4.3a`／`FR4.3b`／`FR4.5a` 同樣落在文法外，
> 會被解析成 `FR4`。本檔的追溯表以群組 `FR4` 承接，三條子需求的**個別**
> 追溯在機械層不可見，列為交接事項。

### US4.1 系統記得我們之前談過什麼

**身為** 架構設計者 `[P-1]`，**我想要** 系統跨對話記得相關的脈絡，
**以便** 我不用每次從頭交代背景。`[FR4.1][FR4.2][Q9]`

| AC | Given / When / Then |
|---|---|
| **AC4.1.1** | **Given** 我在先前的對話中提過某個系統的設計取向，**When** 系統為新對話組裝脈絡，**Then** 組裝結果**包含**那一筆先前記憶 `[FR4.1]` |
| **AC4.1.2** | **Given** 記憶中有屬於他人的資料，**When** 系統為我組裝脈絡，**Then** 組裝結果**只**包含我依可見範圍有權讀取的部分 `[FR4.3]` |
| **AC4.1.3** | **Given** 三種記憶（語意／程序／情節）各有資料，**When** 系統組裝脈絡，**Then** 三者皆可被取得，不是只有其中一種 `[FR4.1]` |

> **AC4.1.1 是原 AC4.1.1 的改寫，由品質工程師指出。** 原稿寫「系統的回覆
> **反映出**它取得了那項先前資訊」——「反映出」不是二元可判的，QA 無法在不做
> 判斷的情況下說通過或失敗。改寫後斷言的是**脈絡組裝的結果**（與 AC4.1.2
> 同形狀），而非回覆的散文內容。這是草稿自己已示範過的做法，不引入新的紀律妥協。
>
> **仍存在的一項限制（如實記載）**：品質工程師另指出此故事的 Given「我在先前的
> 對話中提過某個系統的設計取向」**無法構造**——沒有任何需求說什麼事件會產生一筆
> 語意或程序記憶（寫入端懸空）。`FR4.1` 只說「應提供三種記憶」，未定義寫入時機。
> 這是 `requirements.md` 的缺口，本站無法在故事層補上；已列為本檔 Assumptions
> 並指派 `domain-design`（2.6）——那一站定資料模型時必須同時定寫入時機。

### US4.4 我的記憶是我的

**身為** 架構設計者 `[P-1]`，**我想要** 系統寫下的記憶確實歸屬於我，
**以便** 別人不能冒用我的身分留下記憶。`[FR4.3a]`

| AC | Given / When / Then |
|---|---|

> **AC9.1.4 是本站修訂 1 補入的，由開發者查出，而且它修的是一個會靜默通過的洞。**
>
> 開發者對 `AC9.1.2`／`AC9.1.3` 的判定是**不可驗證，且失敗是靜默的**，理由是
> 兩個環境走**不同的 schema 路徑**：CI 的 `deploy/docker-compose.test.yml:20–22`
> 每次重建 DB 並把 `schema_rbac.sql` 掛成 initdb，而 staging 只走
> `backend/database.py` 的 `_ensure_*` 補丁。**CI 驗的那一條路 staging 永遠不走**，
> 而 `AC9.1.2` 的 Given（一張在本 intent 之前建立的架構圖）在每個自動化環境裡
> **都不可達**——每個環境的 DB 都是新的。`backend/database.py:504–511` 的
> docstring 已逐字寫下這個失敗模式。
>
> 加 NOT NULL FK 的唯一既有前例是 `database.py:403–415` 的三步
> （add nullable → backfill → set not null），而那三句**逐句**
> `except Exception: logger.warning`——回填失敗即靜默留 NULL。
>
> `AC9.1.4` 把這件事變成一個**二元可判且會大聲失敗**的不變量：列數不是 0 就是
> 不是 0，而且它斷言「不為 0 時必須失敗」，直接否掉照抄既有 `logger.warning`
> 形狀的實作。這條在 CI 上也驗得出來（新 DB 的列數本來就該是 0），在 staging
> 上則是遷移後的驗收關卡。

**本故事的最大風險**：既有架構圖的遷移沒有任何技術試探涵蓋（`[F10]`＝A 明確
否決），且 `schema_rbac.sql` 只在空 volume 執行。遷移的歸屬規則與回復方式由
`domain-design`（2.6）產出（`[FR9.3]`／`[H3]`）。

**Definition of Done（US9 全群）**：遷移程序不得沿用 `_ensure_*` 的
`except Exception: logger.warning` 形狀——回填失敗必須讓程序失敗，
否則 `AC9.1.4` 在 staging 上恆真而無意義。另 `FR9.4`（跨雲分析為專案層級但本次
不納入）在本群**刻意無 AC**：它是一個明確的範圍排除項，不是待實作的行為；
為它寫 AC 會產生一條驗收「某件事沒有被做」的標準。`FR9.4` 的落點即此註。

## US10 — 成本／FinOps 能力的編排（能力 10，**Must**）

### US10.1 在入口頁問成本，就地得到答案

**身為** 成本／FinOps 關注者 `[P-3]`，**我想要** 在入口頁問一句就得到成本答案，
**以便** 我不必自己走到成本頁再找對的估價集合。`[FR10.1][FR10.2][FR10.6][FR10.7][Q12][Q14][R4][R5]`

| AC | Given / When / Then |
|---|---|
| **AC10.1.1** | **Given** 我在入口頁，**When** 我問一句成本問題（脈絡列已指向某系統時用「這個系統」；未指向時在句中指名系統），**Then** 系統辨識為成本類需求、認出對象並交給既有的成本能力 `[FR10.1][AC1.1.5]` |
| **AC10.1.2** | **Given** 成本工作正在進行，**When** 我查看畫面，**Then** 進度以**單一則就地更新**的訊息呈現，不是每次進度都新增一則 `[FR10.6][R5]` |
| **AC10.1.3** | **Given** 成本工作完成，**When** 我查看畫面，**Then** 該則進度訊息被**結構化卡片**取代，卡片附可點往成本頁的連結 `[FR10.6][R4]` |
| **AC10.1.4** | **Given** 全程進行中，**When** 我觀察自己的位置，**Then** 我**沒有離開入口頁** `[FR10.7][Q14]` |
| **AC10.1.5** | **Given** 我不具備成本能力的檢視權限，**When** 我問成本問題，**Then** 我被拒絕——大腦代呼叫**不繞過**既有授權 `[FR10.2]` |

### US10.2 成本工作失敗的時候我看得出來

**身為** 成本／FinOps 關注者 `[P-3]`，**我想要** 分得出「還在跑」與「已失敗」，
**以便** 我知道要等還是要重試。`[FR10.4][FR10.5][FR10.8]`

| AC | Given / When / Then |
|---|---|
| **AC10.2.1** | **Given** 成本工作逾時，**When** 該終態發生，**Then** 畫面出現可見訊息說明它逾時，不是停在最後一則進度 `[FR10.5]` |
| **AC10.2.2** | **Given** 成本工作失敗，**When** 該終態發生，**Then** 畫面出現可見訊息說明它失敗，且與逾時的訊息**可區分** `[FR10.5]` |
| **AC10.2.3** | **Given** 我送出成本問題，**When** 成本端仍在處理，**Then** 大腦**已經開始回覆**——不等成本工作完成才開始 `[FR10.4]` |

| **AC10.2.4** | **Given** 我經由大腦問了成本問題，**When** 管理者查看該次成本操作的稽核事件，**Then** 事件的行為主體是**我本人**，不是大腦或任何服務帳號 `[FR10.3]` |

> **AC10.2.4 是 `FR10.3` 的落點**（開發者查出它原本在 `stories.md` 零引用）。
> 它是外部可觀察的：`estimate_audit_events` 有寫入端，事件的 actor 欄位可被檢查。
> 這條同時是 `FR10.2`（一律走 HTTP 帶使用者 token）的**後果驗收**——若實作改走
> 同進程呼叫 service 層，actor 就不會是使用者本人，這條 AC 會紅燈。

**AC10.2.3 的技術前提（不寫成 AC，但下游必讀）**：成本端的「串流」是每秒輪詢
DB 送出的**狀態事件**，不是 token 串流；真正的 LLM 呼叫是同步 `invoke`。
因此大腦**不得**對它做 token 級的巢狀轉送（`[FR10.8]`／`C-T10`）。

**Definition of Done（US10 全群）**：與 US8 第 4 項同——e2e 需以注入接縫打樁
LLM（`[US:U9]`＝A），否則本群的 AC 在測試 stack 上無法驗證。

## 量測交付物（`M-*`，**非**使用者故事）

不是使用者可見行為。它們**刻意不寫成故事**——硬套 `As a [persona]` 會產生
`user-story-patterns.md` 列為反樣式的「開發者視角故事」，而 `personas.md` 的
清單中也沒有開發者。

給它們 `M-*` id 是為了讓 `delivery-planning`（2.9）看得到並估算工作量——
它們正是 `requirements.md` 列為回補項的 **N-3**。

| id | 交付物 | 綁定 | 內容 |
|---|---|---|---|
| **M-1** | ≥ 50 筆人工標註的意圖測試集 | `[NFR1]` | 每筆為「一句使用者輸入 → 應交辦給哪一個功能能力」的配對。與本檔各故事的 Given/When/Then 同源——AC1.1.1、AC5.1.1 等即為標註集的典型條目 |
| **M-2** | N 個具名的跨頁面切換情境清單 | `[NFR2]` | 每個情境為一次頁面切換（入口頁／`/workspace`／`/assessment` 三者之間）。AC2.1.1、AC2.1.2、AC2.2.1 即為情境的範型 |
| **M-3** | 跨功能任務情境集合 ＋ 現行 UI 的切換次數基準 | `[NFR11]` | 每個情境為一個完整的跨功能任務（例如「改圖再估成本」）。基準值須由**人工實際清點**現行 11 條路由下的切換次數，不是估計 |

**三項的承接與轉移**：本站（`user-stories`）為 `CONDITIONAL`。若本站被判定不適用
而 skip，三項的產生義務**自動轉移**至 `build-and-test`（3.6，`ALWAYS`）——
與 `requirements.md` 為 NFR1 標註集所訂的轉移規則相同。

**M-1 的獨立性提醒**：標註集由本站（產品視角）產生而非由實作者產生，是刻意的
——`[RA:R9]` 的選項 B（在 Construction 的工作單元內產生）被否決，理由是
「標註集由實作者自己出、量測自己的實作，獨立性較弱」。

AC 在 CI 裡目前無法被驗證。

（`advice_orchestrator._run_agent` 是既有先例），讓 e2e 在不需要真實金鑰的情況下
驗證**行為**（意圖被辨識、工作項被建立、狀態轉換正確）。**不把金鑰放進 CI**
——本 repo 為 public、Actions log 公開可讀，`project.md` 已記載「一次意外 echo
即等同公開發布」。

**樁不驗證的那一半如實記載**：模型判斷的**品質**（選對功能的比例）不由 e2e 驗，
由 `NFR1` 的 ≥ 50 筆標註集在另一條路徑量測（`M-1`）。兩者不可互相替代。

**受影響的 AC**：US1 全群、US5.1、US6.1、US10.1／US10.2 中凡斷言「系統辨識為
某類意圖」或「回覆內容」者。各群的 Definition of Done 已就地載明打樁義務。

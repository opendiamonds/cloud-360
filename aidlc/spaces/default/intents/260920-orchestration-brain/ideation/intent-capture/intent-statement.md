## Problem Statement

Cloud-360 的 AI 能力目前分散在各自獨立的功能入口上，使用者必須自己完成
「判斷該用哪個功能、切到哪一頁、把前一頁的脈絡重講一次」這三件事。本次要
建立的是一個**統一入口**，讓使用者說出需求之後，由系統負責判斷要做什麼、
交給誰做、以及維持整段過程的上下文。[desc]

具體要收斂的是三個同時存在的痛點 [Q1]：

- **沒有統一入口**：想做的事跨多個功能時，使用者得先知道該去哪一頁、該找
  哪個功能，系統沒有一個「說出需求就會被帶到對的地方」的入口。[Q1]
- **上下文在頁面之間斷掉**：在某一個功能裡講過的對象與意圖，換到另一個
  功能後要重講一次，對話與工作狀態不連續。[Q1]
- **能力無法組合**：一個需求需要多個功能接力時，沒有任何機制能把它拆成
  幾件工作並分派出去。[Q1]

為了讓「上下文不斷掉」成立，系統必須能明確指出**使用者當下正在處理哪一個
對象**。[Q5] 本次確認該對象以「專案 → 系統 → 架構圖」三個層級來識別與
記錄，而非僅止於單一張架構圖。[Q5] 這個層級關係本身來自使用者對 Cloud-360
的描述：一個專案有多個系統，一個系統對應一份架構圖檔與其中多張圖，系統
各自有其成本，而**跨雲分析是專案層級**的面向。[desc]
（修訂 1：本句原把跨雲分析寫成系統層級的既定面向，與原始描述逐字的
「也有該自己的成本，跨雲分析（by專案）」及下方 Assumptions 第 2 項矛盾；
此為前次審查 R-02 的修正，非本輪新定案。）

## Target Customer

第一版的服務對象與其現況困難如下 [Q2]：

| 對象 | 關注的事 | 第一版的定位 | 來源 |
|---|---|---|---|
| 架構設計者 | 在架構圖工作區畫圖、改圖；需求從對話變成圖的過程要反覆切換工具與頁面 | 直接服務 | [Q2] |
| 評估／稽核者 | 使用 Well-Architected 檢視；看完結果後要自己把發現帶回架構圖或成本討論 | 直接服務 | [Q2] |
| 成本／FinOps 關注者 | 想問「這個系統花多少、跨雲怎麼比」 | 直接服務：其成本問題由統一入口辨識後交給**既有的**成本／FinOps 能力回答，第一版就問得到答案；答案**就地在入口頁呈現**，使用者不需離開入口頁 | [Q2][Q12][Q14] |
| 管理者／平台維運者 | 關心誰在改什麼、有沒有紀錄 | 間接服務：其需求由長期記憶或既有稽核紀錄承載，不經由跨頁面的共享工作階段 | [Q2][Q10] |

共享工作階段（同一段對話脈絡可跨功能延續）的涵蓋範圍為**統一入口、架構圖
工作區、評估頁**三處，不含管理功能頁面。[Q7] 成本頁面同樣不在此範圍內，
而成本關注者仍是直接服務對象——因為成本答案就地在入口頁呈現，不需要該頁
加入共享範圍。[Q14]

## Success Metrics

第一版要以下列三項可量測結果判斷是否成功 [Q3]：

- **意圖識別準確率**：使用者在統一入口說出一句需求，系統選對要交辦之功能的
  比例，達到指定門檻。門檻值於後續階段定案。[Q3]
- **跨頁面上下文保留率**：切換功能後，系統仍正確指向同一個作業對象、使用者
  不需要重講的比例；本項一併涵蓋「完成一個跨功能任務所需的頁面切換次數
  下降」。[Q3]
- **首字回應時間**：從使用者送出到畫面出現第一個字的時間低於指定秒數。
  秒數於後續階段定案。[Q3]

## Initiative Trigger

現在做這件事的理由是**既有的 AI 功能路徑已經到達極限**：目前的兩個生成
入口彼此獨立，再增加任何功能都會變成第三、第四個孤島。[Q4]

## Initial Scope Signal

- **workflow-selected**：本工作流程以 `agent-orchestration-brain` 這個範圍
  啟動（28 站執行、6 站跳過、25 道人工核可關卡）。[scope]
- **使用者確認的產品邊界**：使用者確認沿用上述工作計畫，且產品邊界即為本
  文件所述的能力集合，不做增刪。[Q9]

本次確認納入產品邊界的能力（內容來自使用者的原始描述，「納入邊界」這個
確認動作本身由 Q9 的作答支撐）[desc][Q9]：統一入口的
意圖識別與工作交辦、跨功能共享的對話脈絡與自動切換、可在子功能各自開啟新
對話、長短期記憶（語意記憶、程序記憶、情節記憶）、多意圖識別、多輪對話、
主動通知推播，以及讓回覆能逐步顯示的串流式互動。

本次確認**納入**「專案 → 系統 → 架構圖」層級的建立，作為作業對象識別的
基礎。[Q5]

成本／FinOps 能力**已經存在**，故本次納入的是**對它的編排**：統一入口要能
辨識成本類需求並交給既有能力回答。本次**不新建**成本計算，也**不納入**
原始描述提到、而既有能力尚未具備的「跨雲分析（by 專案）」。[Q12]
（修訂 1：本段原依 [Q6][Q11] 寫為「只納入交接介面，不納入成本計算本身」，
其前提「成本能力不存在」已被推翻，改以 Q12 為準。）

編排能力本次**自建**，不改造既有已上線的成本能力，兩者並行。[Q13]

此決定的已知代價已於作答時向決策者逐項揭露，在此完整承接而非概括：系統內
將並存**兩份 OpenRouter 客戶端**與**兩套串流事件語意**。這正是 `team.md`
的 `## Code Style` 之「單一真實來源」規則所管制的形狀——該規則要求新增
第二份物化前先確認是否有既有機制可用，若確實無法避免，新增副本的同一個
變更必須一併新增鎖住兩者一致的測試。本次是**使用者知情後的決定**，不是
疏漏；因此處置是把「鎖住兩份執行機制一致性的驗證」作為約束項下推給後續
階段，而不是在本階段推翻決定。下游不需回頭讀問題檔即可承接此約束。[Q13]

專案層級的既有邊界不因本次而改變：雲端供應商 production 環境、production
credentials、environment-specific secrets、direct production IaC、destructive
cloud operations 與 native iOS/Android app 仍在範圍之外。[memory:M2]
本次能力落在既有的 in-scope 清單所涵蓋的 architecture diagrams 與 agent
routing design 之內。[memory:M1] 專案定位為 AI-native multi-cloud
architecture & operations platform，本次能力與該定位一致。[memory:M3]

## Assumptions & Open Questions

- 三項成功指標的具體門檻值（意圖識別準確率的百分比、首字回應時間的秒數、上下文保留率的百分比）尚未定案，留待後續階段決定；在那之前本文件不對任何數值做出承諾 [assumption]
- 使用者的原始描述提到「跨雲分析（by 專案）」是專案層級的一個面向，但本階段未確認它是否屬於第一版要交付的能力、或僅是層級模型要預留的位置 [assumption]
- 使用者的原始描述提到「主動通知推播」，但本階段未確認推播的觸發情境與接收對象 [assumption]
- 「專案 → 系統 → 架構圖」層級一旦建立，既有以單張架構圖為單位的使用方式將如何銜接（既有資料的歸屬、既有頁面的呈現）尚未確認 [assumption]
- 統一入口本身要以串流方式逐步顯示回覆，而本次要編排的成本能力自己也是串流來源；兩層串流如何交接（逐字轉送、彙整後再送、或兩者並存）尚未確認 [assumption]
- 大腦代使用者呼叫既有成本能力時，既有的成本授權（`CostPage` 與成本端點以 `can('C1','view')` 控管）如何在代呼叫路徑上被沿用、確保不被繞過，本階段未確認；此為 ADR-0006 security baseline 的 IAM 面向影響項 [assumption]
- 既有成本能力會寫稽核事件，而經大腦代呼叫時稽核記錄的行為主體如何認定（記為使用者本人或記為大腦）本階段未確認；此為 ADR-0006 security baseline 的 audit logging 面向影響項 [assumption]

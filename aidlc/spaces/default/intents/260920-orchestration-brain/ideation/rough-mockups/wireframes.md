# Wireframes — 統一入口大腦

## 上游輸入

本站消費 `<record>/ideation/intent-capture/intent-statement.md`、
`<record>/ideation/scope-definition/scope-document.md` 與 `intent-backlog.md`。
其中對本站具約束力的已核可決定：共享工作階段涵蓋**入口頁、架構圖工作區、
評估頁**三處 [Q7]；成本答案**就地在入口頁呈現** [Q14]；能力 10 成本編排為
**Must** [S11]；能力 3「子功能各自開新對話」為 Must；能力 7 主動通知推播為
唯一的 **Should**，故本站只畫它「若存在時的落點」，不當成必然存在。

## 設計決策摘要

| 決定 | 內容 | 來源 |
|---|---|---|
| 入口落點 | Sidebar 置頂獨立項（不歸入現有三個功能群組），`/` 預設導向改為入口頁 | [R1] |
| 版面骨架 | 對話為主 ＋ **頂部脈絡列**（常駐但不佔寬度，可展開） | [R2] |
| 子頁面脈絡 | 與入口頁**同一個脈絡元件**，跟著使用者走 | [R3] |
| 成本呈現 | 對話流中的**結構化卡片** ＋ 前往成本頁連結 | [R4] |
| 進度呈現 | **單一則就地更新**的進度訊息，不逐則累加 | [R5] |
| 新對話入口 | 由**脈絡列**承載「共享 ↔ 獨立」切換 | [R6] |
| 裝置與無障礙 | 桌機 ＋ 響應式 ＋ WCAG 2.1 AA | [R7] |
| 入口頁權限 | 取得自己的 story id，置於 `DefaultRedirect` 瀑布之首 | [R8] |
| 多意圖呈現 | 拆成編號的多項，各自標示狀態，不混成一則回覆 | PL-02 補正 |
| 記憶的使用者可見面 | 獨立的「我的記憶」畫面，三類記憶各可逐則刪除 | [F5]=C、PL-02 補正 |
| 兩種串流區分 | 成本 job 的狀態輪詢（第 4 節）與大腦自身回覆的逐字串流（第 11 節）分開畫 | 自行複查補正 |
| 意圖識別的失敗面 | **不確定時先問不動手**（第 12 節）＋ **交辦後可逐項導回**（第 13 節）；被停掉的工作須有可見的終止狀態，且畫面須明講它有沒有留下東西 | iteration 2 人工退回補正 |

**ASCII 框線產生方式**：依 `project.md` 的 `rough-mockups:c4`，本檔所有框線
以腳本產生並驗證「每個框內每一行的 `len()` 字元數一致」（本檔為 72），非手寫。
依 `rough-mockups:rev1-c15`，計數基準沿用既有 artifact 的慣例＝`len()` 字元數，
非顯示寬度。依 `rough-mockups:c2`，圖示一律基本 ASCII（`(!)`／`(i)`／`(o)`／
`[*]`／`[v]`），不使用 emoji。

<!-- Text fallback: 記憶管理畫面分三區——語意記憶（偏好與慣用說法）、程序記憶
（常走的工作流程）、情節記憶（過往對話），每一則旁邊有刪除。頂部說明刪除後
大腦不再依據它回答，但刪除動作本身會留下稽核紀錄。底部顯示保存期限，N 值待定。 -->

**依據**：本節為 iteration 1 審查發現 **PL-02** 的補正，但查證後發現缺口比該
發現所述更大——能力 4 並非「純後端、無 UI」：feasibility **[F5]=C** 已核可
「保存期限 ＋ **使用者可自行刪除自己的記憶**」，那是一個已定案的、使用者可見
的操作，原稿完全沒有承載它的畫面。

**與能力 2 的邊界**（PL-02 明文要求釐清）：能力 2「跨功能共享的對話脈絡」的
使用者可見面是**脈絡列**（第 3、6 節）——它回答「我現在在處理哪一個對象」。
能力 4「長短期記憶」的使用者可見面是**本節**——它回答「大腦記住了關於我的
哪些事，我能不能刪」。兩者不同：脈絡是當下的、隨對象改變；記憶是累積的、
跨 session 存在。

**基準方案聲明**（依 `rough-mockups:c5`）：本節的**落點**（獨立頁面、入口頁
的面板、或設定頁的一區）為單一基準方案，目的是讓 reviewer 與關卡有具體對象；
替代方案留待 refined-mockups 探索。**不是基準的部分**是「這個使用者可見面
必須存在」——那由 [F5]=C 定案，不可在下游被省略。

**安全註記（ADR-0006 audit logging 面向）**：刪除動作本身留下稽核紀錄，呼應
feasibility RAID **R-7**「記憶層的刪除權與稽核需求互相抵消」所記的緩解方向
（刪除可被稽核而內容被移除）。

**為什麼是分組固定欄位而不是自由鍵值對（[R12]=D）**：自由欄位會讓同一個概念

agent 需要某欄位時，由大腦與使用者溝通後寫回（經 MCP 封裝、底下 HTTP 帶 token，
[S13]=A）。若畫面不顯示是誰寫的，使用者無法分辨哪些值是自己填的、哪些是對話中
被記下來的。

**無障礙註記**：每個欄位為 `label` ＋ `input`（`ux-guide.md`：標籤在輸入框上方，
不得只用 placeholder）；「未填」為文字而非只有紅框；分組為 `fieldset` ＋ `legend`。

**本站自檢查出的缺口（未補設計，只標出）**：依 `project.md` 的契約端點三問
（誰寫、誰讀、誰清），本節只交代了**兩端**——寫入端是使用者與大腦代 agent
（底部「最後更新」那一行），讀取端是各 agent 與總覽籤的計數。**清除端沒有任何
畫面**：一個填過的欄位要怎麼清空、清空與「從未填過」在畫面上是否可區分、以及
agent 寫錯時使用者如何撤銷，三者皆未畫。本站**不自行發明**該設計——它牽涉
「值的歷史要不要留」這個資料模型決定，屬 domain-design。此缺口登記於
Assumptions，並在交接時點名。

## 本站查出、已核可 scope 尚未涵蓋的項目（**需回補**）

依 `project.md` 的既有規則——本階段查出、已核可 scope 未涵蓋的項目須**逐處明標並

### 成員管理（iteration 1 審查 `R-01` 觸發，本站據以查出範圍缺口）

審查指出 §16–§18 的頁首畫了 `[成員]` 按鈕卻沒有任何對應畫面。**查證後發現
問題比「少畫一張圖」更深**：

- **會議結論明文描述了成員管理的完整工作流**——專案創建者為 `project_owner` 即
  `project_admin`、可指定其他加入專案的成員角色給予權限、`project_admin` 可多人、
  `project_owner` 帳號被移除時自動改選其他人。
- **`[S14]=A` 的定案預設它存在**——「專案成員角色不進 `CANONICAL_ROLES`」這句話
  只有在有成員角色這件事的前提下才有意義。
- **但 `scope-document.md` 修訂 2 的能力 11 定義逐字沒有它**：「建立專案／系統、
  需求欄位的查詢新增更新、子 agent 記憶的摘要彙整呈現、專案儀表板」——四項，
  沒有成員管理。

**本站的處置**：`[成員]` 按鈕已從 §16–§18 移除——**不為一個沒有範圍的東西畫
affordance**，那會讓使用者點了之後無處可去，也會讓下游誤以為它已被設計過。
**要求回補**：`scope-definition` 須決定成員管理是併入能力 11、另立能力 12、
還是明確排除。本站**不替它決定**——那是範圍決定，不是線框決定。

**這個缺口的來源是我自己**：scope-definition 修訂 2 寫能力 11 定義時，我把會議
結論的前半段（需求彙整）寫進去了，後半段（角色模型）只在 `[S14]` 當成命名問題
處理，沒有回頭看它是否需要自己的範圍條目。

### 可無障礙存取的籤（tab）在本 repo 零前例

§16–§18 的三籤設計，其無障礙註記要求 `role="tablist"` ＋ 方向鍵切換
（`accessibility-wcag.md` 的鍵盤樣式表）。本站查證前端現況：

- **籤式切換的機制有前例**——`frontend/src/pages/AssessmentPage.tsx:134` 的
  `useState<'reviews' | 'lens'>`。
- **但那是純 `useState`，沒有 `role="tablist"`、沒有 `aria-selected`、沒有方向鍵**：
  全樹搜尋這三者為零命中。

所以 `[R10]=B` 的三籤比提問時所說的多一項成本:**一個可無障礙存取的籤元件要新寫**。
這一項在我推薦 `[R10]=B` 時沒有查、因此沒有揭露，記此以免下游把它當成零成本沿用。

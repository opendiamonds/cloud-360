## 二、執行方式

以一次性分支的 workflow 在 staging runner 上執行（比照先前的診斷 workflow），跑完刪除分支、永不合併。

**量測 A（路由層）**：在 `cloud360-backend-1` 容器內以 `docker exec` 執行一段 Python，直接建立與線上相同的路由 port（`intent_routing_port.select_routing_port`，`LLM_PROVIDER=openrouter`、`BRAIN_ROUTER_MODEL=typesafe/jev-1.14`），對 §三 每一筆呼叫 `classify`：
- 第 1 輪逐筆、第 2 輪 5 併發（`asyncio.gather` 分批）。
- 不經閘道，故**不建立 session、不寫記憶、不交辦任何工作**；名稱目錄傳空（標註集不含專有名稱）。
- 金鑰只在容器內使用，從不輸出。Actions log 只印彙總：命中數、準確率、反問率、P50／P95／最大值、錯誤類別計數。逐筆判定寫進容器內暫存檔，以 `docker cp` 取出後**只上傳為 workflow artifact**（7 天保留），不印到 log。標註集的句子本來就在 public repo，不含任何使用者資料。
- 費用：每次路由約 2.9e-05 美元（ADR-0024），60 筆 × 2 輪約 0.004 美元。

**量測 B（完整對話）**：在同一容器內：
- 建立一個專用測試帳號 `__cloud360_perf_probe__`（角色 `Project_Architect`，具 K1），以容器內的 `create_access_token` 簽一個短效 token；token 與密碼都不輸出。
- 以該 token 開 WebSocket 到容器內的 `ws://127.0.0.1:8000/api/brain/ws`，依序送 30 句（取自 §三 的單一意圖與應反問句），每句等到該輪結束。
- 該帳號**不設任何作業對象**：交辦出的工作項會立即以「請先在脈絡列選定架構圖或系統」結束，不會觸發架構生成、評核或成本計算——量的是首字延遲，不是能力本身的耗時。
- 結束後從 `docker logs --since` 取該時段的 `turn_end` 計算分段分位數。
- 測試帳號保留以利重測；其 session 與對話紀錄留在 Redis／DB，依既有的 90 天記憶清除與 session TTL 自然消失。

### 實際執行與計畫的差異（2026-11-16，執行後補記）

- 標註集經使用者過目後**照原樣**執行（未改任何一筆）。
- 量測 B 第一次執行（run 43887439909）在中途以 `ConnectionClosedError` 失敗；第二次（run 43888107820）改為記錄 close code 並在斷線後重連續跑，且以 `if: false` 跳過量測 A，避免重複呼叫模型。
- **客戶端計時作廢**：每一輪使用者對話之後，伺服器會為交辦結果再送一輪自己的 `done`，腳本把它當成下一句的結束而使計時錯位（詳見 `test-results.md` §二）。NFR3／NFR13.1 依定義以伺服器端 `turn_end` 判定，不受影響。
- 百分位數採最近秩法（`ceil(p × n)`）；第一版公式在 n＝2 時取錯位，執行前已修正並以已知值驗證。

**計分總數**：單一意圖 45 筆＋多意圖 16 筆＋應反問 7 筆＝**68 筆判定**（≥ 50，符合 NFR1）。

**計分規則**：
- 單一意圖：路由給出唯一一個交辦目標且等於標籤 → 命中；反問或交辦錯 → 未命中。
- 多意圖：每個標籤各算一筆，該能力出現在交辦集合中即命中；多交辦出標籤以外的能力，每多一個記一筆未命中。
- 應反問：路由走反問（不交辦）→ 命中；交辦了任何能力 → 未命中。
- **反問率**＝路由走反問的筆數 ÷ 60 句，與準確率並列（`intent-router:NFR1.60`）。

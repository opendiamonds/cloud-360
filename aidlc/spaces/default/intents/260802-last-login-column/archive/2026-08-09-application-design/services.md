> **本文件為 iteration 3**，依 iteration 1、2 的 reviewer findings 修訂。

## 結論先行：本 intent 不新增服務

本設計**不新增任何服務、不引入新的執行單元、不新增外部依賴**。這是一個明確的設計決定而非省略，理由與被否決的替代方案記於 `decisions.md` AD-5。

判斷依據：本 intent 的全部行為（在請求路徑上寫一個時間戳、在既有回應中多帶兩個欄位、在既有頁面多顯示一欄、在啟動時套用兩個補丁）都落在既有服務的職責範圍內。新增服務會引入跨程序通訊、部署單元與失敗模式，而換得的收益為零。

因此本檔的實質內容是：**本 intent 在既有服務拓樸中的落點**，以及它對既有服務**運行特性的影響**。

## 既有服務拓樸與本 intent 的落點

部署堆疊由四個服務組成（codekb `architecture.md`）：資料庫、後端應用、前端靜態服務、對外通道。本 intent 觸及其中三個：

| 服務 | 本 intent 的變更 | 變更性質 |
|---|---|---|
| 資料庫 | 使用者表新增一個可為空的時間戳欄位；權限表一列的值變更 | schema 擴充 + 單列資料變更（皆可重複執行） |
| 後端應用 | 請求路徑新增條件式寫入；三個使用者物件端點的回應各新增兩欄；啟動流程新增兩個補丁 | 既有模組內擴充 |
| 前端 | 管理頁新增一欄與小螢幕卡片佈局 | 既有頁面擴充 |
| 對外通道 | 無 | 不觸及 |

後端為模組化單體，本 intent 的三個新**後端**元件（C-1 政策、C-2 記錄器、C-7 權限套用）以既有的 service 模組形式加入，不構成新的服務邊界。（元件清單中標為「新增」者共四個，另一個是前端的 C-5。）

## 通訊模式：全同步

本 intent 的所有元件間通訊皆為**同步的程序內函式呼叫**，唯一的跨程序通訊是前端到後端的既有 HTTP 請求。

**沒有非同步、沒有事件、沒有訊息佇列**。這不是因為未考慮 —— 本站 Q1 明確評估過非同步背景寫入並否決之（`decisions.md` AD-1）。否決的核心理由是：非同步改變的是「寫入何時發生」而非「寫入多常發生」，它**本身不構成節流手段**，仍需搭配判定邏輯才能滿足 requirements FR-1.3；而加上背景任務後，例外不再傳回請求端，需額外的錯誤處理才不違反 construction 階段護欄。以本 intent 的寫入量級（每帳號每 5 分鐘至多一筆單列更新），這些成本換不到對應收益。

**編排模式**：無編排也無編舞 —— 沒有需要協調的多方參與者。C-2 的呼叫是單一觸發點的直線流程。

## 生命週期：啟動期的兩個前置條件

本 intent 引入兩個**啟動期執行、請求期不執行**的元件：

| 元件 | 啟動時做什麼 | 未執行的後果 |
|---|---|---|
| C-3 | 為既有資料庫補上新欄位 | 讀寫路徑皆因欄位不存在而失敗 |
| C-7 | 在權限種子之後，對權限表做條件式的目標更新（只更新不插入） | 目標角色進不了管理頁 —— US-3 整則落空 |

**因此部署後必須完成一次服務重啟**（requirements C-2、stories AC-1.7）。專案無資料庫遷移框架，結構與 seed 變更都靠啟動時自動補齊；這不是可選的維運建議，而是本設計成立的必要條件，須寫入部署程序。

兩個補丁皆為**可重複執行**：多次啟動的結果相同，不會累積副作用。但 **C-7 的執行位置與寫入語意有嚴格契約**（必須在權限種子之後、只更新不插入、條件式套用）—— 違反會清空整份權限矩陣，詳見 `components.md` C-7。

**同步義務**（requirements C-4，blocking）：欄位 DDL 與權限 seed 的語意變更，皆須同步更新 repo 根目錄的 schema 檔與部署文件，未同步不得標示相關階段完成。

## 運行特性

### 寫入量級

節流生效後，**單一帳號的寫入上限是每 5 分鐘一筆**（requirements FR-1.3、NFR-1）。以本專案的使用者規模，這是資料庫負載中可忽略的一項。

未被節流擋下的請求（絕大多數）**完全不觸碰資料庫寫入路徑** —— 判定所需的值已隨認證流程取得的使用者物件在手（iteration 1 實測確認認證依賴為所有認證請求的必經點，且該處已查出完整使用者物件），因此判定本身不產生任何查詢。這是本設計相對於「先讀再判斷」方案的關鍵成本差異。

### 延遲影響

**判定為「不需寫入」時**：新增成本是一次記憶體內的時間比較，對請求延遲無可測量的影響。

**判定為「需寫入」時**（iteration 1 Finding 12 補完）：新增兩項成本，而非初版所寫的一項。

1. 一次以主鍵定位的單列更新與提交 —— 對 PostgreSQL 是次毫秒級操作
2. **一次因工作階段過期而產生的使用者重讀** —— 既有的工作階段設定在提交後會使已載入物件過期（未關閉該預設行為），因此提交之後，後續的權限檢查讀取該使用者的角色與授權狀態時會觸發一次重新查詢

兩項合計仍是次毫秒級，且**每帳號每 5 分鐘至多發生一次**。requirements NFR-1 的效能約束在此設計下有明顯餘裕。

若日後量測顯示這次重讀值得消除，可在 Construction 以工作階段設定調整處理 —— 但那是最佳化，不是本設計的前提，本站不預先綁定實作。

### 擴展特性 —— 本設計的一項刻意保險

目前後端為**單一實例、單一 worker 程序**（iteration 1 實測確認容器啟動命令未指定 worker 數，且部署堆疊中後端無水平擴展）。

本設計的節流判定**不依賴這個事實**。判定基準是資料庫中的欄位值本身，而非任何程序記憶體狀態，因此：

- 加上多個 worker 程序 → 行為不變，節流仍然正確
- 加上多個後端實例 → 行為不變，節流仍然正確

這是選擇 C-1／C-2 這個形狀（而非程序內記憶體節流表）所換得的性質。若採用記憶體節流表，每個 worker 會各持一份快取，同一帳號的實際寫入頻率將變成 worker 數的倍數，屆時 requirements FR-1.3 的約束在字面上就會被打破，而**這個破壞不會有任何測試或告警發現** —— 它只會在有人擴容的那天悄悄發生。以近乎零的效能收益換取這個風險並不划算，故否決（`decisions.md` AD-1 替代方案 B）。

### 失敗模式

| 失敗 | 影響 | 處置 |
|---|---|---|
| 活動時間寫入失敗 | 該次活動未被記錄；顯示的時間偏舊 | **先復原工作階段**再記錄失敗，不影響使用者的原始請求。復原是必要的 —— 不復原則後續的權限檢查查詢會拋錯，原始請求照樣失敗 |
| C-3 補欄在啟動時失敗 | 欄位不存在，讀寫路徑皆報錯 | 沿用既有補丁機制的既有處置形狀（記錄警告後續行）；屬部署期問題 |
| C-7 權限套用在啟動時失敗或未命中 | 目標角色進不了管理頁 | **在既有測試路徑上無自動化驗證**（見下）；以啟動日誌的三態記錄 + 部署後人工核對承接 |
| 資料庫不可用 | 既有的全域失敗模式 | 本 intent 不改變既有行為 |

**本 intent 引入的唯一請求期失敗模式**（活動時間寫入失敗）已被設計為不可傳播至使用者請求 —— 但這只在 C-2 確實執行復原時成立，見 `component-methods.md` C-2 的交易契約。

### 資料生命週期

新欄位為單一時間戳，**每次寫入覆蓋前值，不累積歷史**（requirements FR-1.2）。這是 ideation 階段已定案的範圍界線：稽核需求只需要最後一次活動，不需要活動歷史。因此本 intent **不產生資料成長** —— 沒有需要輪替、封存或清理的資料，也不需要保留政策。

requirements FR-1.4 要求資料模型保留未來擴充為歷史紀錄的路徑；本設計的判定與理由見 `components.md` C-3。

## 對既有服務契約的影響

**回應形狀擴充但不破壞**：使用者物件的回應新增兩個欄位，既有欄位不變、不改名、不改型。既有的前端消費端在未更新的情況下仍能正常運作（多出的欄位被忽略），因此後端與前端的部署順序沒有硬性約束（前提是 C-6 的正規化，見 `component-dependency.md`）。

**沒有 API 版本問題**：新增可選欄位屬向後相容的變更，不需要新端點或版本協商。

**三個構造點必須同步**：requirements FR-2.5 要求所有回傳使用者物件的端點都包含此欄位（邊界定義見 `components.md` C-4）。實測**三處全部都是手寫具名引數構造**，其中兩處現行就已漏傳既有欄位 —— 這是本 intent 最容易在「看起來完成」的狀態下實際失敗的地方。

**權限機制不變、權限資料改變**：既有的端點層權限檢查機制完全不動；改的是權限表中一列的值，以及兩處預設值來源。詳見 `components.md` C-7。

### 測試義務對照

| 義務 | 來源 | 落點 |
|---|---|---|
| 授權矩陣 allow/deny 雙向測試 | requirements NFR-4、team-practices 規則 A | C-7 的**種子預設值變更**（見下方限制） |
| 端點需測試客戶端斷言 status code 與欄位集合 | requirements NFR-5、team-practices 規則 B | C-4（涵蓋三個構造點） |
| 前端資料形狀變更需 e2e 斷言 | requirements NFR-6、team-practices 規則 C | C-6 |
| 既有功能不得退化 | requirements NFR-7 | **本站不承載具體驗證設計**，屬測試策略／交付規劃階段 |

**NFR-4 雙向測試的涵蓋邊界（iteration 3 Finding M2，如實記載）**：實測測試輔助模組以強制模式直接由預設矩陣建表、**從不呼叫啟動流程**，因此雙向測試驗證的是**種子預設值是否已改**，**不涵蓋 C-7 在既有環境的套用** —— 把 C-7 整個刪掉，該測試照樣通過。初版把此失敗模式的處置寫成「需有測試涵蓋」是錯的，且與 `decisions.md` 自承「執行順序不會被測試保護」互相矛盾。

C-7 的套用結果因此以兩件事承接，並登錄為已知限制：①啟動日誌的三態記錄（已套用／已跳過／**未命中目標列**）；②部署後人工核對該角色確實能進入管理頁。

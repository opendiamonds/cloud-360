## US-1 兩類使用者看得到每個帳號的最後活動時間

> **As a** `Security_Reviewer`（主要）或 `Platform_Admin`（次要），
> **I want** 在使用者管理頁的每一列看到該帳號的最後活動時間，且格式可直接抄錄，
> **so that** 稽核者能判定帳號是否仍在使用並把時間值記入報告，管理者能在處置帳號時同一頁就掌握活躍度。

**優先序**：Must Have
**建置依賴**：無（可與 US-3 平行）
**驗收依賴**：US-3（稽核者需有權限才能親自驗收；管理者視角不受此限）
**涵蓋**：FR-1.1～FR-1.4、FR-2.1、FR-2.2、FR-2.5、NFR-1、NFR-5

### 驗收標準

**AC-1.1 活動產生紀錄**
- **Given** 一個帳號目前無活動紀錄
- **When** 該帳號以有效憑證發出任一需認證的請求
- **Then** 該帳號的最後活動時間被記錄為該請求發生的時刻

**AC-1.2 只保留最後一次**（獨立於節流條件）
- **Given** 一個帳號已有活動紀錄
- **When** 該帳號的最後活動時間被更新為新的值
- **Then** 系統中僅存在後一次的時間值，前一次不被保留（無歷史累積）

**AC-1.3 寫入節流（以可觀測狀態表述）**
- **Given** 一個帳號剛完成一次活動時間寫入，記錄時刻為 T
- **When** 該帳號在 T 之後未滿 5 分鐘內再次活動
- **Then** 該帳號的最後活動時間**仍為 T**（未被更新）
- **And** 距 T 滿 5 分鐘（含）之後的下一次活動，最後活動時間更新為該次活動的時刻

**AC-1.4 表格顯示位置與格式**
- **Given** 使用者已進入使用者管理頁
- **When** 頁面完成載入
- **Then** 表格出現「最後活動時間」欄，位置在「角色」之後、「操作」之前
- **And** 有活動紀錄的帳號以 `YYYY-MM-DD HH:MM` 格式顯示

**AC-1.5 API 回應契約完整**（取代原「操作後不變空白」的恆真 AC）
- **Given** 任一會回傳使用者物件的 API 端點
- **When** 該端點回應成功
- **Then** 回應中該使用者物件的最後活動時間欄位**帶有與資料庫一致的值**（有紀錄者為時間值，無紀錄者為明確的空值），而非因構造遺漏而缺失或為 `null`

**AC-1.6 時區一致性**
- **Given** 一個帳號在某個已知的絕對時刻活動
- **When** 稽核者在介面上讀取該帳號的最後活動時間
- **Then** 顯示的時間與該絕對時刻對應同一時點，不因寫入端與顯示端的時區處理差異而偏移

**AC-1.7 既有環境實際生效**（承 requirements C-2）
- **Given** 一個已存在資料的既有環境（非全新建立）
- **When** 本變更部署並完成服務重啟
- **Then** 既有帳號的資料表具備新欄位，且所有需認證的請求正常回應（不因欄位缺失而失敗）

**AC-1.8 上線日狀態為預期行為**（依 Q6=A）
- **Given** 本功能剛上線，尚無任何帳號產生過活動紀錄
- **When** 稽核者檢視使用者清單
- **Then** 全部列皆呈現無紀錄態、且無任何逾期標示
- **And** 此為**預期行為而非缺陷** —— 系統無可回填的歷史來源（requirements C-1）

**AC-1.9 載入與錯誤態沿用既有模式**（design 實測後補入）
- **Given** 使用者管理頁正在載入使用者清單，或載入失敗
- **When** 使用者檢視頁面
- **Then** 呈現方式與本變更前**完全相同** —— 整個表格區域被替換為單一的載入或錯誤訊息
- **And** **不**為新欄位單獨設計骨架佔位或單獨的錯誤呈現

### Definition of Done（交付條件，非行為驗收）

依 team-practices 的測試底線：

- 存在 `TestClient` 測試涵蓋**所有會回傳使用者物件的端點**，斷言回應中該欄位帶有與資料庫一致的值（不只是 key 存在）。已知的高風險落點為使用者清單端點與兩個更新端點（角色調整、啟停用）—— 後兩者正是既有 `requested_role` 漏傳缺陷的所在位置，新欄位若比照現行寫法會複製同一缺陷
- 存在 e2e 斷言表頭出現「最後活動時間」欄，且**至少一個有活動紀錄的帳號顯示對應時間值**（需在測試資料中準備有紀錄的帳號，否則斷言恆真）
- 節流與門檻判定的核心邏輯以純函式形式實作，使其可被單元測試直接驗證
- `schema_rbac.sql` 與 `DEPLOY.md` 同步更新（requirements C-4，blocking）

## US-2 稽核者一眼看出哪些帳號已逾期未活動

> **As a** `Security_Reviewer`，
> **I want** 超過 90 天未活動的帳號在清單中帶有明顯的視覺標示，
> **so that** 我不必逐筆計算日期差，能直接鎖定需要處置的帳號。

**優先序**：Must Have
**建置依賴**：US-1（標示疊加在時間值的顯示之上）
**涵蓋**：FR-2.3、FR-2.4、FR-3.1～FR-3.3、NFR-2

### 驗收標準

**AC-2.1 逾期標示與邊界判定**（邊界語意與 FR-3.1 對齊）
- **Given** 一個帳號的最後活動時間**早於**當下起算 90 天（即距今**超過** 90 天，不含恰為 90 天者）
- **When** 稽核者檢視使用者清單
- **Then** 該列的時間值前方顯示 `(!)` 圖示，且時間值以警示色呈現
- **And** 距今恰為 90 天或未滿 90 天的帳號**不**顯示該標示

**AC-2.2 標示不僅依賴顏色**（WCAG 2.1 AA）
- **Given** 一個帳號處於逾期狀態
- **When** 以不感知顏色的方式檢視（灰階顯示或螢幕閱讀器）
- **Then** 逾期狀態仍可辨識 —— 圖示與文字替代同時存在

**AC-2.3 無紀錄不套用逾期標示**
- **Given** 一個帳號從未產生活動紀錄
- **When** 稽核者檢視該列
- **Then** 該列**不顯示** `(!)` 圖示、時間值不變色

**AC-2.4 無紀錄態的呈現與可及性**
- **Given** 一個帳號從未產生活動紀錄
- **When** 稽核者檢視該列
- **Then** 該欄顯示破折號 `—`
- **And** 以鍵盤 Tab 可聚焦該元素並讀到說明文字

**AC-2.5 與既有空值符號可區分**（design 發現的既有衝突）
- **Given** 一個帳號同時處於「角色未指派」與「無活動紀錄」狀態
- **When** 稽核者檢視該列
- **Then** 兩欄的空值呈現**可被區分** —— 至少在可及性層面（活動時間欄可聚焦並有說明，角色欄不可聚焦）
- **And** 具體的視覺區分手段於 refined-mockups 定案

**AC-2.6 門檻不可由介面調整**
- **Given** 任何角色進入系統的任何頁面
- **When** 尋找調整 90 天門檻的設定
- **Then** 系統中不存在任何此類使用者介面

### Definition of Done

- 門檻比較邏輯以純函式實作並具備邊界單元測試（第 89 天、第 90 天、第 91 天）
- 日期計算不在 render 階段執行不純運算（避免觸發既有 lint 規則，requirements C-6 的同類約束）
- AC-2.2 的驗證方式明確標示為人工或無障礙工具輔助（現行工具鏈無自動化對比度檢查）

## US-3 稽核者能自行進入使用者管理介面

> **As a** `Security_Reviewer`，
> **I want** 自己就能進入使用者管理介面，
> **so that** 我取得稽核證據時不需依賴他人代為查詢，證據的即時性與完整性由我自己掌握。

**優先序**：Must Have
**建置依賴**：無（可與 US-1 平行）
**涵蓋**：FR-4.1～FR-4.3、NFR-3、NFR-4

### 驗收標準

**AC-3.1 稽核者可取用使用者清單**（以現行環境可執行的形式表述）
- **Given** 一個 `Security_Reviewer` 角色的已認證使用者
- **When** 請求使用者清單資料
- **Then** 請求成功，回應包含完整的使用者清單
- **And** 該角色的權限對照表中，使用者管理功能的檢視權限為啟用

**AC-3.1a 導覽入口可見**（介面層，驗收路徑見 DoD）
- **Given** `Security_Reviewer` 角色的使用者已登入介面
- **When** 檢視側邊導覽
- **Then** 「系統管理」區塊出現「使用者角色」入口
- **And** 點擊後可進入該頁面並看到完整使用者清單

**AC-3.2 未獲授權者不可存取**
- **Given** 一個未獲此授權的角色
- **When** 嘗試存取使用者管理功能
- **Then** 存取被拒絕

**AC-3.3 兩處預設值來源一致**
- **Given** 權限預設值存在於資料庫腳本與後端種子資料兩處
- **When** 本變更完成
- **Then** 兩處對該角色的權限值**相同**

**AC-3.4 既有環境實際生效**（developer 指出的缺口）
- **Given** 一個已完成權限初始化的既有環境
- **When** 本變更部署完成
- **Then** `Security_Reviewer` 在該環境**實際獲得**檢視權限（不因種子資料僅在空表時寫入而落空）

**AC-3.5 已知的範圍事實**
- **Given** `Security_Reviewer` 取得此檢視權限
- **When** 檢視其可存取的頁面
- **Then** 除使用者清單外，**升權申請佇列**亦可見 —— 此範圍經人工確認為可接受，非缺陷

### Definition of Done

依 team-practices 測試底線 A：

- 存在測試同時驗證「`Security_Reviewer` 可檢視」與「未獲授權角色不可檢視」（allow/deny 雙向）—— AC-3.1 與 AC-3.2 的自動化落點在此
- 存在自動化檢查驗證兩處權限預設值來源的一致性（可解析 SQL 種子與 Python 常數比對，零新依賴）
- 既有環境的權限套用路徑已於部署文件明載（requirements C-3 排除了重跑整份腳本）
- **AC-3.1a（導覽入口）的驗收缺口需有定論**：現行 e2e 環境不存在 `Security_Reviewer` 帳號（僅 seed 一位管理員，註冊路徑只得 `Developer`），故該 AC 目前無可執行的 e2e 路徑。交付規劃前須擇一：於 e2e 測試資料新增該角色帳號，或明確接受此 AC 以人工驗證。**不得默認略過**

## US-5 兩類使用者在帳號數成長後仍能逐頁查驗清單（**Revision 1 新增**）

> **As a** `Security_Reviewer`（主要）或 `Platform_Admin`（次要），
> **I want** 使用者清單以分頁方式載入、並有可切換頁次的控制，且我在某一頁做完處置後仍停在那一頁，
> **so that** 帳號數成長後這一頁仍然可用，而我逐帳號查驗的位置不會在每次處置後被丟失。

**優先序**：Must Have（scope Revision 2 的第六項能力，與其餘五項一起上線才算完成）
**建置依賴**：無技術依賴 —— 清單端點為既有功能
**排序約束（避免重工，非技術依賴）**：US-5 與 US-1 動的是**同一個清單端點的回應形狀**；若 US-1 先以裸陣列實作、US-5 再包上分頁結構，後端序列化、型別契約與前端消費端要各改一次。兩者的回應形狀須在同一次改動中決定。此性質承 scope Revision 2 對 PU-6／PU-5 的既有記載（**避免重工的排序約束，下游可在記明重工緩解方式的前提下覆寫**，與不可覆寫的技術依賴不同）。
**驗收依賴**：US-3（權限 —— 稽核者需有權限才能親自驗收）、**US-4**（AC-5.7 的小螢幕面需卡片佈局到位；Revision 1 mob 補）
**涵蓋**：FR-6.1～FR-6.7、**NFR-2**（AC-5.9 逐字援引其非色彩傳達要求）、NFR-8、NFR-9、NFR-10

### 驗收標準

> **Round 1（Revision 1 mob）整合說明**：design／developer／quality 三方盲審共提出 **29 項 OBJECT**，本節的 AC 已依其實測結果重寫。主要改動：三條恆真或不可二元判定的 AC（AC-5.2、AC-5.5、AC-5.8）移到會真的失敗的層次而非刪除（承 `project.md` `cid:user-stories:c4`）；新增 AC-5.10、AC-5.11 承接兩個先前無落點的已核可決定。

**AC-5.1 清單以頁為單位回傳**
- **Given** 系統中的帳號總數大於每頁筆數
- **When** 使用者清單端點被請求
- **Then** 單次回應包含的帳號筆數等於 **application-design 定案的每頁筆數設定值**（不是「回應自己回報的每頁筆數」—— 後者對 `per_page = len(data)` 的自我回報式實作恆真）
- **And** 該筆數**小於**帳號總數

**AC-5.2 分頁資訊三個值各自正確**（mob 改寫：由存在性斷言改為值斷言）
- **Given** 使用者清單端點回應成功
- **When** 檢視該回應
- **Then** **總筆數**等於系統中符合查詢條件的帳號總數（不是本頁筆數）
- **And** **目前頁次**等於請求的頁次
- **And** **每頁筆數**等於 application-design 定案的設定值
- **And** 帳號總數**少於一頁**時三個值仍各自正確（此情境是唯一能分辨「自我回報式實作」的情境 —— 回應模型帶預設值時，完全沒讀分頁參數的實作也會輸出三個 key）

**AC-5.3 切換頁次取得不同的帳號，且順序確定**
- **Given** 帳號總數需要至少兩頁才能容納
- **When** 使用者切換到第 2 頁
- **Then** 顯示的帳號與第 1 頁**沒有重複**
- **And** 兩頁的帳號合計涵蓋前兩頁份額的全部帳號（無遺漏）
- **And** 前兩個 Then 的適用前提為**本次瀏覽期間未發生刪除** —— 依 AC-5.6 就地刪除且不重抓時，資料庫端剩餘帳號會左移一格而下一頁仍由原 offset 起算，原本落在頁邊界的帳號因此可能不出現在任何一頁的渲染結果中。兩條 AC 在此前提外會字面衝突，**收斂手段（切頁時重抓、以最後一次切頁為準重算、或改用穩定游標）為 application-design 的開放決策**，與 AC-5.5 的分支選定同性質；本階段不預選
- **And** **重複請求同一頁得到相同的帳號與相同的順序** —— 分頁後必須保留確定且穩定的全序（現行 `list_users` 的 `order_by(User.id)` 提供此性質，分頁後不得移除）。無此保證時前兩個 Then 會退化為間歇性通過，而 `retries: 1` 與 `ui-regression` 對 `stats.flaky` 的容忍會把它當 flake 吸收掉

**AC-5.4 超出範圍的頁次為成功且為空**
- **Given** 帳號總數只需要 2 頁
- **When** 請求第 5 頁
- **Then** 回應為**成功**（非錯誤），資料清單為空
- **And** 總筆數與每頁筆數仍為正確值，**目前頁次回顯請求值 5**（不夾到最後一頁）
- **And** 介面呈現空態，且**分頁控制仍在畫面上**，使用者可直接選擇第 1 頁（本 And 獨立可失敗：照抄 AC-1.9 的「整塊替換」樣板會把分頁控制一併移除，此時前兩個 Then 仍全過而本條靜默失敗）

**AC-5.5 非法的分頁參數不進入資料查詢**（mob 改寫：原「拒絕或夾取」兩個互斥結果都通過，不是 pass/fail 判準）
- **Given** 使用者清單端點
- **When** 以非數值、負數或零作為**頁次**或**每頁筆數**發出請求，或以超過上限的每頁筆數發出請求
- **Then** 回應的狀態碼**不為 5xx**
- **And** 回應的帳號筆數**不超過每頁筆數上限** —— 這是本條的核心不變量：非法值原樣進入查詢層時，資料庫可能回傳整表剩餘全部（實測 SQLite：`LIMIT 5 OFFSET -5` 回 5 列、`LIMIT -1 OFFSET 3` 回整表剩餘），而回傳全表正是 NFR-8 要防的暴露面
- **And** 所選處置分支**可被觀察**：拒絕分支回 4xx 且不回傳任何帳號資料；夾取分支回 2xx 且回應**回顯夾取後的實際值**（否則夾取與「照收後回空清單」無法區分）
- **And** 本條與 AC-5.4 是不同判定：AC-5.4 的頁次**合法但超出範圍**（查詢成立、結果為空），本條的參數**型別或範圍非法**（查詢根本不該成立）

> **逐參數的分支選定（拒絕 vs 夾取）為 application-design 的記錄項** —— 兩條路對前端是不同契約（4xx 會觸發整塊錯誤畫面），本階段只定不變量，不代決。全 backend 目前無任何參數範圍約束的既有慣例可依（`grep "ge=\|le=\|gt=\|lt=" backend/` 零命中）。

**AC-5.6 頁面內處置後仍停在原本的頁次**
- **Given** 稽核者正在檢視第 2 頁
- **When** 對該頁的某個帳號執行停用（角色調整、刪除**各自**同理 —— 三者的既有路徑並不相同，見下方註）
- **Then** 畫面**仍在第 2 頁**，未回到第 1 頁
- **And** 該列的狀態已就地更新（刪除為就地移除該列），**未整份重抓清單**
- **And** 就地更新後，畫面上的**總筆數與總頁數**不得停留在已知錯誤的值 —— 刪除後總筆數本地遞減；若因此使目前頁次超出範圍（例如刪掉某頁唯一一列），以 AC-5.4 的空態處置承接
- **And** 操作**失敗**時亦不得把使用者彈回第 1 頁（現行 `AdminPage.tsx:91-94` 的 `catch` 呼叫 `fetchUsers()`，是 US-5 之後唯一殘留的整份重抓點）

> **三個操作的既有路徑不同，不可合併陳述**（承 `project.md` 上一個 stage 剛學到的 correction）：角色調整（`AdminPage.tsx:89`）今日已是就地更新，本 AC 對它接近恆真；**啟停用（`:113`）與刪除（`:129`）今日皆 `fetchUsers()` 整份重抓**，是本 AC 真正會抓到的行為變更。

**AC-5.7 兩種佈局皆可切換頁次，且提供同一組能力**（mob 改寫：原「語彙一致」與已核可線框直接矛盾且不可二元判定）
- **Given** 帳號總數需要至少兩頁
- **When** 分別在桌面寬度與斷點以下的小螢幕檢視
- **Then** 兩種佈局**皆可跳至特定頁次**（不只能逐頁前後移動）—— 已核可線框逐條否決游標式，理由正是「不能跳頁，回到先前看過的帳號只能逐頁往回」
- **And** 兩種佈局皆呈現：目前頁次、**總筆數**、前往上一頁／下一頁的方式（三者皆為線框已定案的控制項組成）
- **And** 切換後取得的帳號集合相同
- **And** 同一個邊界情境（例如第一頁的「上一頁」、只有一頁時的整組控制）在兩種佈局採取**同一種處置**（同為停用或同為隱藏，擇一由 refined-mockups 定案）
- **And** **視覺密度與標籤長短可以不同** —— 線框明訂小螢幕「因寬度較窄而簡化呈現」，要求外觀一致會使已核可的線框自身不通過本 AC

**AC-5.8 分頁回應中的欄位值與資料庫一致**（mob 改寫：原「同一帳號在任何頁次上標示相同」恆真 —— `isOverdue` 由呼叫端在抓取時算好傳入，頁次不進入判定路徑）
- **Given** 一個逾期帳號與一個無紀錄帳號都不在第 1 頁
- **When** 使用者**經由分頁切換路徑**（而非初次載入）取得該頁
- **Then** 兩者的最後活動時間與逾期旗標**帶有與資料庫一致的值**（非缺失、非 `null`），標示呈現與經初次載入路徑取得時**完全相同**
- **And** 落點理由：分頁 envelope 是**新的回應構造點**（與 US-1 DoD 點名的漏傳缺陷同型），而分頁切換是 `fetchUserList` 的**第三個呼叫點**（既有兩個各自更新 state）—— 逾期映射若寫在呼叫端而非單一抓取點，新增的切頁路徑很可能整頁不帶標示

**AC-5.9 分頁控制符合無障礙底線**
- **Given** 分頁控制已呈現
- **When** 以鍵盤或螢幕閱讀器操作
- **Then** 分頁控制可用鍵盤到達與**觸發**（WCAG 2.1.1；分頁按鈕是可觸發的互動元素，標準高於破折號的「可聚焦」）
- **And** 目前頁次可被輔助技術讀出，且**不僅以顏色**表達（NFR-2 的非色彩傳達要求）
- **And** 聚焦時有**可見的焦點指示**（checklist O-2／WCAG 2.4.7）
- **And** 小螢幕上每個分頁目標的觸控尺寸不小於 44x44（checklist O-5；US-4 的 AC-4.3 只綁三個**既有**操作，文義涵蓋不到本次新增的控制項，而小螢幕分頁 box 是本 feature 最擠的觸控區）

**AC-5.10 切換頁次期間分頁控制不消失**（mob 新增：三個已核可決定的算術結果）
- **Given** 使用者正在檢視第 N 頁
- **When** 觸發切換到另一頁，且新一頁的資料尚未到達
- **Then** 分頁控制**仍在畫面上**且目前頁次仍可辨識（不與表格／卡片一同被整塊替換）
- **And** 鍵盤焦點不因該次切換而離開分頁控制
- **And** 依據：分頁控制位於表格同一容器內下方（線框）＋ `isLoading` 為真時整個容器被單一訊息取代（`AdminPage.tsx:160-166`）＋ 既有重抓路徑一律先 `setIsLoading(true)`（`:53`）＋ C-6 要求沿用既有抓取形狀 —— 四者合起來，點「下一頁」會讓控制項在游標下消失、焦點退回 `document.body`、Tab 序從頁首重來（WCAG 2.4.3）。**手段留 refined-mockups**，但約束由本階段寫下

**AC-5.11 非分頁的查詢參數不改變結果**（mob 新增：承接 FR-6.7 在契約層的正向可測落點）
- **Given** 使用者清單端點
- **When** 以 `sort`／`order_by`／`filter` 等**非分頁**查詢參數發出請求
- **Then** 回應的帳號集合與順序**與未帶該參數時完全相同**
- **And** 系統中不存在依最後活動時間排序或篩選清單的使用者介面（與 AC-2.6 同型的不存在性子句，人工／靜態檢查）
- **And** 理由：分頁改的就是查詢參數面，順手加一個排序參數是最典型的越界；scope Revision 2 明文擔心的正是「下游把單一新增讀成整類已解禁」

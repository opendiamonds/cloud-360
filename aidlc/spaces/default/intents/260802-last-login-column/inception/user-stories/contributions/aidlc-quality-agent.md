### 2. 需要修正的 AC（附可直接取用的文字）

#### 2.1 AC-1.5／AC-3.3：Then 子句在現行實作下永遠為真

**實測證據**（`frontend/src/pages/AdminPage.tsx`）：

因此「操作後該列變為空白」這個 Then 在目前的程式碼路徑下**不可能發生**。照這條 AC 寫出來的 e2e 測試會在有缺陷與無缺陷的實作上同樣通過 —— 正是 `construction.md` 禁止的形狀。

> **AC-1.5 所有回傳使用者物件的端點都帶正確的欄位值**（防禦性，源自既有缺陷的教訓）
> - **Given** 某帳號在資料庫中的最後活動時間為一個已知的非空值 T

> - **Then** 三個回應中該帳號物件的最後活動時間欄位**皆等於 T**（不是缺欄、不是 `null`）

> **實作註記（給 construction）**：既有缺陷的具體形狀是 `user_router.py` 的 `update_user_active`（第 604–610 行）與 `update_user_role`（第 709–715 行）手工建構 `UserSchema(...)` 時漏傳 `requested_role`。新欄位若沿用同一個手工建構形狀，缺陷會原樣複製到這兩處。

#### 2.2 AC-1.6：斷言強度不足以抓到它要防的缺陷

現行 Then：「存在 `TestClient` 測試斷言該端點的 status code 與回應**欄位集合包含**新欄位」。

**問題**：若新欄位比照既有慣例宣告為 `Optional[datetime] = None`（`UserSchema` 的 `requested_role` 即是此形狀，`user_router.py:117`），則手工建構時漏傳 **Pydantic 仍會輸出該 key，值為 `null`**。欄位集合檢查會**通過**。FR-2.5 存在的唯一理由就是防這件事，而 AC-1.6 剛好驗不到。

建議改寫：

> **AC-1.6 端點測試涵蓋**（承 team-practices 測試底線 B）
> - **Given** 使用者清單端點的回應結構已變更
> - **When** CI 執行後端測試
> - **Then** 存在 `TestClient` 測試對 `GET /list`、`PUT /{user_id}/role`、`PUT /{user_id}/active` 三個端點各斷言：status code 為 200，且回應中該帳號的最後活動時間**值等於資料庫中的實際值**（僅斷言 key 存在不足以構成本 AC 的滿足）

#### 2.3 AC-5.5：「或」讓斷言恆真

**實測證據**：e2e 環境的 DB 由 `deploy/docker-compose.test.yml`（第 20 行）把 `schema_rbac.sql` 掛成 initdb 建立，該檔只 seed **一位** `admin`（第 497–510 行）；`database.py::init_db()` 的 11 位預設 persona 因 `user_count != 0` 不會 seed。也就是說**每一次 e2e run 的 DB 都是全新的，所有列的最後活動時間都是無紀錄態 `—`**。

現行 Then：「至少一列顯示時間值**或**無紀錄態的破折號 `—`」。在「後端完全沒有記錄任何東西、前端永遠渲染 `—`」的實作上，這條照樣通過。這正是 team-practices 的測試底線 C 所要擋的那條失敗路徑，寫成這樣等於自我抵銷。

建議改寫成兩條**可分別失敗**的斷言：

> **AC-5.5 前端斷言涵蓋**（承 team-practices 測試底線 C）
> - **Given** 前端的資料呈現形狀已變更
> - **When** CI 執行 e2e 測試（測試環境的資料庫每次為全新建立，初始全數為無紀錄態）
> - **Then** 存在測試斷言使用者管理頁的表頭出現「最後活動時間」欄
> - **And** 存在測試斷言：管理者登入並進入該頁後，**登入者自己那一列**顯示符合 `^\d{4}-\d{2}-\d{2} \d{2}:\d{2}$` 的值（此列的值由該次登入的活動本身產生；若後端未記錄，此斷言必然失敗）
> - **And** 存在測試斷言：至少一個從未活動的帳號那一列顯示破折號 `—`
>
> **設計約束（因本 AC 而生，須於 application-design 一併決定）**：登入者自己的活動寫入必須在**同一次頁面載入所取得的清單**中已可見，或明確定義「需重新整理一次才可見」；後者需在本 AC 對應的測試步驟中反映。此可見性時序若未定案，本 AC 的第二條斷言無法穩定實作。
>
> **前置成本揭露**：現行 6 個 e2e case 無一導覽至使用者管理頁（`frontend/tests/e2e/regression.spec.ts` 全檔實測：只在第 53 行斷言側欄連結「使用者角色」可見，未點擊進入）。本 AC 是第一個會實際進入該頁的 case。

#### 2.4 AC-1.3：觀察量選錯，且現行工具鏈無法測

三個獨立的阻礙，任一單獨成立即讓這條 AC 落不了地：

1. **「資料庫寫入次數」是實作內部量，不是可觀察行為。** 達成手段（節流／彙整／非同步）刻意留給 application-design（requirements OQ-1、`raid-log` R1）。手段未定時，「寫入次數」要用什麼方式觀察也就未定 —— AC 不該綁在一個尚未存在的觀察面上。
2. **無時間控制手段。** `backend/requirements.txt` 12 行依賴中**無 `freezegun`、無 `time_machine`**（本輪實測），現行測試也無任何時間注入設施。要驗「滿 5 分鐘後觸發第 2 次寫入」，在現行架構下只剩真的 `sleep(300)` —— CI 不可接受。
3. **無寫入計數設施。** `backend/tests/helpers.py` 的 session 是裸的 in-memory SQLite（第 25–35 行），沒有任何 flush/commit 計數 hook。

建議改寫為透過公開介面可觀察的行為契約，並把測試所需的接縫明確升格為設計約束：

> **AC-1.3 寫入節流（可觀察行為）**
> - **Given** 某帳號剛完成一次活動時間記錄，記錄值為 T
> - **When** 該帳號在節流間隔內再次發出任一需認證的請求
> - **Then** 該帳號的最後活動時間**仍為 T**（未推進）
> - **And** 距 T 滿一個節流間隔（含）之後的下一個請求，使該值推進為新的時刻
>
> **可測試性前置條件（application-design 必須滿足，屬 OQ-1 的附帶約束）**：所選手段必須讓**節流間隔與時間來源在測試中可注入或覆寫**。若兩者皆硬編在請求路徑上，本 AC 在現行測試架構（無 `freezegun`／`time_machine`）下只能以真實等待驗證，等同不可測。

同時建議把 requirements FR-1.3 已明訂的「滑動視窗，非固定時間桶」寫進 Given —— 現行 AC-1.3 只在 And 子句隱含這件事，讀 AC 的工程師會漏掉。並補一條 4:59 側的邊界（見 §3.2）。

#### 2.5 AC-4.3：兩處來源，只有一處進得了測試

**實測證據**：

- Python 側：`backend/tests/helpers.py:32` 呼叫 `ensure_role_permissions_seeded(db, force=True)`，seed 來源是 `rbac.py::DEFAULT_ROLE_PERMISSIONS`。
- SQL 側：`schema_rbac.sql:475` 的 `('Security_Reviewer', 'J3a', false, false, false)`，只在 e2e stack 的 initdb 被執行。

後果：**AC-4.2 的雙向測試即使全綠，SQL 側漏改仍然過關** —— 因為單元測試看不到 SQL 檔。而 e2e 也接不住（見 §2.6，測試環境沒有該角色的帳號）。所以 AC-4.3 的「任一處未同步即視為未完成」目前沒有任何自動化判定者，只能靠人工記得。

好消息是有一條零依賴的自動化路徑，且 team-practices 的「單一真實來源」條款本來就要求它（「新增副本的同一個 PR 必須一併新增鎖住兩者一致的測試」）。建議新增：

> **AC-4.3 兩處預設值來源同步（可自動化判定）**
> - **Given** 角色權限預設值同時存在於後端種子資料與資料庫初始化腳本兩處
> - **When** CI 執行後端測試
> - **Then** 存在一支測試解析初始化腳本中的權限預設值列（現行格式為 `('<角色>', '<story id>', <bool>, <bool>, <bool>),`，共 308 列），與後端種子常數比對，兩者的集合**完全相等**，任一側單獨變更即測試失敗
>
> **成本**：純 Python 字串解析與集合比對，零新依賴，可放進 `backend/tests/`，被現行 `python -m unittest discover -s tests` 自動撿到。

#### 2.6 AC-4.1：目前無法以 e2e 驗證，AC 未說明由誰驗

**實測證據**：e2e 環境只有 `admin`（`Platform_Admin`）一個帳號；`regression.spec.ts:56-74` 的註冊路徑取得的是 `Developer`。**沒有 `Security_Reviewer` 帳號可用**，所以「該角色登入後側邊導覽出現使用者管理入口」無法在現行 e2e 環境重現。

建議把驗收落到確實可行的層次，並誠實揭露若要 e2e 驗證的前置成本：

> **AC-4.1 稽核者可自行取用管理介面**
> - **Given** 一位角色為 `Security_Reviewer` 且授權狀態為已核准的使用者
> - **When** 以其身分呼叫使用者清單端點
> - **Then** 回應為 200 且包含完整使用者清單（`TestClient` 可驗）
> - **And** 前端的導覽入口與路由守衛以同一權限判定為條件（本項為靜態對照，非自動化斷言）
>
> **e2e 驗證的前置成本（若決定要做）**：測試環境須新增一個該角色的種子帳號。這會動到初始化腳本的 seed 語意，依 `project.md ## Mandated` 屬 blocking 的部署資產同步觸發條件（須同步 `schema_rbac.sql` 與 `DEPLOY.md`）。本階段不預作決定，但成本應被交付規劃看見。

#### 2.7 必然人工的三條，應明確標註驗證方式

**實測證據**：`frontend/package.json` 的 `devDependencies` 共 17 項，**無 `@axe-core/playwright`、無 `axe-core`、無 lighthouse**，唯一的測試依賴是 `@playwright/test`。team-practices Q4 已明確**不採 D**（不由本 intent 夾帶新前端測試依賴）。

因此：

- **AC-2.2**（不僅依賴顏色）：Playwright 可斷言「`(!)` 圖示元素存在」與「該元素有 accessible name」，這兩項是可自動化的**必要條件**；但「以灰階／螢幕閱讀器檢視仍可辨識」這個充分條件必然人工。建議把 AC 拆成可自動化的必要條件（寫成斷言）＋人工複核項（明確標註）。
- **AC-5.4**（對比 4.5:1）：**完全無自動化手段**。不建議刪除，但必須標註為人工／工具輔助的人工檢查，否則會被誤當成 CI 會擋的項目。
- **AC-2.5**（門檻不可由介面調整）：這是**全稱否定**，測試無法證明「不存在任何此類介面」。建議改為可判定的正面陳述：「門檻值以單一常數定義，且不由任何請求參數、環境變數或設定端點讀取」，並標註驗證方式為靜態檢查／code review。

統一建議：**在每條 AC 後面加一個「驗證方式」標記**（`自動化：後端`／`自動化：e2e`／`人工`／`靜態檢查`）。目前 23 條 AC 沒有任何一條標示驗證方式，讀者無從分辨哪些會被 CI 擋、哪些只是宣告。

#### 2.8 AC-1.2 與 AC-1.4 的加碼

- **AC-1.2**：現行 When 是「該帳號再次活動（**距上次寫入已滿 5 分鐘**）」。FR-1.2 只說「只保留最後一次的值，不保留歷史」，那是資料模型的斷言。加上節流條件之後，AC-1.2 變成必須先滿足 AC-1.3 才驗得了，喪失獨立性。建議 When 改為「該帳號的最後活動時間被更新為新的值」，Then 不變。
- **AC-1.4**：「有活動紀錄的帳號以 `YYYY-MM-DD HH:MM` 格式顯示，**可直接抄錄**」。「可直接抄錄」是主觀判斷，不可測（`inception.md`：避免無可量測門檻的模糊語）。建議改為「顯示值符合 `^\d{4}-\d{2}-\d{2} \d{2}:\d{2}$`」。

#### 2.9 US-3 三條 AC：沒有一條是可失敗的獨立驗收

- **AC-3.1**「角色、授權狀態、最後活動時間、可用操作皆在**同一列的視野內**」：「視野內」無可執行判準（哪個 viewport？是否允許捲動？），且與 AC-1.4 的欄位存在斷言重複。
- **AC-3.2**「操作行為與本 intent 之前**完全一致**，無新增步驟、無行為變更」：「完全一致」不可測。更關鍵的是 INVEST 表（`stories.md:181`）寫「AC-3.2 由既有 e2e 回歸涵蓋」—— **這與 repo 事實不符**：現行 6 個 e2e case 涵蓋登入、錯誤密碼、登出、工作區導向、兩條 RBAC 可視性，**無一執行任何 Admin 頁操作**（角色調整／啟停用／刪除全無測試）。「既有 e2e 回歸」在 Admin 頁上是空集合，這條 AC 目前沒有任何自動化守門者。
- **AC-3.3**：見 §2.1，建議刪除。

我不主張刪掉 US-3（次要 persona 的價值敘事有其意義，lead 的撰寫者註已說明），但這三條 AC 不應被計入「可驗收」的集合。若要保留可驗收的部分，AC-3.2 建議改為具體且可失敗的形式：

> **AC-3.2 既有操作不退化**
> - **Given** 管理者在使用者管理頁
> - **When** 執行角色調整與啟停用
> - **Then** 兩項操作皆成功完成，且操作後清單中該帳號的角色／啟用狀態反映變更後的值
>
> **前置成本揭露**：現行 e2e 對此頁的操作零覆蓋，本 AC 需新增 e2e case，非「既有回歸涵蓋」。

### 3. 邊界條件的遺漏

#### 3.1 90 天門檻的邊界完全沒有 AC

FR-3.1 寫「**超過** 90 天未活動」，AC-2.1 寫「**早於**當下起算 90 天」。恰好第 90.0 天算不算逾期，兩份文件都沒有定。`inception.md` 要求「每個需求都要有明確的 pass/fail 判準」，這裡沒有。建議補：

> **AC-2.6 逾期門檻的邊界**
> - **Given** 三個帳號的最後活動時間分別為當下起算的 89 天前、90 天前、91 天前
> - **When** 稽核者檢視清單
> - **Then** 89 天前者**不**帶逾期標示；91 天前者**帶**逾期標示
> - **And** 恰好 90 天前者的判定為 `<待定：> 逾期／不逾期`（本項須先定案再實作，不得由實作決定）
>
> **測試註記**：三個 fixture 皆以「相對於當下的時間差」建立（非絕對時間字串），以避免測試在 in-memory SQLite（不保存時區）與 Postgres（`DateTime(timezone=True)`）之間行為分歧。

#### 3.2 節流的另一側邊界沒有 AC

AC-1.3 的 And 已寫「滿 5 分鐘（含）之後的下一個請求」（承 FR-1.3 的滑動視窗定義，這點寫得好）。但**未滿**的那一側只有籠統的「5 分鐘內連續發出多個請求」，沒有貼邊的案例。建議在改寫後的 AC-1.3 補一條：「距上次記錄 4 分 59 秒時的請求**不**使該值推進」。

#### 3.3 時區完全沒有被處理 —— 這是稽核證據的正確性問題，不只是顯示細節

實測到的分歧：

- `backend/models.py` 的時間欄位一致使用 `DateTime(timezone=True)` 搭配 `server_default=func.now()`（第 65、67、84、105、132、134、149、151、169 行）。
- 但 `backend/services/auth.py:32` 的 `create_access_token` 用的是 **naive 的 `datetime.utcnow()`** —— 同一個 codebase 對時區並不一致。
- `wireframes.md:31` 的顯示樣例是 `2026-08-03 14:52`，**不帶任何時區標記**。

對這個 intent 而言這不是小事：US-1 的整個價值主張是「取得可抄錄、可比對的稽核證據」。若顯示值是 UTC 而稽核者假定 UTC+8，抄進報告的證據就差 8 小時；若 90 天比較在前端以 `new Date()` 解析一個無時區字串，邊界判定也會跟著偏移。23 條 AC 中**沒有任何一條**觸及這件事。建議補：

> **AC-1.7 時間值的時區語意**
> - **Given** 某帳號的最後活動時間已被記錄
> - **When** 稽核者在使用者管理頁檢視該值
> - **Then** 顯示值為 `<待定：UTC／伺服器時區／瀏覽器本地時區>`，且該語意在畫面上對稽核者是明確的（例如欄位標題或說明文字載明）
> - **And** 逾期判定所用的時間基準與顯示值的時間基準**為同一個**，不得一個用伺服器時間、另一個用瀏覽器時間
>
> **待定項**：時區語意的選定屬 application-design／refined-mockups，但**必須在實作前定案**，否則稽核證據的正確性無法驗收。建議一併登記為 open question。

### 7. Given/When/Then 的形式正確性

- **AC-1.6、AC-4.2、AC-5.5** 三條的 GWT 是**元層次**的：Given「回應結構已變更」／When「CI 執行測試」／Then「存在測試斷言…」。它們描述的是「有沒有寫測試」，不是系統行為。這是把 checklist 套進 GWT 的殼。這件事本身可以兩種立場並存（見 Positions 的判斷題），但它有一個**實質後果**：這種形狀讓 AC 只驗「有寫測試」、不驗「斷言夠不夠強」，正是 §2.2 與 §2.3 兩個漏洞的成因。我上面給的改寫版把 Then 具體化到斷言內容，兩種立場都能滿足。
- **AC-2.5、AC-3.1、AC-3.2** 是狀態描述而非行為場景。AC-2.5 的 When「尋找調整門檻的設定」不是可執行的使用者動作。
- **AC-2.3 與 AC-2.4** 的 Given／When 逐字相同，只有 Then 不同。分成兩條可以接受（一條驗否定、一條驗肯定），僅提示可考慮合併以降低閱讀成本。

### R1-2. AC-5.2「三個數值皆存在」是同一個弱斷言陷阱（回答派工第 3 項）

**是，與 `project.md` 為最後活動欄位記載的「不只是 key 存在」是同一型。** 而且 US-1 的 DoD 自己已經把這個教訓寫進去了（第 127 行：「斷言回應中該欄位帶有與資料庫一致的值（**不只是 key 存在**）」），US-5 的 AC-5.2 卻退回到存在性斷言。

具體機制：分頁 envelope 必然是一個 Pydantic 回應模型。只要欄位宣告帶預設值（`page: int = 1`、`per_page: int = 20`、`total: int = 0`），**即使查詢層完全沒讀取 `page`／`per_page` 參數**，回應照樣輸出三個 key 且皆為數值 —— AC-5.2 主句原文「回應中同時帶有總筆數、目前頁次、每頁筆數三個數值」會通過。三值中只有「總筆數」有值斷言（`And` 子句），「目前頁次」與「每頁筆數」只有存在性。

AC-5.1 有連帶問題：「單次回應包含的帳號筆數**等於每頁筆數**」——若「每頁筆數」取自回應本身，一個回傳 `per_page = len(data)` 的實作使該子句恆真；真正承重的是後半句「且小於帳號總數」。自我回報的值不能拿來當自己的錨。

**建議改寫 AC-5.2 的 Then／And（可直接取用）**：

- **Then** 回應的「每頁筆數」**等於 application-design 定案的設定值**，而非本頁實際回傳的筆數
- **And** 「目前頁次」**等於請求所指定的頁次**（未指定時為第 1 頁）
- **And** 「總筆數」等於系統中符合查詢條件的帳號總數，不是本頁筆數
- **And** 當帳號總數**少於一頁**時，上述三值仍各自正確（此時本頁筆數 < 每頁筆數，可分辨「把 `len(data)` 當成每頁筆數回報」的實作）

最後一條是關鍵：它是唯一能把「自我回報式實作」與「真的有讀參數的實作」分開的情境，而且零成本（`backend/tests/helpers.py:46` 的 `make_user` 造帳號不經 bcrypt，`password_hash="unused"`）。

### R1-5. AC-5.8 恆真，但防禦意圖是真的 —— 改寫到會壞的那一層

AC-5.8 現文：「同一帳號因頁次切換而出現在不同的頁上，其逾期標示與無紀錄態的呈現完全相同，判定不因它在第幾頁而改變」。

**建議改寫 AC-5.8（可直接取用）**：

**AC-5.8 分頁封裝不得損及每列的資料內容**

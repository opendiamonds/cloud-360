## Q1. 切分方案

> 七個元件要切成幾個 work unit。下列三案的差別不在「粗細偏好」這種抽象取捨，而在**哪些東西被綁在同一個交付單位裡**，那會直接決定哪些工作能並行、哪些必須排隊。

A. **四單元：規則與寫入 / 序列化 / 前端 / 權限** — **（建議）**
   - `U1 後端規則與活動記錄`（C-1、C-2、C-3）· `U2 使用者物件序列化`（C-4）· `U3 管理頁欄位呈現`（C-5、C-6）· `U4 權限開通`（C-7）
   - 每個單元對應**一條可獨立驗證的路徑**：U1 是寫入路徑、U2 是讀取契約、U3 是呈現、U4 是授權。四者各自有明確且不重疊的測試落點（U1 純函式與 property-based、U2 端點測試、U3 Playwright、U4 授權雙向測試），對應 team-practices 的三項測試底線 A/B/C 剛好各就各位。
   - **U4 可與 U1 完全並行**（零耦合，不同資料表），U2 只需要 U1 的 C-1／C-3 就緒。
   - 代價：四個單元對一個加欄 feature 略顯多。但這裡的「多」不是儀式成本 —— 四條路徑本來就要分別驗證，切開只是讓「哪條還沒好」變成可見的事實。

B. **兩單元：後端 / 前端** — `U1 後端`（C-1〜C-4、C-7）· `U2 前端`（C-5、C-6）
   - 好處：最少的單元數，DAG 只有一條邊。
   - 代價：把權限開通（C-7）和欄位功能綁進同一個交付單位，而兩者**零耦合且風險性質完全不同** —— C-7 是靜默落空型風險（無自動化驗證、需人工核對），欄位功能是有測試涵蓋的。綁在一起會讓「後端完成了嗎」變成一個模糊的問題。寫入路徑與讀取契約也被綁死，無法分別判定完成。

C. **五單元：把 C-3（資料模型與補欄）獨立** — 在 A 的基礎上把 schema 變更抽成 `U0 資料模型與補欄`
   - 好處：schema 是 U1 與 U2 的共同前置，獨立出來讓「欄位存在了嗎」成為單獨可判定的事實；且它有 requirements C-4 的 blocking 同步義務（`schema_rbac.sql` + `DEPLOY.md`），獨立單元讓那個義務有明確歸屬。
   - 代價：U0 本身極小（一個欄位定義 + 一個補欄函式 + 兩份文件同步），單獨成一個單元的管理成本相對於內容偏高；且它與 U1 的其餘部分幾乎必然一起做。

## Q2. 單元間的整合契約以什麼為準

> U2（序列化）與 U3（前端）之間需要一個契約：前端依賴後端回應裡有那兩個欄位。這個契約用什麼形式固定下來，決定了「後端改了形狀而前端不知道」這件事會不會被發現。
>
> 背景事實（team-practices 已記載）：前端的使用者型別是**手寫的本地 interface**，資料抓取以 `await res.json()` 直接放行，**與後端的回應模型沒有任何編譯期連結**。`tsc -b` 對這條落差無效。

A. **以 U2 的端點測試作為契約，前端型別手動對齊** — **（建議）**
   - U2 的測試客戶端測試斷言回應的欄位集合（requirements NFR-5、team-practices 規則 B），該斷言就是契約的可執行形式；U3 的手寫型別依此對齊，並由 U3 自己的 Playwright 斷言（規則 C）驗證實際渲染。
   - 這是**零新依賴**且與既有實務一致的做法：兩端各自有能失敗的測試，落差會在其中一端亮紅燈。
   - 代價：型別對齊仍是人工的，後端改欄位名時前端不會自動報錯 —— 但那個缺口是既有的（52 處 `fetch` 皆如此），本 intent 不擴大也不修復它。

B. **引入前後端共用的型別產生機制**（如自 OpenAPI 產生 TypeScript 型別）
   - 好處：從根本消除手寫型別漂移。
   - 代價：新增工具鏈與建置步驟，屬獨立的基礎設施決策，成本遠超一個加欄 feature —— 與 practices-discovery 對前端測試框架、AD-3 對 migration 工具的判斷同理，不應由本 intent 夾帶。

C. **以文件（本站的 artifact）為契約，不要求測試**
   - 代價：文件不會失敗。這正是 team-practices 本輪新增規則 B／C 要解決的問題。

## Q3. 並行度的表達方式

> 本站產出的 DAG 會被下一站（Delivery Planning）用來排 Bolt。DAG 要表達成「嚴格線性」還是「標出可並行集合」？
>
> 注意：這**不是**在問實作順序（那是 2.8 的決定），而是在問本站要不要把「哪些單元之間沒有依賴」這個事實明確標出來。

A. **標出可並行集合，保留多條合法拓樸序** — **（建議）**
   - DAG 只記錄真實存在的依賴邊，不新增為了排序方便而虛構的邊。無依賴關係的單元（例如權限開通與其他三者）明確標為可並行。
   - 這正是 stage 檔要求的形狀（「Parallel development opportunities — 多條合法拓樸序存在」），也讓 2.8 有真正的選擇空間 —— 若本站先把它壓成一條線，2.8 的經濟決策就沒有東西可決定了。
   - 代價：無 —— 標出並行不等於要求並行，2.8 仍可選擇序列執行。

B. **壓成單一線性序** — 直接給一條建議順序。
   - 代價：**違反本站的範圍界線**（stage 檔明文「2.7 MUST NOT recommend an implementation order or identify a critical path」），且會把 2.8 的決策空間預先關掉。

## Q4. C-9 橫跨前後端，要獨立成單元、拆成兩半併入既有單元，還是整個併入一個既有單元？

> C-9 的兩半驗證方式**不同類**：後端部分（分頁查詢、envelope、422）由 `TestClient` 端點測試驗，失敗模式是「回應形狀或狀態碼錯」；前端部分（分頁控制、切頁、處置後維持頁次）由 Playwright e2e 驗，失敗模式是「畫面沒有控制項或頁次跳走」。既有的 Q1a 正是以同一判準把 C-8 獨立為 U5。

A. **拆成兩半併入既有單元：後端併 U2（`user-object-serialization`）、前端併 U3（`admin-page-column`）** —— **（建議）** 三個理由：①**驗證方式完全同類** —— C-9 後端與 C-4 都由 `TestClient` 斷言**同一個端點**的回應，application-design 已把 envelope 定位為「本 intent 的第四個回應構造點」，與 C-4 的三個構造點是同一類失敗模式；C-9 前端與 C-5／C-6 都由 e2e 斷言同一個頁面。②**動同一段程式碼** —— C-9 前端與 U3 修改同一段 JSX，stories 明載這類變更「須序列合併避免衝突」；拆成不同單元不會消除衝突，只會讓衝突跨單元。③不新增單元編號，拓樸維持五個單元。代價：U2 與 U3 的範圍變大（AC 數各 +7），複雜度需重評。
B. 獨立為第六個單元 U6 —— 好處：C-9 的身分清楚。代價：**它的兩半驗證方式不同類**，U6 內部會同時存在兩種不可互相替代的完成判準，正是 `cid:units-generation:c6` 所指的反例；且前端半仍與 U3 動同一段 JSX，衝突照舊、只是跨了單元。
C. 整個併入 U3 —— 代價：把改變 API 回應契約的能力歸進顯示類單元，直接違反 `project.md` 的 `cid:scope-definition:rev2-c1`（改變 API 回應契約的能力不得被歸類為顯示類能力的完成條件）。
D. 拆成兩半但各自獨立為 U6／U7 —— 代價：U7（前端）與 U3 動同一段 JSX 卻分屬兩個單元，製造跨單元的合併約束；且兩者的驗證落點完全重疊（同一批 e2e），湊不出各自獨立的完成判準。

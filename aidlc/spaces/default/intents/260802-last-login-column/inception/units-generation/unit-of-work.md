## 本站的範圍界線

本站只描述**拓樸**：有哪些單元、各自擁有什麼、誰能依賴誰、哪些之間沒有依賴。

**不決定實作順序，也不指出關鍵路徑** —— 那是下一站 Delivery Planning 的經濟決策。下方任何清單的排列順序都不隱含先後。

## 切分依據

切分的接縫直接來自 application-design 的依賴矩陣，不是另行推導的：

- **C-1、C-3、C-5、C-7 皆為葉節點**（不依賴任何元件）
- **C-2（寫入）與 C-4（讀取）互不依賴**，只透過 C-1 與 C-3 間接關聯
- **C-7（權限）與其他元件零程式碼耦合** —— 動的是不同資料表
- **C-8（型別契約）完全在建置期**，不進執行路徑

每個單元對應**一條可獨立驗證的路徑**，且各自的測試落點不重疊 —— 這正是 Q1 選 A 的理由，Q1a 選 A 是同一個理由延伸到 C-8。

## U1 `backend-activity-policy`（service）

**擁有**：C-1（活動時間政策）、C-2（活動時間記錄器）、C-3（使用者資料模型與既有庫補欄）

**交付什麼**：讓「任何認證請求都更新該帳號的最後活動時間，且同一帳號每 5 分鐘至多寫一次」這件事成立。

**部署模型**：隨既有後端服務部署，不新增執行單元。**部署後必須完成一次服務重啟**，補欄才生效（requirements C-2、stories AC-1.7）。

**驗證落點**：
- C-1 的兩個判定為純函式，可直接斷言邊界（恰好 5 分鐘含等於、恰好 90 天不含等於、無紀錄態）
- **ADR-0006 的 property-based hard constraint**（來源為 `project.md`，**非 requirements** —— requirements 全文無此條文）在本 intent 的落點就是這裡。附帶說明：team-practices 已判定該約束原本點名的三個模組在本 repo 尚無對應實作，故其現況為 N/A；C-1 是本 intent 自願提供的落點

**已知的驗證缺口（如實記載，與 U4 同型）**：

`services.md` 的測試義務對照四項全部落在 C-7／C-4／C-6／C-8，**無一落在本單元**。具體兩處：

- **C-2 的交易契約（自行提交、失敗先復原）無自動化驗證** —— 純函式測試不碰資料庫，U2 的端點測試只斷言回應欄位集合，兩者**結構上都抓不到**「提交了沒有」。
- **C-3 的既有環境補欄（AC-1.7）無自動化驗證** —— 測試輔助模組以強制模式直接建表、從不呼叫啟動流程。stories 已實測記載此失敗模式：只改模型而不補啟動補丁，staging 上每個已認證請求都會失敗，**而 CI 全綠**。

承接方式：部署後重啟 + 人工核對。**這使「五個單元各有明確且不重疊的驗證方式」對本單元是過度宣稱** —— 正確的表述是分級的，見文末「驗證強度分級」。

**實作注意（來自設計的 blocking 約束）**：
- **C-2 必須自行提交** —— 既有的工作階段供應器不提交，唯讀端點本身也不提交，不做則寫入被整個丟棄
- **失敗必須先復原再記錄** —— 不復原則後續權限檢查查詢會拋錯，使用者請求照樣失敗
- 所有時間值為帶時區 UTC；測試環境讀回不帶時區，需正規化
- requirements C-4 的同步義務（blocking）：schema 檔與部署文件

## U2 `user-object-serialization`（service）

**擁有**：C-4（使用者物件序列化）

**交付什麼**：所有回傳使用者物件的端點都包含新欄位（requirements FR-2.5）。

**部署模型**：隨既有後端服務部署。

**驗證落點**：測試客戶端測試斷言 status code 與回應欄位集合（requirements NFR-5、team-practices 規則 B）。這是本 intent 中**唯一**能自動抓到「某個端點漏了欄位」的機制。

**實作注意（本 intent 最容易「看起來完成」卻實際失敗的地方）**：
- 回應模型在**三處**被構造（清單、啟停用、角色調整），**三處全部是手寫具名引數**，且後兩者現行就已漏傳既有的一個欄位
- 兩個新欄位**不得設可靜默通過的預設值**，或改走單一共用工廠函式
- ORM 自動轉換**不是可行選項** —— 逾期旗標是衍生值，ORM 物件上不存在

## U3 `admin-page-column`（ui）

**擁有**：C-5（最後活動時間儲存格）、C-6（管理頁資料傳遞）

**交付什麼**：稽核者在管理頁看得到每個帳號的最後活動時間，含無紀錄態與逾期標示，且小螢幕可用。

**部署模型**：隨既有前端映像部署。

**驗證落點**：Playwright e2e 斷言表頭出現該欄位、且至少一列顯示時間值或無紀錄態的破折號（requirements NFR-6、team-practices 規則 C）。這是目前**唯一**能碰到管理頁的自動化層。

**實作注意**：
- 使用者物件型別**採用 U5 產生的型別**，不再手寫
- 傳遞前需正規化（後端未部署時欄位為未定義，而儲存格的 props 不含未定義）
- 逾期旗標**由後端傳入**，不在算繪過程計算（避免 lint 規則違反）
- 載入態、錯誤態、既有的角色欄空值呈現**皆不動**
- **顯示端的在地化策略須於 Construction 定案**（AC-1.6 的驗收面）：`components.md` C-4 定案「回應一律為 UTC，顯示端負責在地化」，而 `refined-mockups/` 全目錄無任何時區規則 —— 「拿到 UTC 字串後是否換算本地時間」目前無人決定。直接截斷 ISO 字串呈現會讓時間整體偏移一個時區位移量，AC-1.6 直接失敗

## U4 `security-reviewer-permission`（service）

**擁有**：C-7（權限預設值變更與既有環境套用）

**交付什麼**：目標角色取得使用者管理介面的檢視權限，且該變更在既有環境**真的生效**。

**部署模型**：隨既有後端服務部署；套用發生在啟動流程。

**驗證落點**：授權矩陣的 allow/deny **雙向**測試（requirements NFR-4、team-practices 規則 A）。

**已知的驗證缺口（如實記載）**：雙向測試涵蓋的是**種子預設值變更**，**不涵蓋既有環境的套用** —— 測試輔助模組以強制模式直接建矩陣、從不呼叫啟動流程，把 C-7 整個刪掉該測試照樣通過。套用結果以啟動日誌的三態記錄 + 部署後人工核對承接。

**實作注意（設計中最嚴格的順序契約）**：
- **必須在既有權限種子之後執行**，且**只更新不插入** —— 順序或插入行為錯誤會讓整份 308 列預設矩陣不被建立，全系統 RBAC 端點盡數拒絕存取，而**沒有任何測試會發現**
- 條件式套用以既有的「最後異動者」欄位為標記
- requirements C-3 禁止以重跑整份初始化腳本作為套用手段
- **交易語意須自行負責**（application-design 的殘留項，本站更正歸屬）：沿用既有補丁的 `with engine.begin()` 先例即正確；但若改用啟動流程的既有 session 而未自行提交，寫入會被靜默丟棄 —— 屆時啟動日誌會報「已套用」而權限實際未變，與本單元既有的「無自動化驗證」疊加成雙重靜默

## U5 `api-type-contract`（packaging）

**擁有**：C-8（API 型別契約產生）

**交付什麼**：後端回應形狀與前端型別之間一條**編譯期會失敗**的連結。

**Kind 為 `packaging` 的理由**：它不是被部署的執行單元，也不是業務邏輯 —— 它產出的是建置與 CI 的資產（腳本、規格檔、型別檔、兩道 gate）。**完全在建置期，不進生產環境的執行路徑。**

**部署模型**：**無** —— 不部署。產出物隨 repo 進版控，型別檔隨前端映像建置被編譯掉。

**驗證落點**：兩道 CI 漂移檢查本身即為驗證機制 —— 規格檔的在 backend job、型別檔的在 frontend job。

**但這是自我驗證**：交付物即 gate，沒有任何外部機制驗證這兩道 gate 本身有效（例如被寫成永遠通過的形式）。**採用時須以一次刻意的漂移實測**（改一個欄位名而不重新 dump，確認兩道 gate 確實變紅），否則無從得知它們是否真的會失敗。

**實作注意**：
- 型別產生**不進 `npm run build`**；型別檔 commit 進前端原始碼目錄
- 規格檔置於 repo 根目錄，**不得**落在會被靜態服務原樣供出的路徑
- 產生器**只得輸出型別宣告**，不得輸出進入 bundle 的執行期程式碼
- 兩支關鍵函式庫需**精確等值**釘選；升版時須在同一 PR 內重新 dump 規格檔
- 新增 devDependency 需一併重產並 commit 依賴鎖定檔
- 型別檔是否納入 lint 作用域須於採用時定案

## 部署模型總覽

**所有單元共用同一次部署**（既有的 deploy-on-merge 至自有 staging），因為 application-design 已定案不新增服務、不新增執行單元、不新增部署單元。

| 單元 | 部署形式 |
|---|---|
| U1、U2、U4 | 隨既有後端服務 |
| U3 | 隨既有前端映像 |
| U5 | **不部署**（建置期資產） |

U1 與 U4 的變更**在服務重啟時才生效**（補欄與權限套用皆在啟動流程），這是 requirements C-2 的直接後果，非可選的維運建議。

## 驗證強度分級（誠實表述，取代「五個單元各有明確驗證」的籠統宣稱）

| 級別 | 單元 | 說明 |
|---|---|---|
| **有可執行的自動化斷言** | U2、U3 | 端點測試斷言欄位集合；Playwright 斷言表頭與列值。兩者皆能真的失敗 |
| **有斷言但涵蓋不全，缺口已記載** | U4 | 授權雙向測試只涵蓋種子預設值變更，不涵蓋既有環境的套用 |
| **關鍵契約無自動化驗證，缺口已記載** | U1 | C-2 的交易契約與 C-3 的補欄皆無機制驗證（見 U1 段） |
| **自我驗證** | U5 | 交付物即 gate；gate 本身的有效性須以刻意漂移實測 |

「每個單元對應一條可獨立驗證的路徑」在**職責邊界**的意義上成立（各單元的驗證對象互不重疊），但**驗證強度不齊** —— 這是切分本身無法解決的，來自 repo 既有的測試涵蓋現況。

## 非依賴的交付約束

以下不是依賴（不影響誰能先做），但會影響交付時的合併方式，來自 stories 的既有記載：

- **U3 內部的三則故事修改同一段前端程式碼**（US-1 的欄面、US-2 的標示、US-4 的卡片佈局）—— stories 明列「必須序列合併以避免衝突」。這是同一單元內的事，不跨單元。
- **驗收依賴**：`Security_Reviewer`（主要 persona）要親自驗收 U1／U2／U3 交付的「看得到最後活動時間」，需要 U4 已到位（否則進不了管理頁）。stories 明文將此與建置依賴區分保留。**這不是程式碼依賴**，不進 DAG；但在 deploy-on-merge 之下它是下一站排序時的真實輸入。

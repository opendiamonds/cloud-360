## 本檔只做對應

每條 AC 落在哪個單元。**不排順序** —— 表格內的 AC 排列不隱含實作先後。

**關於 stage 檔要求的「單元內的故事實作順序」**：stage 檔 Step 6 對 story map 列了四項產出，其中「Story implementation order within each unit」本檔**刻意不給**，理由如下（記為已聲明的 deviation 而非缺項）：

- 本站的 MUST NOT 條款約束的是**單元層**的實作順序與關鍵路徑；單元內的故事序不在禁令範圍內，本可產出。
- 但實際檢視後，**只有 U3 承載多於一則故事**（US-1、US-2、US-4），其餘四個單元各只承載零或一則。為單一故事的單元排「內部順序」沒有內容。
- U3 內部確實有一條技術前後關係（欄面 → 標示 → 卡片佈局，因卡片改造以最終欄面為輸入），但那條關係**已由 stories 的建置依賴記載**（US-1 → US-2 → US-4），本站重述只會製造第二份可能漂移的副本。
- 因此本檔以「指向上游既有記載」取代「重新產出一份順序」。若下游需要單一來源，應讀 stories 的優先序與依賴總覽。

## 測試底線的分佈

team-practices 本輪新增的三項測試底線，在單元間**不重疊**：

| 底線 | 落在 |
|---|---|
| A — 授權矩陣變更需 allow/deny 雙向測試 | U4 |
| B — 新增或修改 HTTP 端點需測試客戶端測試 | U2 |
| C — 前端資料形狀變更需 e2e 斷言 | U3 |

U1 的 C-1 落在既有的純函式測試實務（含 property-based）；U5 的驗證機制是它自己交付的兩道 CI 漂移檢查。

**但驗證強度不齊，這是誠實的表述**（初版寫「五個單元各有明確且不重疊的驗證方式」是過度宣稱，已更正）：

| 級別 | 單元 |
|---|---|
| 有可執行的自動化斷言 | U2、U3 |
| 有斷言但涵蓋不全（缺口已記載） | U4；**U3（Revision 1 追加 —— 無障礙面）** —— AC-5.9 的八項義務中四項必然人工（無 axe、無 jsx-a11y），且「屬性存在」型斷言有已記載的弱點（掛錯元素照樣通過） |
| 關鍵契約無自動化驗證（缺口已記載） | **U1** —— C-2 的交易契約與 C-3 的補欄皆無機制驗證 |
| 自我驗證（交付物即 gate） | U5 |

切分讓**驗證對象**互不重疊（這是 Q1=A 與 Q1a=A 的核心理由，仍然成立），但**驗證強度**的落差來自 repo 既有的測試涵蓋現況，不是切分能解決的。完整分級見 `unit-of-work.md` 的「驗證強度分級」。**兩檔的分級表逐格相同**（reviewer Revision 1 Finding 3 指出 Revision 1 初稿只更新了 `unit-of-work.md` 一側、使兩檔重新分歧，已同步）。

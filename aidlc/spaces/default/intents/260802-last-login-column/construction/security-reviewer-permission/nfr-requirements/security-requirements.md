# Security Requirements — U4 `security-reviewer-permission`

> Stage: nfr-requirements（Construction 3.2）· Unit: `security-reviewer-permission`（kind: service）
> 上游來源：`../functional-design/business-logic-model.md`、`business-rules.md`、`domain-entities.md`、`../../../inception/requirements-analysis/requirements.md`（下稱 requirements）、`../../../inception/application-design/components.md` C-7、`component-methods.md`、`decisions.md`、`services.md`。
> 問答定案：Q1=A（high-risk 條款**適用**，三項寫進本站 artifact）、Q2=A（rollback 為管理員經介面撤銷）。

## 本單元是 ADR-0006 IAM 面向的落點

requirements NFR-3 把 ADR-0006 的四面向列為 hard constraint、缺一不可。本單元是其中 **IAM 面向**的唯一落點。

## ADR-0006 四面向逐項判定

| 面向 | 判定 | 影響與處置 |
|---|---|---|
| **IAM／授權** | **適用 —— 本單元就是它** | 使目標角色取得使用者管理功能的檢視權限。處置見下方 §high-risk action 三項 |
| **Encryption** | **不適用** | 本單元不新增欄位、不改變任何欄位的儲存形式；只翻轉既有布林欄位的值 |
| **Network exposure** | **不適用** | 不新增端點、不改變路由、不對外開放新介面。**但有一項既有事實須揭露**：權限種子函式有一個**公開未認證**的呼叫端（角色目錄端點），空表時可由外部觸發種子。本次不致出錯（預設值已改為開啟，觸發結果與補丁一致），但該路徑不在本單元的時序模型內 —— 如實標為既有限制，非本單元引入 |
| **Audit logging** | **適用** | 見下方 §audit logging 面向 |

## high-risk action 的三項（Q1=A 定案）

`org.md ## Deployment` 與 `project.md ## Mandated` 皆要求 IAM 變更前須有 plan + impact + rollback，並通過 human approval gate。本節即為該要求的落實。

### Plan

| 項目 | 內容 |
|---|---|
| 變更範圍 | 權限矩陣中**單一列**：目標角色 × 使用者設定功能的檢視旗標，由關閉改為開啟 |
| 兩處預設值來源 | 種子資料模組與資料庫初始化腳本**同步修改**（requirements FR-4.3；任一處未同步即視為未完成） |
| 既有環境套用 | 啟動期的目標式更新（只更新不插入、條件式、四態記錄），詳見 3.1 |
| 不變更的部分 | 編輯與審核旗標維持關閉；其餘 307 列完全不動；權限檢查**機制**完全不動 |

### Impact assessment

| 面向 | 評估 |
|---|---|
| **取得什麼** | 目標角色可檢視使用者清單與授權申請清單**兩個端點** |
| **範圍外溢** | 該功能識別碼同時開啟上述兩個端點 —— **此範圍已在 requirements FR-4 與 stories AC-3.5 經人工確認為可接受，非缺陷** |
| **不會取得什麼** | **不含編輯權** —— 變更、啟停用、角色調整等端點由同功能的**編輯**旗標把關，本次不動 |
| **影響的角色數** | 一個。其餘 10 個角色的權限完全不變 |
| **最壞情況** | 若補丁的執行順序或插入行為實作錯誤，會清空整份 308 列權限矩陣、全系統拒絕存取。3.1 已將「只更新不插入」與「在種子之後」定為契約，且論證了前者才是真正扛住災難的那一項 |

### Rollback path（Q2=A 定案）

**管理員經權限管理頁撤銷該權限。**

| 面向 | 內容 |
|---|---|
| 生效時機 | **即時**，不需部署、不需重啟 |
| 是否會被復原 | **不會**。撤銷後該列的最後異動者變成管理員帳號，不符補丁的更新條件，後續每次啟動都會跳過 |
| 這是設計保證而非巧合 | 條件式更新的謂詞正是為了保留管理員的調整而設計（3.1 的 R2） |
| **為何不是回滾部署** | 回滾程式碼只能拿掉補丁與預設值，**不會**把已寫入資料庫的那一列改回關閉。對本單元而言回滾部署**不等於**收回權限 |
| 已知限制 | 權限重置端點（管理員可呼叫）會刪光整張表並以種子重寫 —— 由於種子預設值已改為開啟，該操作會使權限**再度開啟**。此為既有行為，非本單元引入 |

### Human approval gate

**以 B1 這個 Bolt 的核可 gate 承接。** 本專案為單一決策者，B1 本來就有一道人工核可；額外設獨立關卡實質上是同一人再按一次（Q1 的選項 C 已據此排除）。

## Audit logging 面向

| 面向 | 內容 |
|---|---|
| 變更本身的可稽核性 | 補丁寫入時把最後異動者標記為**補丁專屬識別字**，使「這一列是被本補丁改的」在資料層可辨識 |
| 執行結果的可觀察性 | 四態記錄（已套用／已跳過／未套用：該列已被管理員異動／未命中目標列），後兩態為需人工處置等級 |
| **已知限制（繼承自上游）** | 權限變更的稽核記錄保存期約等於兩次部署間隔（requirements C-7）。本 intent 不修復 |

## SEC-1 不得擴大授權範圍

**需求**：本單元**只**翻轉檢視旗標。編輯與審核旗標必須維持關閉，其餘 307 列不得被觸及。

**可驗證性**：由 requirements NFR-4 的 allow/deny 雙向測試與 3.1 定案的 308 列全量比對測試共同覆蓋。

## SEC-2 不得因補丁而繞過既有的權限檢查

**需求**：本單元改變的是權限**資料**，不得改變權限**機制**。任何端點的授權判定路徑不得因本單元而改變。

**依據**：3.1 已明列本單元「不擁有權限機制本身」。

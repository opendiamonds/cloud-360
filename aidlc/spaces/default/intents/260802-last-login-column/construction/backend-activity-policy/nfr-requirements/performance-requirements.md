## 本單元的效能主張：設計上界，不是實測值

**必須先講清楚的事實**：依 S1／S5，repo **沒有任何觀測性依賴、CI 沒有效能測試**。因此本檔**不訂延遲預算** —— 訂了也沒有任何機制能驗證，那是虛假精確。

本檔改以**可由規則直接推導、無需儀表即可論證**的上界表述。

## P-1 寫入頻率上界（承 requirements NFR-1）

| 面向 | 內容 |
|---|---|
| **需求** | 同一帳號的活動時間寫入，**5 分鐘內至多一次** |
| **推導的系統上界** | N 個活躍帳號 ⇒ 每 5 分鐘至多 N 次寫入 |
| **依據** | 節流規則（requirements NFR-1／FR-1.3；門檻與邊界已由 3.1 定死） |
| **可驗證性** | **可**。節流判定為純函式，其邊界（恰為 5 分鐘時仍寫入、未達則不寫）可被單元測試與 property-based 測試直接斷言 |
| **不保證什麼** | **不是延遲保證**。單次請求的延遲增量未被量化，也無工具可量 |

### 這個上界在本專案的實際量級

依 S4，啟動流程種入 11 個預設帳號，本專案為單一組織的內部工具。即使活躍帳號數成長一個數量級，上界仍在每分鐘個位數次寫入。

**此處不宣稱「因此效能沒有問題」** —— 那需要量測。此處只主張：**寫入頻率的上界由規則保證，且該上界的量級遠小於任何合理的資料庫容量**。

## P-2 節流檢查本身不新增查詢

| 面向 | 內容 |
|---|---|
| **需求** | 節流判定**不得**為此新增一次資料庫查詢 |
| **依據** | 認證依賴在觸發點已持有使用者物件，其最後活動時間欄位隨該物件一併載入 |
| **後果** | 未達節流門檻的請求（即多數請求）**完全不觸及寫入路徑**，只做一次記憶體內的時間比較 |
| **可驗證性** | 由設計形狀保證（判定函式的輸入是已載入的值，不是查詢） |

這一條是 P-1 之外真正決定「是否成為請求路徑上顯著負擔」的機制：**絕大多數請求的成本是一次時間比較**，而非一次寫入。

## P-3 不新增連線需求

| 面向 | 內容 |
|---|---|
| **需求** | 寫入**沿用請求既有的資料庫工作階段**，不另開連線 |
| **為何重要** | 依 S2，建立引擎時**未帶任何連線池參數**，採函式庫預設值。若記錄器另開連線，等於在每個認證請求上增加一次連線取得 —— 在預設池大小下這是可觀的風險 |
| **與 C-2 契約的關係** | C-2 要求**自行提交**，但提交與另開連線是兩回事：沿用同一工作階段並自行提交即同時滿足兩者 |

## 明確不承諾的事

| 事項 | 為何 |
|---|---|
| 延遲預算（如 P95 增量上限） | 依 S1／S5 無任何量測或驗證機制。訂了就是不可檢驗的數字 |
| 吞吐量目標 | 同上；且依 S3 部署無資源限制設定，基準未定義 |
| 「效能沒有問題」這個結論 | 需要量測才能宣稱。本檔只論證寫入頻率的上界與其量級 |

## 待補承載機制（如實登錄，非本 intent 範圍）

導入效能量測工具在本 repo 尚無承載機制。本單元的效能主張因此停在「可由規則推導的上界」層級 —— 這是誠實的天花板，不是偷懶。

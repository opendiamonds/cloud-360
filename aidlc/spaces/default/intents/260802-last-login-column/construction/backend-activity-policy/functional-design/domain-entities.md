## 本單元觸及的實體：一個，且只加一個欄位

本單元**不引入新實體**。它在既有的使用者實體上新增單一欄位，並為該欄位建立兩條規則與一條寫入路徑。

## 使用者實體的變更

| 項目 | 定義 | 來源 |
|---|---|---|
| 欄位語意 | 該帳號**最後一次活動**的時刻（非最後登入 —— 任何以有效憑證發出的請求都算活動） | requirements FR-1.1；語意於 ideation 階段由「最後登入」重新定錨 |
| 型別 | 帶時區的時間戳 | requirements C-5（既有時間戳慣例）；components C-3 |
| 可為空 | **是，且必要** | 功能上線時既有帳號全部無值（requirements C-1）。若設為非空並給預設值，「從未活動」與「剛建立帳號」在資料上無法區分 —— 直接摧毀本 intent 的核心語意 |
| 資料庫層預設值 | **無** | 同上。**此處刻意偏離 requirements C-5** —— 該條原文要求「資料庫層預設值」，但那與「可為空且無預設值」不相容：任何非空預設值都會讓「從未活動」與「剛建立帳號」在資料上無法區分。本站判定 C-5 的真實意圖是「欄位新增不得使既有列變成不合法」，而**可為空**已完整滿足該意圖。此偏離為刻意且已標明，非疏漏 |
| 歷史 | **不保留** —— 每次寫入覆蓋前值 | requirements FR-1.2 |

### 為何不保留歷史，以及它對未來的影響

requirements FR-1.4 要求「資料模型須保留未來擴充為歷史紀錄的路徑」，且該需求無行為驗收條件 —— 其落點是設計審查。

**本單元的形狀符合該要求**：使用者表上的單一可為空欄位、每次覆寫，對日後新增獨立歷史表**沒有任何阻擋** —— 歷史表可用外鍵指向使用者，而現有欄位可保留為「最後一次」的快取或逕行移除。

**未引入會妨礙擴充的結構**：沒有把多筆活動塞進單一欄位的序列化字串，也沒有以欄位語意承載時序假設。

## 值域與不變式

| 不變式 | 說明 | 誰保證 |
|---|---|---|
| 值為空 ⟺ 該帳號自功能上線後從未發出過認證請求 | 空值是唯一的「無紀錄」表達，不用哨兵值 | C-3 的欄位定義（可為空、無預設值） |
| 值一旦非空，不會再回到空 | 沒有任何路徑會把它設回空 | C-2 只寫入當下時刻 |
| 值單調前進（極小例外見下） | 一般情況下新值晚於舊值 | C-2 的節流判定 |

**單調性的已知例外**：兩個並行請求同時判定為「該寫入」時，各自持有自己算出的當下時刻。資料庫的列鎖保證更新序列化，但**不保證後提交者的時刻較大** —— 最終值是後提交者的時刻，與兩者的較大值可能有次毫秒級的偏差。

在 5 分鐘的節流語意下這個偏差沒有實務影響，因此不需要鎖。**這是刻意接受的競態，不是缺陷**（components C-2 已記載，本站沿用不重新論證）。

## 生命週期

| 事件 | 對該欄位的作用 |
|---|---|
| 帳號建立 | 值為空（無預設值） |
| 首次認證請求 | 由空變為該請求的時刻 |
| 後續認證請求（距上次寫入未滿 5 分鐘） | **不變** |
| 後續認證請求（距上次寫入已達 5 分鐘） | 更新為該請求的時刻 |
| 帳號停用 | 不變（停用不清除活動紀錄，且**停用後的請求不再更新** —— 依據為 `business-rules.md` **R0**：觸發點在停用檢查之後，故已停用帳號的請求走不到記錄邏輯） |
| 帳號刪除 | 隨列一併刪除 |

**沒有任何清理、輪替或封存機制** —— 單一時間戳不累積資料，requirements FR-1.2 已定不保留歷史。本欄位**不產生資料成長**。

## 既有環境的欄位建立

依 Q1=A 定案，**新增一個獨立的補欄函式**，與既有的三個並列，由啟動流程呼叫。

| 面向 | 定義 |
|---|---|
| 語句形狀 | `ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...`，可重複執行 |
| 呼叫時機 | 啟動流程，與既有三個補欄函式同一區塊 |
| **交易邊界** | **自行提交** —— 既有三個補欄先例皆以自行提交的連線區塊包覆 DDL，不沿用外部傳入的 session。此細節必須明寫：`unit-of-work.md` 已記載同型遺漏在 C-7 造成的後果（寫入被靜默丟棄，而啟動日誌仍報「已套用」） |
| 失敗處置 | 沿用既有補欄函式的形狀（逐句 try、記錄警告後續行） |
| 生效前提 | **部署後必須完成一次服務重啟**（requirements C-2、stories AC-1.7）—— 這不是維運建議，是本設計成立的必要條件 |

**為何獨立而非擴充既有函式**：既有的三個補欄函式各對應一個功能批次。塞進既有函式會讓不同批次的 schema 變更混在一起，日後無法分辨哪個欄位屬哪次變更；且既有函式的命名與本 intent 無關。

依 requirements C-4，本欄位的 DDL 必須同步寫入 repo 根目錄的 schema 檔與部署文件。**未同步不得標示本單元完成。**

## 測試環境的差異（已知，不修復）

測試以 in-memory SQLite 執行，直接由模型建表、**從不呼叫啟動流程**。因此：

- 補欄函式在現行測試路徑上**不會執行**（其語法為 PostgreSQL 專屬）
- SQLite **不保存時區**，帶時區的欄位讀回為不帶時區的值 —— 這是時區正規化必須存在的直接原因（見 `business-rules.md`）

**後果如實記載**：C-3 的補欄**沒有自動化驗證**。承接方式為部署後重啟與人工核對（`unit-of-work.md` 已記載，本站不重新發明解法）。

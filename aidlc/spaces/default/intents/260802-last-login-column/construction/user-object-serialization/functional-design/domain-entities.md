# Domain Entities — U2 `user-object-serialization`

> Stage: functional-design（Construction 3.1）· Unit: `user-object-serialization`（kind: service）
> 上游來源：`../../../inception/application-design/components.md` C-4、`component-methods.md` C-4、`services.md`、`../../../inception/requirements-analysis/requirements.md`（下稱 requirements）。

> 事實查證 S1〜S5 見 `functional-design-questions.md` 的 `## Sources`。

## 本單元觸及的實體：一個回應模型，零資料庫變更

**使用者回應模型**（API 邊界的資料形狀）。本單元**不碰資料庫** —— 沒有 DDL、沒有新表、沒有新欄位。儲存層的欄位新增屬 U1。

這是本單元與 U1／U4 的分工邊界：U1 決定值**怎麼寫進去**、U4 決定**誰看得到頁面**，本單元只決定值**怎麼出現在 API 回應裡**。

## 回應模型新增的兩欄

| 欄位 | 型別 | 來源 | 可為空 | 有預設值 |
|---|---|---|---|---|
| 最後活動時間 | 時間，帶時區（UTC） | **讀自資料庫**（U1 建立的欄位），經 R3 正規化後放入 | **是** —— 空表示無紀錄 | **否**（R1） |
| 逾期旗標 | 布林 | **每次序列化計算**，呼叫 U1 的判定函式 | 否 | **否**（R1） |

### 兩欄的根本差異

| 面向 | 最後活動時間 | 逾期旗標 |
|---|---|---|
| 在資料庫中 | **存在**（U1 建立） | **不存在** |
| 取得方式 | 讀取後正規化 | 以當下時刻計算 |
| 隨時間變化 | 否（除非有新活動） | **是** —— 同一筆資料在不同時刻可能得到不同結果 |
| 可否由 ORM 自動轉換帶出 | 可 | **不可** —— ORM 物件上根本沒有這個屬性 |

最後一列是 components C-4 iteration 2 Finding N8 排除「ORM 自動轉換」分支的理由：要讓自動轉換成立，就得在模型層加一個自行取用系統時鐘的屬性，那會把 U1 刻意參數化的「當下時刻」在邊界處重新藏回去，與其可測性設計直接衝突。

## 回應模型的既有欄位（本單元不動）

依 S3，既有欄位中有兩個帶預設值。**本單元不改變任何既有欄位的預設值或型別** —— 那屬於範圍外的既有缺陷（見下）。

## 三個構造點

依 S1，回應模型在三處被構造，**三處全部都是手寫具名引數**（全 repo 自動轉換使用數為 0）：

| 構造點 | 用途 | 本次改動 | 現況（S2） |
|---|---|---|---|
| 使用者清單端點 | 本 intent 的**主要顯示路徑** | 加兩欄 | 傳 6 個欄位（完整） |
| 啟停用端點 | 管理員切換帳號啟用狀態後回傳更新結果 | 加兩欄 | 傳 5 個欄位，**缺一個既有欄位** |
| 角色調整端點 | 管理員變更角色後回傳更新結果 | 加兩欄 | 同上 |

requirements FR-2.5 要求**所有回傳使用者物件的端點**都包含新欄位。三處形式相同、風險相同 —— 依 R1，任一處漏傳都會在構造當下失敗。

## 已知的既有缺陷（範圍外，本單元不修但必須標明）

依 S2／S3，啟停用與角色調整兩個端點**漏傳一個既有欄位**，而該欄位有預設值，因此漏傳靜默通過、回應該欄一律為空。

| 面向 | 記載 |
|---|---|
| 性質 | **既有缺陷，非本 intent 引入** |
| 範圍判定 | `verification/phase-check-inception.md`「未進入 Construction 的事」已明確列為範圍外（獨立項目） |
| 與本單元的關係 | 它是 R1 的**反面教材** —— 本單元的兩個新欄位刻意不走這條路 |
| 為何不順手修 | 修它需要決定那兩個端點要不要做 S4 的額外查詢，那是獨立的行為變更；且 `team.md` 已規定修改此檔時不夾帶額外改動 |
| 會不會被 Q3=A 的測試抓到 | **不會**。三個端點皆宣告 `response_model`，key 集合由回應模型決定，該欄位一律存在；欄位集合斷言對「值被靜默預設為 `null`」完全無效。本單元**新增**的兩個欄位另以 R1 的必填宣告與 AC-1.5 的值斷言保護，但那兩項保護不及於這個既有欄位（它有預設值且不在本 intent 範圍） |

## 值的生命週期（單一使用者列）

| 情境 | 最後活動時間 | 逾期旗標 |
|---|---|---|
| 帳號剛建立、功能剛上線 | 空 | 否（U1 契約保證） |
| 該帳號發出過認證請求 | 該次活動時刻（UTC） | 依當下時刻與門檻計算 |
| 資料未變，但查詢時間往後推移 | 不變 | **可能由否翻為是** —— 這正是不儲存它的理由 |
| 帳號已停用 | 凍結於停用前的時刻（U1 的 R0） | 照常計算，會隨時間翻為是 |
| 帳號待授權 | 其實際活動時刻（U1 的 R0 判定待授權**計入**活動） | 照常計算 |

最後兩列的帳號都會出現在清單中（清單端點回傳全部使用者）。這是已知且已被接受的現況，非缺陷 —— requirements FR-4.2 已定案不做欄位級控制，refined-mockups 亦已為待授權狀態設計呈現方式。

## 與 U1 的介面

| 取用 | 用途 | 為何不自己做 |
|---|---|---|
| U1 的**時區正規化函式**（公開介面） | R3 的序列化前正規化 | 自寫第二份會產生可漂移且未被鎖住的副本，違反單一真實來源 |

本單元在 DAG 上**只依賴 U1**（`unit-of-work-dependency.md`）。

## Revision 1（2026-08-11）— `UserListPage`

新增的回應模型，非領域實體 —— 它是 API 契約的一部分，不對應任何資料表。

| 欄位 | 型別 | 必填 | 預設 | 語意 |
|---|---|---|---|---|
| `items` | `List[UserSchema]` | 是 | **無** | 本頁的帳號，順序即 `ORDER BY id` 的順序 |
| `total` | `int` | 是 | **無** | 符合查詢條件的帳號**總數**，不是本頁筆數 |
| `page` | `int` | 是 | **無** | 目前頁次（1 起算）；超出範圍時**回顯請求值** |
| `page_size` | `int` | 是 | **無** | 每頁筆數的**設定值**，不是本頁實際筆數 |

**四欄皆無預設值**是刻意的設計約束而非疏忽：帶預設值時，一個完全沒讀查詢參數的實作也會輸出四個形狀正確的 key，使驗收標準只能驗到「key 存在」而驗不到「值正確」。無預設值讓「忘記傳」在構造當下就是錯誤（實測：Pydantic 立即拋 `ValidationError: Field required`，非靜默補值）。

`UserSchema` 本身的欄位定義**不變**（Revision 1 之前已定義的兩個新欄位維持原樣）。

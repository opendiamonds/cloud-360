# Business Rules — U2 `user-object-serialization`

> Stage: functional-design（Construction 3.1）· Unit: `user-object-serialization`（kind: service）
> 上游來源：`../../../inception/application-design/components.md` C-4（下稱 components C-4）、`component-methods.md` C-4、`services.md`、`../../../inception/requirements-analysis/requirements.md`（下稱 requirements）、`../../../inception/user-stories/stories.md`（下稱 stories）、`../../../inception/units-generation/unit-of-work.md`、`unit-of-work-story-map.md`。
> 問答定案：Q1=A（新欄不設預設值）、Q2=A（每請求取一次時刻）、Q3=A（欄位集合完全相等）。
> 事實查證 S1〜S5 見 `functional-design-questions.md` 的 `## Sources`。

## 本單元擁有三條規則

R1 管欄位存在性（三個構造點都要帶出兩欄），R2 管衍生值的計算基準，R3 管序列化前的時區正規化。三條各自對應一個上游明確點名的失敗模式。

## R1 — 兩個新欄位不得有可靜默通過的預設值（Q1=A）

**規則**：兩個新欄位在回應模型上**必填**，任一構造點漏傳即在構造當下失敗。

### 為何這條規則存在：既有缺陷就是它的反面教材

依 S2／S3，三個構造點中有**兩個**漏傳了一個既有欄位，而該欄位有預設值，所以漏傳不報錯、回應靜默為空。

**這正是 components C-4 逐字警告的「完整複製既有缺陷」**：若給兩個新欄位一個預設值然後只改清單端點，兩個 PUT 端點會回傳空值，stories AC-1.5 逐字要求的「帶有與資料庫一致的值……而非因構造遺漏而缺失**或為 `null`**」直接失敗，**而所有現有測試都會是綠的**。

### 必須釐清的一件事：欄位集合斷言抓不到構造遺漏

實測三個端點皆宣告 `response_model`，因此**回應 JSON 的 key 集合完全由回應模型的欄位宣告決定，與構造點傳了什麼無關** —— 有預設值的欄位不論傳不傳都會出現在 key 集合中，只是值不同。

| 失敗模式 | 欄位集合斷言抓得到嗎 | 真正抓得到的是什麼 |
|---|---|---|
| 構造點漏傳**必填**欄位 | **抓不到**（key 仍在） | **R1 本身** —— 必填欄位缺漏時在構造當下拋錯，端點回 500 |
| 構造點漏傳**有預設值**的欄位 | **抓不到**（key 仍在、值靜默為預設值） | **值斷言**（AC-1.5 的 Then 逐字要求；驗證項見 `business-logic-model.md` 的驗證強度表） |
| 回應模型本身增刪欄位 | **抓得到** | 欄位集合斷言的真正用途 |

**因此 R1 不是靠測試守護的規則，它本身就是結構性保護** —— 必填宣告讓構造遺漏成為執行期的硬失敗，而不是靜默的空值。這一點在本站初版被錯誤地歸功給欄位集合斷言，此處更正。

### 為何不採共用工廠函式（C-4 的選項二）

| 理由 | 依據 |
|---|---|
| 工廠拿不到 C-4 寫的簽章 | 依 S4，清單端點的既有欄位之一需要一次**額外的 DB 查詢**（且只在該使用者為待授權時執行），另兩處完全不傳。`(使用者物件, 當下時刻)` 重現不了這個差異，工廠得多接參數或多接 session |
| 工廠會順手碰到範圍外的缺陷 | 那兩處的漏傳已被 `verification/phase-check-inception.md` 明確劃在本 intent 範圍外；走工廠必須就地決定補或不補 —— 補了超範圍，不補則工廠內部仍要分歧 |
| 與既有團隊規則同向 | `team.md ## Code Style`：「修改 `user_router.py` 就地沿用既有形狀，不趁機夾帶抽取」 |

**如實記載這條規則的邊界**：R1 保證的是「漏傳會**失敗**」，不是「不可能漏傳」。將來新增第四個構造點仍需人記得帶上兩欄 —— 但那時會在構造當下拋錯，不是靜默回傳空值。這個差別就是本規則的全部價值。

## R2 — 逾期旗標是衍生值，且整次回應共用同一個判定時刻（Q2=A）

**規則**：逾期旗標**不進資料庫**，每次序列化時以當下時刻呼叫 U1 的判定函式計算。**當下時刻在進入端點時取一次，整次回應的所有列共用**，且該時刻**必須帶時區（UTC）**。

### 「帶時區」是硬性約束，不是風格

U1 的規則層明載：把**不帶時區**的當下時刻傳進判定函式，與資料庫讀回的帶時區值相比較會直接拋型別錯誤。由於本規則讓整次回應共用同一個時刻，一旦取錯，**三個端點的第一次比較就會全部失敗**——不是偶發，是必然且全面。

此約束與 R3 的正規化是同一個時區契約的兩端：R3 管**讀出來的值**，本規則管**比較的基準**。

| 面向 | 定義 |
|---|---|
| 儲存 | **不儲存**。它是每次請求重新算出來的 |
| 為何不儲存 | 保證永遠反映請求當下的判定，不會因資料陳舊而失準 |
| 計算者 | **U1 的逾期判定函式**，本單元不自行實作判定邏輯 |
| 時刻來源 | 端點進入時取一次，往下傳遞 |

### 為何整次回應共用同一個時刻

1. **同一張表的逾期標示彼此可比較** —— 不會出現「同一次回應中兩列用不同基準判定」的情形。
2. **可測性** —— U1 的判定函式**刻意把當下時刻參數化**。每列各取一次會讓測試必須 patch 系統時鐘才能控制判定結果，等於把 U1 刻意打開的接縫在呼叫端重新封死。

## R3 — 序列化前套用時區正規化（呼叫 U1 的公開函式）

**規則**：最後活動時間在放進回應之前，必須先通過**與逾期判定同一份**的時區正規化。

### 為何這條規則存在

最後活動時間從資料庫直通序列化時，在 SQLite 測試路徑下讀回為**不帶時區**的值，序列化後不帶偏移量。requirements NFR-5 的端點測試若斷言 UTC 形式就會失敗 —— 而那正是 team-practices 規則 B 的第一支測試。

### 為何呼叫 U1 而非自己寫一份

U1 的正規化 helper **已為此改為公開介面**（U1 reviewer iteration 1 Finding 1 的定案）。若本單元自寫第二份，就會產生一份**可獨立漂移且未被鎖住的副本**，違反 `team.md ## Code Style` 的單一真實來源規則（「新增副本的同一個 PR 必須一併新增鎖住兩者一致的測試；無法寫測試的副本不新增」）。

**這是一條跨單元的實質依賴**，不只是概念上的一致：兩處若各自正規化而規則不同，逾期判定與顯示值會對不上。

## 空值語意（上游已保證，本單元不重新定義）

最後活動時間為空時，逾期旗標**必為否** —— U1 的判定契約已保證（無紀錄態回傳否）。這兩欄**不會**出現「無紀錄卻標記逾期」的組合，前端不需防禦此情形。

## Revision 1（2026-08-11）— 分頁（C-9 後端半）

承 units-generation Revision 1（C-9 後端併入本單元）與 application-design 的 AD-10／AD-11。

### BR-P1 清單端點的分頁契約

| 項目 | 規則 |
|---|---|
| 查詢參數 | `page`（整數，**最小值 1**，預設 1）、`page_size`（整數，**最小值 1、最大值 100**，預設 **20**） |
| 約束的表達方式 | **框架原生的查詢參數範圍約束**，不在函式內手寫檢查。理由：前者在依賴解析階段就擋下、非法值結構上到不了查詢層，且約束會進入 OpenAPI 規格因此被型別契約與規格漂移 gate 覆蓋 |
| 違反約束 | 框架自動回 **422**，回應**不含任何帳號資料** |
| 回應模型 | `UserListPage`：`items`、`total`、`page`、`page_size` —— **四欄皆必填、皆無預設值** |

### BR-P2 `total` 必須獨立計數

`total` 為**不帶 offset／limit 的計數查詢**結果，**不得**由 `len(items)` 導出。

由 `len(items)` 導出的實作在「總數少於一頁」時完全正確，只在多頁時錯 —— 而目前系統只有 12 個帳號，多頁情境不會自然出現。這條規則存在的意義就是讓那個錯誤在測試中被抓到而不是上線後才發現。

### BR-P3 排序必須保留

分頁查詢**必須保留既有的 `ORDER BY id`**。這是「重複請求同一頁得到相同帳號與相同順序」的結構前提；沒有確定全序時，`LIMIT`／`OFFSET` 的結果集順序未定義，而 CI 對 flaky 的容忍會把由此產生的間歇失敗吸收掉。

### BR-P4 超出範圍的頁次不是錯誤

頁次**合法但超出實際範圍**（例如共 2 頁請求第 5 頁）時：回 **200**、`items` 為空、`total` 與 `page_size` 仍為正確值、**`page` 回顯請求值不夾到最後一頁**。

實作上不需特別處理 —— offset 超過總數時查詢自然回空清單。**但必須有測試釘住它**，否則日後有人「順手」加上夾頁邏輯不會被發現。

### BR-P5 不接受非分頁的查詢參數

端點**不得**因 `sort`／`order_by`／`filter` 等參數改變回傳的帳號集合或順序。這是 FR-6.7（不引入排序／篩選）在契約層唯一正向可測的落點 —— 分頁改的就是查詢參數面，順手加一個排序參數是最典型的越界。

### 與既有三個構造點的關係

envelope 是本單元的**第四個回應構造點**。前三個（清單、啟停用、角色調整）構造 `UserSchema`，第四個構造 `UserListPage`。四者的共同風險相同：**手寫具名引數 ＋ 可靜默通過的預設值 = 漏欄位而無人察覺**。既有的 `requested_role` 漏傳就是這個風險已經發生過的證據。

# 技術選型決定 — api-type-contract（U5）

> **上游輸入**：`../../../inception/application-design/components.md` 的 **C-8**（四個組成、兩道 gate、兩項位置約束、版本釘選）與 `decisions.md` 的 **AD-9**。本單元 kind 為 `packaging`，其行為完全由 C-8 界定，故**沒有**自己的 `functional-design/`（該階段的 `produces_kinds` 對 `packaging` 不產出 business-logic-model／business-rules）—— 這是 kind 的直接後果，不是缺漏。

## 其餘 NFR 面向的不適用判定（不留空白）

本單元 kind 為 `packaging`，**完全在建置期**、不部署、不進執行路徑。逐項判定：

| 面向 | 判定 | 理由 |
|---|---|---|
| 效能 | **不適用** | 無執行期行為。建置期成本為兩次產生器執行（實測各約 65ms），不構成任何效能主張 |
| 擴展性 | **不適用** | 不部署、無負載、無狀態 |
| 可靠性 | **部分適用** | 唯一的可靠性面是「gate 會不會誤報」，見 T-2；其餘（可用性、復原、降級）皆不適用 |
| 安全 | **適用** | 見 `security-requirements.md` |

## T-1 兩份產出物、兩道 gate、分屬兩個 CI job

| 產出物 | 位置 | Gate 位置 | 為什麼是那裡 |
|---|---|---|---|
| 規格檔 | repo 根目錄 | CI **backend** job | 真相來源是後端程式碼；該 job 已有 Python 環境 |
| 型別檔 | `frontend/src/` 內 | CI **frontend** job | 需要 node 與產生器；該 job 為全樹 checkout，讀得到 repo 根的規格檔 |

**為何需要兩道而非一道**：規格檔的 gate 只保證「規格 == 後端程式碼」。若有人重新 dump 了規格卻忘了重產型別檔，型別檔仍宣告舊形狀，而 `tsc -b` 檢查的是「**用法**是否符合型別檔」，不是「型別檔是否符合規格檔」—— 那條路徑會靜默通過，前端在執行期拿到未定義值。**backend job 沒有 node，結構上不可能重產型別檔**，所以第二道 gate 必須在 frontend job。

## T-2 gate 的誤報風險與其處置（本單元唯一的可靠性主張）

| 層面 | 實測 | 處置 |
|---|---|---|
| 同一組依賴版本 | 規格輸出為**位元決定性** | 無需處置 |
| 跨依賴版本 | **會飄** —— 同一份原始碼換 `fastapi`／`pydantic` 版本即產生差異 | `requirements.txt` 對這兩支**精確等值**釘選（見 U2 的 `tech-stack-decisions.md` T-2） |

不釘的後果不是「偶爾紅一次」，而是**紅燈與真漂移在訊號上不可區分** —— 會誤報的 gate 比沒有 gate 更糟，它訓練人忽略紅燈。

## T-3 gate 本身的有效性必須以刻意漂移實測

本單元的交付物**就是** gate，這是自我驗證 —— 沒有任何外部機制保證這兩道 gate 真的會失敗（例如被寫成永遠通過的形式）。

**採用時必須以一次刻意的漂移實測**：改一個欄位名而不重新產生，確認兩道 gate 確實變紅。

**已執行，結果如下**（不是計畫，是已完成的動作）：

| Gate | 乾淨時 | 刻意漂移時 |
|---|---|---|
| 規格漂移（backend job） | exit 0 | **exit 1** |
| 型別漂移（frontend job） | exit 0 | **exit 1** |

兩道皆確認會真的失敗，且錯誤訊息指出該跑哪一個指令修復。

## T-4 型別檔的 lint 作用域

型別檔進入 `frontend/src/` 後會落入既有 lint 的作用域（忽略清單只有建置輸出目錄）。**定案：納入作用域，不加豁免。**

理由：實測產生器的輸出**自然通過**現行規則集（`npm run lint` 維持 0 errors）。加豁免是在沒有實際衝突時預先開後門；若日後產生器輸出真的違反某條規則，屆時再以具體理由處置，比現在憑空豁免誠實。
